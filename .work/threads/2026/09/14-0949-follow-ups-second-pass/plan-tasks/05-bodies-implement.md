**The rules applied to every body in this task.** The letters are for this brief only; none of them, and no `DR<N>` identifier, is written into a body.

- **A. Prefix.** Every pointer to a file inside the skill's own folder is written with the literal prefix `<skill_path>/` — `<skill_path>/references/formats/adr.md`, `<skill_path>/references/instructions/append-log-line.md`, `<skill_path>/references/worked-example.md`. Project paths (`docs/adr/`, `docs/glossary.md`, `.wip/roadmaps/`, thread files such as `spec.md`, `plans/<folder>/`) stay bare.
- **B. Project-layer inputs.** The first two items of `## Inputs` become, with the target clause adapted to the skill (the per-body clause is given below):

  ```markdown
  - `docs/adr/`, read via `/consult-adrs` — the project decisions bearing on <the target>.
  - `docs/glossary.md`, read via `/consult-glossary` — the project's fixed terms, to be used in everything you write.
  ```

  Where the body invokes the conflict rule, the skill is a procedure, never a document: "the conflict rule `/consult-adrs` carries" becomes "as `/consult-adrs` instructs" (or an equivalent that reads as an instruction to classify). The folder is `docs/adr/`, singular, everywhere.
- **C. One shape for Inputs items.** Every item reads `- <path or source><, presence clause when it may be absent> — <what it is and what it is for>.` Remove every trailing tag (`; authoritative.`, `. Authoritative.`, `. Material.`, `. Material: …`, `Authoritative for intent.`, `Authoritative within the thread.`), and fold the inline forms (`, authoritative within the thread;`, `Material either way`) into the clause. Fold what carried information — the thread's `adr/` and `glossary.md` items say the delta takes precedence over the project records inside the thread; a `Material: <what to read>` tag becomes the clause's own sentence — and drop what was decoration. The presence clause is exactly one of `when present`, `when the seed carries one`, `when the file exists`: rewrite every other form (`when the thread holds one`, `whenever the thread holds one`, `when the invocation carries one`, `when the invocation names an entry`, `when it names one`, `when the thread's owner authored one`, `when a plan folder is the form`) to the nearest of the three. An item with no clause is always present or is the primary input; a primary input keeps its accepted-forms text inside its clause, in as many sentences as it needs. After the sweep the words "authoritative" and "material" survive in an item only where they state a ranking the body's procedure uses (for example the primary-input item of the plan skills: the reference "carries no authority over a `spec.md` the thread holds"). Where the body ranks its sources in prose (the review skills' authority-anchor section, `spec`'s "these are the whole of what the spec rests on"), that prose stays and nothing is added to compensate for a removed tag.
- **D. Pointers are directives.** A pointer to an instruction file is the step: "Follow `<skill_path>/references/instructions/<name>.md`" (or "follow … with <parameters>", "by following …"). A pointer to a format file is what a write or read conforms to: "following `<skill_path>/references/formats/<name>.md`" or "in the shape `<skill_path>/references/formats/<name>.md` defines". Other verbs are fine where they read better, provided the intent — open this file and do what it says, or conform to it — stays plain. Strict: the word `per` never directly precedes a `<skill_path>/` pointer; and no text around a pointer restates what the pointed file holds. Delete every sentence or clause that can be deleted because the reference carries it (for `emit-pending-decisions.md`: "one point per open decision", what each point states; for `emit-pending-review.md`: "as a single bundle"; for `append-log-line.md`: the line's shape, the seven types, the transient-framing rule; for `write-implementation-report.md`: the list of what the report folds in; for a format: its section list). Keep only the skill-specific parameters the file leaves open — producer or reviewer name, target, what the line states, which folder, the token and its reason — and any rule the body needs for its own judgment at that step, written as the skill's rule and not as a paraphrase with a citation. Same-body section pointers written "per `## <Section>`" or "per `### <Section>`" are untouched in text and count.
- **E. Every exit through the terminal-outcome instruction** (completion-oriented bodies only). Every sentence that spells a literal `Outcome:` line — refusal, block, or completion — becomes a directive to the instruction with the token and the reason as parameters: "follow `<skill_path>/references/instructions/emit-terminal-outcome.md` with `REFUSED`, naming the dirty paths and how to re-invoke", "… with `DONE` and `Spec written: spec.md`", "… with `BLOCKED` and `pending decisions at <bundle path>`". Existing "End per `references/instructions/emit-terminal-outcome.md` with `Outcome: DONE — …`" sentences become "Follow `<skill_path>/references/instructions/emit-terminal-outcome.md` with `DONE` and `…`". The literal string `Outcome:` appears nowhere in a `SKILL.md`. A body names one token as the parameter at an exit; it never lists `DONE`, `BLOCKED`, and `REFUSED` together as a vocabulary. Skill-local reply tokens and lane verdicts are a different vocabulary and are left alone.

Everything else in each body — posture, write boundary, order of acts, the judgment between them, section headings, numbered-step count, same-body pointers — is unchanged. Preserve each file's existing line-wrapping style (`open-ticket` wraps at 80 columns; the others do not).
