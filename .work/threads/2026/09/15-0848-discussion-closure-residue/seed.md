# Discussion closes on real forks and the spec carries the rest

A review of the open issues against the redesigned suite found that #2 and #57 share one root and one fix. In #2, an agent ended a discussion by declaring a list of details "mechanical" and leaving them to the specification, which then made choices nobody had recorded. In #57, agents interrupt a discussion with a generic "shall we keep going or finish here?" prompt, either abandoning undecided points or asking whether to continue when nothing is left to discuss.

The wanted behaviour: the `discussion` skill presents only real forks, with no limit on how many, and recognises the moment when what remains are points with an obvious answer — mechanical steps, direct consequences of decisions already made, or choices where any admissible option would do. At that moment it tells the user it sees no more real forks, lists every remaining point of that kind in full, and asks whether any of them should be promoted to a fork or the discussion can stop. Those points are not written to the log: the user's acceptance means "this is not a fork", not "I agree with your answer", so they are not settled points and carry no binding weight. When the user later invokes `spec`, the spec is written fully with those choices baked in, and each one is listed as a bullet in a dedicated section of the spec so a reader and a reviewer can see what the spec settled on its own. The two skills are connected by sharing this one concept, not by naming each other.

Settling this needs a fixed vocabulary: the log's `assumption` type, the points the discussion agent holds back, the section of the spec that lists them, the spec's degrees of freedom, and the report's deviations all currently lean on the word "assumption" or on definitions that overlap. This thread fixes those terms in its glossary delta, then changes `discussion` and `spec`, and the shared format files those changes touch.
