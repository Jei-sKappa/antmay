# Ecosystem survey: where the truth about a change lives

**Summary.** Across roughly forty toolkits, methods, and literatures surveyed, the dominant shape for a change's design is a **single per-change specification document paired with a small, in-place-maintained project-level layer** (a constitution, steering files, standards, a glossary, an ADR log). A per-change *decision log* as the origin of that spec is nearly unoccupied territory: the only serious occupant is BMAD's `.memlog.md`, which reaches the same design conclusion Antmay did, for an explicit reason — deriving the contract from an append-only log lets several planning skills feed one artifact without merge drift. But BMAD's log is not lossy, because it records capabilities, constraints and assumptions alongside decisions, so re-derivation invents nothing; Antmay's log records only decisions, which is the mechanical cause of its infer-then-strip loop. Everywhere else the literature is consistent: **freezing a record is only safe when a separately maintained current-state document exists** (IETF, PEP, Rust, arc42, Martraire all say so), and **the mechanisms that actually separate historical from authoritative move authority onto a small enumerable current surface** rather than annotating a growing historical one. On multi-phase work the field has converged hard against writing later phases up front — Shape Up, rolling-wave planning, fog-of-war planning, and OpenSpec's change DAG all refuse it. The recommendation is a variant of option B.

| Project / tradition | Where a change's truth lives | Decision capture | Historical vs authoritative | Multi-phase strategy |
| --- | --- | --- | --- | --- |
| **Antmay (today)** | `decisions.md` → derived `spec.md` | Per-change append-only log, `DR<N>`, supersession records | Archive folder, optional in practice | Roadmap with full child briefs up front + append-only feedback |
| **GitHub Spec Kit** | `specs/<feature>/spec.md` + `constitution.md` | None; `/clarify` writes answers back into the spec | Team-chosen: flow-forward (immutable dirs), living spec, or flow-back | "Spec of specs": shallow roadmap table, design deferred per slice; roadmap edited in place |
| **AWS Kiro** | `requirements.md` (EARS) + `design.md` + `tasks.md` | None; rationale sits inside `design.md` | None documented | Multiple feature-scoped specs; no roadmap artifact |
| **OpenSpec** | `changes/<id>/` delta → merged into `openspec/specs/` | `design.md` § Decisions (a section, not a log) | Merge delta into living spec, move change to `changes/archive/<date>-<id>/` | Many small changes with a dependency DAG; refuses bulk up-front specs |
| **BMAD Method** | `.memlog.md` (canonical) → `SPEC.md` re-derived each run | **Per-change append-only typed log**, supersession by appending, no status field | Supersession inside the log; `bmad-retrospective` reconciles spec to code at epic close | `stories.yaml`, "Learnings from Previous Stories", `bmad-correct-course` change proposal |

| **Taskmaster** | `tasks.json` derived from `prd.txt` | None | None | Task expansion on demand |
| **Ralph loop** | `specs/` (living) + `fix_plan.md` (rewritten each iteration) | None; git is the history | `fix_plan.md` is current by construction | One loop, replanned every iteration |
| **Cline / Roo Memory Bank** | `activeContext.md` + `progress.md`, rewritten | None | Split by file: stable files vs volatile files | n/a |

## 1. Spec-driven toolkits

### 1.1 GitHub Spec Kit

[github/spec-kit](https://github.com/github/spec-kit) runs `/speckit.constitution → specify → clarify → plan → tasks → analyze → implement → converge` over `specs/<NNN-feature>/{spec.md,plan.md,tasks.md,checklists/}` plus a durable `.specify/memory/constitution.md`. The constitution is the project-level layer and it is genuinely authoritative: `/speckit.analyze` treats it as "**non-negotiable** within this analysis scope. Constitution conflicts are automatically CRITICAL and require adjustment of the spec, plan, or tasks—not dilution, reinterpretation, or silent ignoring of the principle." Changing a principle "must occur in a separate, explicit constitution update." Decisions are not captured anywhere as records; `/speckit.clarify` asks up to five targeted questions and "encod[es] answers back into the spec," i.e. the spec is the decision store.

Spec Kit is the only toolkit that has published a taxonomy of the exact fork Antmay faces. [Spec Persistence Models](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md) names three and declines to pick one:

| Model | Mutation rule | Watch out for |
| --- | --- | --- |
| Flow-back | Edit any artifact, then reconcile | "Silent drift between artifacts" |
| Flow-forward | New feature directory per requirement change; completed dirs immutable | "Duplicate or fragmented context" |
| Living spec | Edit `spec.md`; regenerate `plan.md` and `tasks.md` | "Lost rationale in regenerated files" |

Note that Antmay is currently *flow-forward at thread level and flow-back inside a thread*, and is paying both named costs. Spec Kit's own two orienting questions are the fork restated: "Should completed feature directories be historical records or editable work areas?" and "Is `spec.md` the single source of truth, or are `plan.md` and `tasks.md` allowed to become co-equal sources?" It also warns, in the living-spec path, to "preserve important implementation rationale before replacing derived artifacts."

Its multi-phase answer, [Spec of Specs](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-of-specs.md), is the direct counterpart to Antmay's Roadmap and differs in exactly the way the field report predicts. The roadmap is a **table** with an immutable ID, a one-line intent, a scope boundary, dependencies, status, and a link — and "is deliberately shallow: it names and orders the sub-features but does **not** design them. The design happens when each slice runs through its own `/speckit.specify`." The maintenance rule is "**Roadmap first, then reconcile.** When scope shifts, update the roadmap entry first, then update any sub-specs it affects. The roadmap is the source of truth for how the epic is divided." It is a living index edited in place, with no feedback channel, because there is nothing frozen to send feedback about. Spec Kit is also explicit that decomposition "adds the most overhead of any strategy" and should be reached for only after task-scoping and subagent delegation fail.

### 1.2 AWS Kiro

[Kiro](https://kiro.dev/docs/specs/) generates `requirements.md` (user stories with EARS acceptance criteria), `design.md` (architecture, sequence diagrams), and `tasks.md` (each task mapping back to a requirement), behind a three-phase human approval gate. The project-level layer is [steering](https://kiro.dev/docs/steering/): `product.md`, `tech.md`, `structure.md`, "included in every interaction by default," plus custom files with `always` / `fileMatch` / `manual` / `auto` inclusion modes and the instruction to "treat steering changes like code changes—require reviews."

Kiro documents no spec lifecycle at all: its [best practices](https://kiro.dev/docs/specs/best-practices/) page covers organizing multiple feature specs and says nothing about staleness, archiving, or what a spec means after the feature ships. Drift handling is manual and user-triggered — the developer must notice and ask for a refresh — and there is an open request to [record a git ref in spec metadata to detect code drift](https://github.com/kirodotdev/Kiro/issues/9435). Martin Fowler's site classifies Kiro as **spec-first**: the spec is discarded, not maintained.

### 1.3 The taxonomy everyone now uses

Birgitta Böckeler's [*Understanding Spec-Driven Development: Kiro, spec-kit, and Tessl*](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) supplies the field's working vocabulary: **spec-first** (write it, then discard it), **spec-anchored** (maintain it alongside the code), **spec-as-source** (humans edit only the spec; code is generated and marked "GENERATED FROM SPEC - DO NOT EDIT"). She classifies Kiro and spec-kit as spec-first in practice — spec-kit's branch-per-spec strategy shows its "lifetime bound to change requests, not features" — and only Tessl as pursuing spec-anchored. Her caution is that without a maintenance strategy "specs risk becoming stale artifacts rather than genuine sources of truth," and she is openly sceptical of "lots of up-front spec design… especially when it's overly verbose."

**Antmay is spec-first by this taxonomy**, and the field report's finding (3) is the predictable consequence: spec-first artifacts left in an unarchived folder are read as if they were spec-anchored.

### 1.4 OpenSpec: the delta-merged-into-living-spec instance

[OpenSpec](https://github.com/Fission-AI/OpenSpec) splits `openspec/specs/<capability>/spec.md` (the durable "source of truth… how your system currently behaves") from `openspec/changes/<id>/` (`proposal.md`, optional `design.md`, `tasks.md`, and delta specs using `## ADDED` / `## MODIFIED` / `## REMOVED`). Archiving merges the delta into the living spec and moves the change folder to `changes/archive/<date>-<id>/`. This is the only mechanism surveyed that makes "historical or authoritative?" unaskable rather than answerable.

Two of its documented weaknesses are directly instructive. First, from a community schema author: "Because `design.md` is archived with the change, that rationale becomes invisible to future proposals" — which motivated a [`spec-driven-with-adr` schema](https://intent-driven.dev/blog/2026/04/29/spec-driven-development-with-adr/) adding an ADR artifact that lives *outside* the change folder so decisions survive archiving. **A project that merges specs into a living layer still needs a durable home for rationale.** Second, its brownfield stance rejects bulk up-front specification: "Writing specs for code you aren't changing feels productive and usually isn't. Those specs go stale, because nothing forces them to track reality." Its multi-phase answer is many small changes with a dependency DAG rather than one multi-phase plan, motivated by the observation that "parallel work can accidentally reintroduce assumptions already removed by another change."

### 1.5 agent-os: a framework that deleted its decision log, then most of itself

[buildermethods/agent-os](https://github.com/buildermethods/agent-os) is the single most useful negative data point in this survey, because it ran both experiments and abandoned both.

Its v1.0 product layer included `.agent-os/product/decisions.md` for decision logging. The [v1.4.1 changelog](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md) records its removal verbatim: "Earlier versions added a decisions.md inside a project's `.agent-os/product/`. **In practice, this was rarely used and didn't help future development.**" It was replaced by per-spec **Recaps** — "short summaries of what was built… Similar to a changelog, but more descriptive and context-focused," generated automatically at task completion. Note the direction of the swap: from *why we decided* (written before) to *what we built* (written after, from evidence).

Then v3.0 (2026-01) retired the spec-writing, task-breakdown and orchestration layers entirely: "Spec creation now defers to **Plan Mode**… the industry-standard approach to spec-driven development in 2026+", "Implementation/orchestration phases retired—frontier models handle this well on their own now." What survives is the durable project layer: `agent-os/standards/` with an `index.yml` for selective injection, and `agent-os/product/{mission,roadmap,tech-stack}.md`. `/shape-spec` runs *inside* plan mode, asks targeted questions against standards and product context, and saves `plan.md`, `shape.md` ("shaping decisions and context from our conversation"), `standards.md` and `references.md` to a timestamped spec folder — as **Task 1 of the plan**, i.e. the durable record is written as the first act of execution, not maintained during the conversation.

The lesson is not that decision logs are worthless — Antmay's field report shows the opposite on its own evidence — but that a decision log **at the wrong scope** (project-level, written from a per-change moment, with nothing consuming it) decays into unread ceremony. What kept its value in agent-os was the *standards* layer, which is consumed on every run.

### 1.6 Taskmaster, spec-workflow-mcp, cc-sdd

[claude-task-master](https://github.com/eyaltoledano/claude-task-master) parses `.taskmaster/docs/prd.txt` into `tasks.json` and derived per-task files; there is no decision record and no spec lifecycle. Its reported failures are about derived-artifact consistency rather than philosophy — [stale MCP reads vs CLI](https://github.com/eyaltoledano/claude-task-master/issues/348), [task files not regenerating on expand-all](https://github.com/eyaltoledano/claude-task-master/issues/344), and [a race condition when multiple Claude Code windows write `tasks.json`](https://github.com/eyaltoledano/claude-task-master/issues/1567) with no file locking. That last one is worth flagging for Antmay's CLI, which writes thread artifacts from concurrent stages.

The Kiro-clone tier adds three lifecycle experiments. **spec-workflow-mcp** adds an `archive/specs/<name>/` destination and an explicit `approvals/` state with a review dashboard, but its `design-template.md` has no Decisions section. **cc-sdd** adds a `spec.json` carrying `phase` and per-document `{generated, approved}` flags — a status-field lifecycle with no archive. **MUSUBI** keeps `steering/memories/architecture_decisions.md` as a *project-wide cumulative* decision file alongside `lessons_learned.md` and `technical_debt.md`, plus a traceability matrix claiming full Req→Design→Code→Test mapping.

### 1.7 Tessl, and the retreat from spec-as-source

[Tessl](https://tessl.io) is the field's purest spec-as-source bet: `specs/<project>/<name>.spec.md` with directive links (`[@generate]`, `[@test]`, `[@use]`), stability tags (`{ .locked }`, `{ .impl }`), and generated code carrying `// GENERATED FROM SPEC - DO NOT EDIT`. Guy Podjarny's framing is the strongest statement of the thesis: "Code is a representation of an intent… once code exists, the 'why' behind those decisions evaporates." There is no decision log, no archive, no status field; `plans/*.plan.md` records what happened, never why one option beat another. External review names dependence on a non-deterministic compiler, waterfall risk from large up-front specs, and a "sledgehammer problem" where a trivial code tweak requires editing the whole spec. In January 2026 Tessl repositioned as an "Agent Enablement Platform" around skills and evals, and its core-concepts pages no longer define "spec" or "capability" — the most ambitious spec-anchored attempt stepping back from the problem.

### 1.8 Plan modes, orchestrators, and vendor instruction files

**Claude Code's plan mode** writes to `~/.claude/plans/<slug>.md` and `ExitPlanMode` reads a file already written. [Issue #29445](https://github.com/anthropics/claude-code/issues/29445), proposing named persistent plans with a `draft → approved → completed → superseded` lifecycle, characterised the status quo as "disposable, anonymous temp files" and **was closed as not planned**. **Cursor's Plan mode** saves a Markdown plan to the home directory by default, with an opt-in "save to workspace" into `.cursor/plans/`; neither docs nor changelog address staleness. **Windsurf/Devin Cascade** writes a session-scoped plan with an Open Questions section outside the repository. Parallel-agent orchestrators (Conductor, Vibe Kanban, Claude Squad, Sculptor) are worktree runners with **no artifact model at all**.

Vendor instruction files are all *standing configuration*, never per-change. Amazon Q Developer (`.amazonq/rules/*.md`) is being sunset in favour of Kiro. GitHub Copilot ships `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md` with `applyTo` globs, and prompt files — but **no official spec workflow**; its coding agent writes its plan into the PR description and overwrites it as it pushes. GitHub's own docs note instructions can be combined "but avoid conflicting instructions as **no priority order is applied**." [AGENTS.md](https://agents.md), now stewarded by the Agentic AI Foundation across ~60k projects, is explicitly framed as living documentation with **no concept of decisions, history, or staleness**.

Two hosted products are near-misses worth naming. **Factory.ai** persists approved plans to `.factory/docs/YYYY-MM-DD-slug.md` and describes them in decision-record language — "a durable record of what the team intended, and future agents can use it when the code alone does not explain a decision" — but the artifact is plan-shaped and has no supersession. **Traycer** has the best staleness primitive found anywhere: review findings are tagged Critical / Major / Minor / **Outdated**, where Outdated means findings that "may have been relevant at an earlier stage but are no longer applicable given subsequent changes." **Amp** answers context loss with an explicit `/handoff` that generates an editable prompt for a fresh thread rather than letting a long thread degrade.

**GSD** ([open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)) is worth naming here as the closest structural analogue to Antmay's CLI, and it makes the opposite choice about state. Its durable layer is `.planning/` holding `PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md`, `config.json`, `phases/` and `research/`. `STATE.md` is a **single current-state file rewritten in place**, protected by an `O_EXCL` lockfile with stale-lock detection because "two agents read STATE.md, modify different fields, and the last writer overwrites the other's changes." Its stated design principle is "fresh context per agent… this eliminates context rot," with thin orchestrators spawning specialists. GSD keeps ADRs at project level (`docs/adr/`) and no per-change decision log at all: the per-phase artifacts carry the work, `STATE.md` carries what is true now, and the ADR log carries what binds. That three-way split — current-state file, phase artifacts, project ADRs — is close to what option D below proposes, arrived at independently and under an executor with the same concurrency constraints as Antmay's CLI.

### 1.9 Shape Up and rolling-wave planning

[Shape Up](https://basecamp.com/shapeup) shapes work into a **pitch** (Problem / Appetite / Solution / Rabbit Holes / No-Gos) at deliberately sub-wireframe fidelity — breadboards and fat marker sketches exist so that detail *cannot* be added — and then hands the team a project, not tasks. [Chapter 10](https://basecamp.com/shapeup/3.1-chapter-10) is the load-bearing text for Antmay's roadmap question:

> "Splitting the project into tasks up front is like putting the pitch through a paper shredder. Everybody just gets disconnected pieces." … "**Planning up front makes you blind to the reality along the way.**" … "The team naturally starts off with some imagined tasks—the ones they assume they're going to have to do just by thinking about the problem. Then, as they get their hands dirty, they discover all kinds of other things that we didn't know in advance." … "The way to really figure out what needs to be done is to start doing real work."

Chapter 11 adds "It's important at this early phase that they don't create a master plan of parts that should come together in the 11th hour," and Basecamp refuses a backlog entirely — unbet pitches are discarded, not queued. Progress is tracked by a **hill chart** (uphill = figuring out, downhill = executing), not by a plan document. Known limits: it does not fit maintenance work, it gives external stakeholders no roadmap, and quality depends entirely on shaping skill — over-shaping produces "a very detailed design spec [that] will likely become gospel."

The PM tradition's name for the same idea is **rolling wave planning**: "work to be accomplished in the near term is planned in detail, while work further in the future is planned at a higher level… a form of progressive elaboration." Three agent projects adopt it by name and state Antmay's failure mode 2.2 as their motivation. [rolling-wave-engineering](https://github.com/rijkvanzanten/rolling-wave-engineering) notes that agents which "scope the whole project up front… typically leave 10-30% of tasks incomplete," and defines a slice as "one bounded human review decision." [cyanluna.skills](https://github.com/cyanluna-git/cyanluna.skills) makes rolling wave the *default* against a legacy `--big-bang` mode: "Refining everything upfront → earlier implementations change assumptions, later tasks become stale. Refining just-in-time → scope and interfaces are grounded in real code," with later tasks kept as "title + high-level description only" until their turn. [agent-11](https://github.com/TheWayWithin/agent-11) records the rule as a project decision: "Detailed spec only for the current sprint; **the last task of each sprint writes the next sprint's spec**."

Pocock's fog of war is the same principle under a different name, with a user-reported failure that reads like the Leitspace roadmap: "I charted 27 tickets, and by the time I got to the thirteenth, the rest no longer made sense."

## 2. Decision-record literature

### 2.1 Nygard's ADR and the immutability claim

Michael Nygard's [*Documenting Architecture Decisions*](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) (2011) is the source of nearly every decision-record practice in use. Its rules: keep records "in the project repository under `doc/arch/adr-NNN.md`"; number them "sequentially and monotonically. Numbers will not be reused"; and — the sentence Antmay's design descends from — "If a decision is reversed, we will keep the old one around, but mark it as superseded." One record equals one decision; the *current* architecture is not any single file but the set of non-superseded records. The scope gate is narrow: "architecturally significant" decisions, "those that affect the structure, non-functional characteristics, dependencies, interfaces, or construction techniques."

Two things Nygard does not supply are exactly the two gaps in Antmay's field report. There is no project-level rollup or "current decisions" view — the reader reconstructs current state by scanning statuses — and there is no rule against editing a record generally; the immutability claim covers *reversal*, not editing. The frequently quoted "do not alter existing information" is not Nygard's; it comes from the community collection below.

### 2.2 MADR, adr-tools, and what tooling makes cheap

[MADR](https://adr.github.io/madr/) is the dominant modern template. Its v4 front matter carries `status: "{proposed | rejected | accepted | deprecated | … | superseded by ADR-0123}"` and — significantly — `date: {YYYY-MM-DD when the decision was last updated}`. MADR therefore *assumes the file is edited after creation*, a quiet departure from strict immutability, and it carries supersession as free text inside the status string rather than as a structured field. Its [changelog](https://github.com/adr/madr/blob/main/CHANGELOG.md) shows v4.0.0 removing direct hyperlinks from the status field, leaving only an identifier. Supersession is a weak, unenforced convention even in the leading template. The version arc (v2 optional metadata → v3 YAML front matter, merged Consequences → v4 "Confirmation", `minimal` and `bare` variants) trends toward *less* ceremony per record.

[npryce/adr-tools](https://github.com/npryce/adr-tools) shows the economics. `adr new -s 9` creates a superseding record *and* flips ADR 9's status in one command; `adr link` writes a typed cross-link into both files. Appending with a correct bidirectional link costs one command and is mechanically consistent. Editing in place also costs one command but is *silent* — nothing records that an edit happened, and nothing else updates. What no command makes cheap is "what is the current set of decisions?", which is still a manual scan of statuses. **Where supersession is not tool-enforced, it rots.** This is the single most transferable finding for Antmay: the append-only supersession model in Antmay's `decisions.md` is maintained by prose instruction, not by a command that writes both sides.

### 2.3 The explicit mutability dissent

[joelparkerhenderson/architecture-decision-record](https://github.com/joelparkerhenderson/architecture-decision-record), the de-facto ADR catalogue, states both positions in adjacent paragraphs:

> "Don't alter existing information in an ADR. Instead, amend the ADR by adding new information, or supersede the ADR by creating a new ADR."

> "In practice, mutability has worked better for our teams. We insert the new info the existing ADR, with a date stamp, and a note that the info arrived after the decision. This kind of approach leads to a 'living document.'"

That is the canonical statement of the trade-off, and it names a **middle path**: mutate the record, but append the mutation *inside* it with a date stamp and provenance. An append-only log inside a mutable file. It needs no cross-file consistency and cannot produce a dangling supersession link.

### 2.4 The gate problem and the volume ceiling

Olaf Zimmermann ([*ADR = Any Decision Record?*](https://ozimmer.ch/practices/2021/04/23/AnyDecisionRecords.html), [*Architectural Decisions — The Making Of*](https://ozimmer.ch/practices/2020/04/27/ArchitectureDecisionMaking.html)) gives seven significance criteria and insists "Not all decisions are worth capturing; triages are required." His volume bound is blunt: "Do not document everything; an AD log with more than 100 entries will probably put your readers (and you) to sleep." His compressed form, the [Y-statement](https://medium.com/olzzio/y-statements-10eb07b5a177) ("In the context of…, facing…, we decided for…, to achieve…, accepting that…"), exists because "the five sections each in Nygard's ADRs … can get rather long."

The empirical anchor is Buchgeher et al., *Using Architecture Decision Records in Open Source Projects*, IEEE Access 11 (2023) ([IEEE](https://ieeexplore.ieee.org/document/10155430/), [JKU](https://research.jku.at/en/publications/using-architecture-decision-records-in-open-source-projects-an-ms/)): across 921 repositories with at least one Markdown ADR, **roughly half contain only 1–5 ADRs** and fewer than ~2% exceed 25. The median ADR adoption is a pilot that stopped. Any design assuming a long, well-tended chain of superseding records is designing for the <2% case. Note the contrast with Leitspace's CB1, which produced 31 decision records for *one thread* — Antmay's decision volume is one to two orders of magnitude above what ADR practice sustains, which is why promoting all of it to a project-level ADR log would fail and why a gate is unavoidable.

Qualitative critique converges on one defect: undocumented reversal. Stale records are described as "actively misleading to anyone who finds it and reads it at face value" and as "a graveyard of markdown files everyone has quietly agreed to ignore" ([Java Code Geeks, 2026](https://www.javacodegeeks.com/2026/05/the-reason-most-architecture-decision-records-get-written-and-never-read-is-architectural-not-cultural.html)). The counterweight: Thoughtworks has kept [lightweight ADRs in **Adopt**](https://www.thoughtworks.com/en-us/radar/techniques/lightweight-architecture-decision-records) since 2017, recommending "storing these details in source control, instead of a wiki or website, as then they can provide a record that remains in sync with the code itself."

### 2.5 RFC and PEP processes: the strongest evidence for "historical, not living"

Three mature processes freeze the record and name a *separate* current-state artifact.

- **IETF.** "[RFCs do not change after publication](https://www.rfc-editor.org/errata-definitions/)." Corrections accumulate in a typed side channel (errata: Reported / Verified / Rejected / **Held for Document Update**); substantive change requires a new RFC with `Obsoletes:` / `Updates:` headers. Three tiers: immutable text, attached errata, superseding document.
- **Python.** [PEP 1](https://peps.python.org/pep-0001/): "In general, PEPs are no longer substantially modified after they have reached the Accepted, Final, Rejected or Superseded state," at which point a PEP becomes "a historical document rather than a living specification." Supersession is bidirectional and structural (`Superseded-By` / `Replaces`).
- **Rust.** [rust-lang/rfcs](https://github.com/rust-lang/rfcs): "once accepted, RFCs should not be substantially changed… More substantial changes should be new RFCs, with a note added to the original RFC," and candidly, "we cannot expect every merged RFC to actually reflect what the end result will be." Rust made the split *policy*: [RFC 1636](https://rust-lang.github.io/rfcs/1636-document_all_features.html) requires documentation for all new features precisely because features were "documented only in the RFCs which propose them," many of which "seem to be outdated and no longer accurate."

**Every tradition that freezes its records also mandates a separately maintained current-state document.** ADR practice is the one tradition that omits the projection, and it is the one tradition with a documented graveyard problem. Antmay currently omits it too.

### 2.6 Design docs and six-pagers

Malte Ubl's [*Design Docs at Google*](https://www.industrialempathy.com/posts/design-docs-at-google/) draws the line at shipping: "If the designed system hasn't shipped yet, then definitely update the doc." After that, "we humans are bad at updating documents, and for other practical reasons changes are often isolated into new documents," with links from the original to its amendments "immensely helpful for the poor future maintenance programmer." A stale design doc still has residual value — it "often present[s] the most accessible entry point to learn about the thinking that guided the creation of the system" — because its authority is over *the decision at the moment it was made*, never over present behaviour. Amazon's [PR-FAQ](https://workingbackwards.com/concepts/working-backwards-pr-faq-process/) behaves the same way: the FAQ accretes in place before launch and is not maintained afterwards.

### 2.7 arc42 on project-level versus per-change

[arc42 §9](https://docs.arc42.org/section-9/) gives the clearest published placement rule:

> "Please use your judgement to decide whether an architectural decision should be documented here in this central section or whether you better document it locally (e.g. within the white box template of one building block). **Avoid redundant texts.** Refer to section 4, where you captured the most important decisions of your architecture already."

arc42's structural answer is three-way: cross-cutting *constraints* in §2, headline strategy in §4, significant non-redundant decisions in §9, and locally-scoped decisions pushed down to the component they bind. Translated to threads: a thread's own decisions belong to the thread; anything that binds *future* threads must be promoted to a project-level, in-place-maintained artifact, because a frozen per-change record cannot carry project-level authority.

## 3. Living documentation and docs-as-code

### 3.1 Martraire: three bands by knowledge lifetime

Cyrille Martraire's *Living Documentation* ([O'Reilly](https://www.oreilly.com/library/view/living-documentation-continuous/9780134689418/), [pattern-language PDF](https://ptgmedia.pearsoncmg.com/imprint_downloads/informit/bookreg/9780134689326/livingdocumentation_pattern_diagrams.pdf)) is usually cited for "generate docs from the system," but the load-bearing part here is his three-way split by *lifetime*:

> "For all the knowledge that is **ephemeral**, nothing beats conversations and working collectively… At the other hand of the spectrum, the knowledge that is **permanent** — in other words, stable and useful in the long run — can be recorded through traditional forms of documentation… In between these two cases, all the knowledge that is **long-lived but evolves regularly** is best considered in the system itself."

Living documentation is the treatment for the *middle* band only. Ephemeral knowledge gets a conversation and **no file at all**. He names the promotion pipeline explicitly — **Idea Sedimentation**, **Throw-Away Documentation**, **On-Demand Documentation**, **Biodegradable Documentation**: "some ideas deserve to be recorded for the longer run, through a process of idea sedimentation. The ideas that deserve to last for a while can then evolve into on-demand documentation, **can be thrown away later**, or can be turned into some form of living document." That is *precisely* the change-scoped-note → promoted-into-living-doc → discarded shape. Where duplication is unavoidable, his answer is a **reconciliation mechanism** — an automated agreement check — not a convention. Named anti-patterns: "Abusing Living Documentation," "Procrastination by Living Documentation," "Documentation Bankruptcy."

### 3.2 Diátaxis, arc42, C4

[Diátaxis](https://diataxis.fr/) puts decision rationale in **explanation** ("history, choices, alternatives, possibilities, why: reasons and justifications") and insists **reference** be "austere," "wholly authoritative," excluding "explanation, instruction, discussion, opine" — so mixing rationale into a spec is a named defect. It has *no* category for change-event documents; history lives inside explanation, not a fifth mode.

Simon Brown states the C4 split cleanly: diagrams show the *outcomes* of decisions, not the decision-making process, so decisions are documented separately as ADRs ([Visualising ADRs](https://dev.to/simonbrown/visualising-adrs-3klm)). He also names the archive failure mode — "Do team members ever look at that folder of ADRs though?" — and his fix is to *render the supersession graph*.

### 3.3 Living specs, delta specs, and the SbE retrospective

The [WHATWG HTML Living Standard FAQ](https://github.com/whatwg/html/blob/main/FAQ.md) is the strongest primary argument against snapshots: "The problem with following a snapshot is that you end up following something that is known to be wrong… much like the waterfall model is not a good fit for software development, it is also not a good way of developing standards."

The delta-merged-into-living-spec pattern has three notable instances: the [OpenAPI Overlay Specification](https://spec.openapis.org/overlay/v1.1.0.html) (ordered update/remove actions applied to a target description); Rust RFCs (delta proposals, historical archive, separate reference); and [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md), where `specs/` "describe how your system currently behaves" and `changes/*/specs/` carry `## ADDED` / `## MODIFIED` / `## REMOVED` sections that are applied to the living spec at archive time, with the whole change folder (proposal included) moving to `changes/archive/<date>-<name>/`. OpenSpec's stated advantage of deltas over rewrites is merge behaviour: "two changes can touch the same spec file without conflicting, as long as they modify different requirements."

The cautionary data point is Gojko Adzic's [ten-year retrospective on Specification by Example](https://gojko.net/2020/03/17/sbe-10-years.html). Living documentation was "the holy grail" that "didn't really work out as expected over the last 10 years": only ~12% of teams store specs in version control, 57% keep them in task trackers, so the single source of truth fragmented; about a third abandoned automation and lost the self-checking property. His named failure mode is **formula over substance** — "people latch onto G/W/T because it gives comfort in a formula… whereas in reality they are just a lightweight structure to stimulate good thinking." A living-spec layer that is not mechanically checked degrades to a second stale copy.

## 4. Requirements engineering

### 4.1 EARS: a syntax, not a completeness check

EARS ([Mavin et al., RE'09](https://ccy05327.github.io/SDD/08-PDF/Easy%20Approach%20to%20Requirements%20Syntax%20(EARS).pdf), [alistairmavin.com/ears](https://alistairmavin.com/ears/)) defines five patterns — Ubiquitous, State-driven (`While`), Event-driven (`When`), Optional feature (`Where`), Unwanted behaviour (`If…Then`) — plus composition. In the CS-E 50 case study, complexity, omission, duplication, "inappropriate implementation" and untestability were eliminated; requirement count rose 36→47 as compound requirements split, and average words per requirement fell 36.9→25.6.

The paper's own disclaimers matter more for Antmay than the benefits. It is "most suitable to the definition of high-level stakeholder requirements"; "the claim that omissions have been eliminated needs to be treated with caution… there is no evidence that other missing requirements have been captured"; and **conflicting requirements and missing traceability links are explicitly out of scope**. EARS constrains the *shape* of a requirement, never its provenance. Kiro's adoption of EARS therefore buys phrasing discipline and buys nothing at all against invented requirements — the exact failure Antmay's `reconcile-spec` exists to catch.

### 4.2 Traceability, gold plating, and the "invented design" problem

This is the most directly applicable body of literature to failure mode 2.4 and to the spec/reconcile loop.

Gotel & Finkelstein's [1994 analysis](https://discovery.ucl.ac.uk/749/) split **pre-RS** traceability (requirement → originating stakeholder need) from **post-RS** (requirement → design → test) and found "the majority of problems attributed to poor requirements traceability are due to inadequate **pre-RS** traceability." Pre-RS is the direction tools do not support and the direction that catches invented content.

Boehm's top-ten risk list ranks *#3 developing the wrong functions*, *#5 gold plating*, *#6 continuing stream of requirements changes* ([summary](https://people.cs.pitt.edu/~chang/153/c03manage/risk4.htm)). The definitional boundary is worth adopting verbatim: **scope creep is unapproved change led by stakeholders; gold plating is unapproved addition led by the producer** ([PM Academy](https://projectmanagementacademy.net/resources/blog/gold-plating-vs-scope-creep/)). An agent inventing design is structurally gold plating.

The classical detection mechanism is exactly what `reconcile-spec` does by hand: an **orphan requirement** — one with no backward trace to a stakeholder need — is the gold-plating signal, and the standard remedy is "inserting requirements for 'derived' functionality back into the original requirements to 'test' whether the capability is actually needed," with the corollary that "if the capability is important enough to be in the system, it needs to be documented as a requirement." Note the corollary: the literature's answer to a derived requirement is **promote it to a real requirement**, not delete it. Antmay's reconcile agent currently only deletes. That is a one-sided implementation of a two-sided rule, and it is the mechanical cause of field-report finding (1).

The costs are documented and non-trivial. Cleland-Huang et al., [*Grand Challenges of Traceability*](https://arxiv.org/pdf/1710.03129): "the cost, effort, and discipline needed to create and maintain trace links in a rapidly evolving software system can be extremely high, and benefits often go unrealized in practice"; practitioners "avoid the overhead unless required by regulations" ([Why don't we trace?](https://link.springer.com/article/10.1007/s00766-023-00408-9)). Traceability *decays* as linked artifacts change. Against that: complete traceability made maintenance tasks ~24% faster via impact assessment, and value-based selective tracing achieved most of the benefit at ~35% of full-tracing effort. **Selective tracing is the supported position** — trace the decisions that bind, not every sentence.

### 4.3 Stories are tokens, not artifacts

Ron Jeffries' [card / conversation / confirmation](https://ronjeffries.com/xprog/articles/expcardconversationconfirmation/): "The card is a **token** representing the requirement… The requirement itself is communicated from customer to programmers through conversation." The durable artifact is the acceptance test. Jeff Patton: "Stories aren't a written form of requirements… **Stop writing stories and start telling stories.**"

The counterweight is the baseline. [ISO/IEC/IEEE 29148](https://www.iso.org/standard/45171.html) defines one as "a specification or product that has been formally reviewed and agreed upon… and that can be changed only through formal change control procedures" — authority from a ceremony at a point in time, with supersession explicit and dated and the prior baseline retained. Agile does not reject baselining so much as redefine it as "agreement of requirements at a snapshot in time." Requirements churn of 1–3%+ per month (Capers Jones; [Volere](https://www.volere.org/wp-content/uploads/2018/12/Requirements2012.pdf)) correlates with defect density, so the literature supports neither a frozen baseline nor zero up-front specification.

## 5. Agent memory and context-loss handling

### 5.1 Memory Bank (Cline / Roo Code)

The [Cline Memory Bank](https://docs.cline.bot/prompting/cline-memory-bank) is the most-copied durable-state pattern in the agent ecosystem: six files under `memory-bank/` in an explicit hierarchy rooted at `projectbrief.md` — `projectbrief.md` ("core requirements and goals"), `productContext.md`, `techContext.md`, `systemPatterns.md`, `activeContext.md` ("current focus, recent changes, next steps — updates most frequently"), `progress.md` ("what works, what's left, known issues").

The design decision to note is that **historical/current separation is by file, not by section or status**. Three files are near-immutable, two carry volatile state, and the split is visible in the filename. Updates fire on "discovering new project patterns," "after implementing significant changes," and on the explicit user command "update memory bank" (Roo's `UMB`), which forces a review of *all* files. `activeContext.md` is updated after each session.

Documented problems are external to the docs and mostly about cost: [cline#2110](https://github.com/cline/cline/issues/2110) and [discussion #2979](https://github.com/cline/cline/discussions/2979) report ~300K tokens after five iterations with Memory Bank enabled. Cline's own rebuttal concedes it — "Memory Bank isn't about minimizing tokens… Yes, reading memory files costs tokens" ([@cline](https://x.com/cline/status/1900320075829436550)) — and scopes the pattern: "For small, quick tasks (under a day), Memory Bank might be overkill" ([@cline](https://x.com/cline/status/1901408207786193182)). Roo Code separately ships a [Context Poisoning](https://docs.roocode.com/advanced-usage/context-poisoning) page naming stale repo artifacts as a source — "Outdated, incorrect, or ambiguous comments in the codebase can be misinterpreted" — with the severe conclusion that corrective prompting "offers no lasting remedy"; you must "Hard Reset the Session." **A poisoned agent cannot be talked out of it**, which is the strongest available argument for making Antmay's historical/authoritative distinction mechanical rather than advisory.

### 5.2 Anthropic's published guidance

[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) states the constraint ("as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"), the compaction mechanism, and structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window… Like Claude Code creating a to-do list, or your custom agent maintaining a `NOTES.md` file." The governing principle is "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome."

[Effective harnesses for long-running agents](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents) resolves the incremental-vs-checkpoint question and answers it against continuous writing. The prescribed shape is **write at session boundaries, read at session start**, with git as an independent second record: an initializer creates `claude-progress.txt` "that keeps a log of what agents have done"; the coding agent is told to "read the git logs and progress files to get up to speed" at open and to "end the session by writing a git commit and progress update" at close. Progress-file content is prescribed to include **failed approaches and why they didn't work**, not only successes. The named failure mode is premature victory declaration.

[Claude Code's memory docs](https://code.claude.com/docs/en/memory) are the most operationally detailed staleness guidance any vendor publishes, and three rules transfer directly:

- **Size discipline:** "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."
- **Contradiction is the failure:** "if two rules contradict each other, Claude may pick one arbitrarily. Review your CLAUDE.md files… periodically to remove outdated or conflicting instructions."
- **Date the record:** memory files carry a `modified` ISO-8601 field, because "the timestamp shows how current the fact is, both to you and to Claude when it reads the memory back."

Auto memory is built as an **index plus topic files** (`MEMORY.md`, only the first 200 lines loaded), and the harness actively fights bloat: as the index approaches its limit Claude Code "reminds Claude to shorten it: keep one line per entry, move detail into topic files, and merge or drop stale entries." It also **excludes derivable facts** — "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes" — keeping "pitfalls, rationale, and conventions that differ from tool defaults."

Two of those are direct challenges to Antmay's shape: the durable layer must be an index over topic files rather than one growing document, and it must exclude anything derivable from code. A 498-line project `AGENTS.md` (Leitspace) is more than twice the published adherence ceiling.

### 5.3 Cursor rules, and rules that are silently ignored

[Cursor rules](https://cursor.com/docs/context/rules) use `.cursor/rules/*.mdc` with four activation modes (Always, Auto-Attached via `globs`, Agent-Requested via `description`, Manual). Published best practice: "Keep rules under 500 lines," "split large rules into multiple, composable rules," and — the anti-staleness lever — **reference files rather than copy their content**. Reported failures: rules silently skipped on front-matter syntax errors, undefined behaviour when legacy `.cursorrules` coexists with `.cursor/rules/`, `alwaysApply: true` rules dropped entirely in some builds ([forum thread](https://forum.cursor.com/t/alwaysapply-true-rules-are-being-completely-ignored-now/158551)), and attention dilution. The line worth carrying: "Outdated or contradictory rules confuse the model just as much as they'd confuse a new developer." Cursor's **Memories** are one-sentence facts auto-proposed by a sidecar model and requiring user approval, on the reasoning that "an unreviewed memory is an invisible system prompt you never agreed to."

### 5.4 The Ralph loop: durable state is rewritten, not appended

Geoffrey Huntley's [Ralph technique](https://ghuntley.com/ralph/) is `while :; do cat PROMPT.md | claude-code ; done`. Because every iteration is a fresh context, the filesystem *is* the memory, and the file set is revealing:

- `specs/` — requirements and standards, the living contract;
- `fix_plan.md` (a.k.a. `IMPLEMENTATION_PLAN.md`) — a prioritized bullet list of remaining work, **rewritten after each loop**; the single mutable state file;
- `AGENTS.md` — build/run learnings, updated when a discovery improves efficiency;
- git commits as the independent history.

There is no decision log. In the most aggressive long-running-agent design in the ecosystem, durable state is a **current-state file edited in place**, and the append-only history is delegated entirely to git. Documented failure modes in Huntley's own words: search non-determinism (Ralph concludes something is unimplemented when it is not), placeholder bias, context exhaustion (~170K usable tokens, wasted by re-reading specs every loop — mitigated by pushing spec reading into subagents), codebase corruption recovered by `git reset`, and a hard scope limit: "There's no way in heck would I use Ralph in an existing code base."

Matt Pocock's context budget is informal but consistent: pushing past ~100K tokens produces "dumber decisions, worse code, worse instruction-following" ([@mattpocockuk](https://x.com/mattpocockuk/status/2034572011175907474)); the circulating heuristic is a ~125–150K working ceiling regardless of the advertised window. Chroma's [Context Rot](https://www.trychroma.com/research/context-rot) study is the quantitative backstop: across 18 frontier models, reliability degrades non-uniformly and materially well before the stated limit.

### 5.5 Where decisions get written during a live session

This bears directly on the rejection of option A. Pocock's `grill-with-docs` ([aihero.dev](https://www.aihero.dev/skills-grill-with-docs)) does write durably *during* the interrogation — but the write unit is atomic and tiny:

> "A term gets resolved and it lands in `CONTEXT.md` the moment it resolves, not batched at the end. A decision passes three gates and it lands as an ADR."

and the success signal is explicitly that "`CONTEXT.md` changes *during* the session, term by term, rather than appearing in one lump at the end." The cost of everything else is admitted: decisions that fail the three gates exist "in the conversation, and nowhere else."

The opposite timing also exists in the wild. Isaac Flath's [SpecFlow](https://elite-ai-assisted-coding.dev/p/the-specflow-process-for-using-ai) generates `decisions.md` **after** implementation by having the model analyse the full conversation transcript against a "Decision Spec" template, extracting three categories: "the planned decisions from the spec, the implicit decisions the AI made, the ad-hoc decisions the human made." The resulting file becomes "a centerpiece of a pull request."

So the ecosystem has both timings, and they carry different costs: term-by-term writing works because each write is one line into a small store; whole-document maintenance during a live session is not attempted anywhere I found. Post-hoc extraction captures more (including *implicit* agent decisions) but depends on the transcript still existing — which is exactly what Antmay's `decisions.md` was designed not to depend on.

## 6. Failure-mode reports from practice

### 6.1 Ceremony cost, measured

Colin Eberhardt (Scott Logic), [*Putting Spec Kit Through Its Paces: Radical Idea or Reinvented Waterfall?*](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html), is the strongest single measurement. One feature through the full Spec Kit chain: **2,577 lines of markdown produced 689 lines of code**, at 33m30s of agent time plus **3.5 hours of his review**, versus 8 minutes of agent time and 15 minutes of review for ordinary iterative prompting. Verdict: "I am a lot more productive without SDD, around ten times faster." He calls the intermediate artifacts "an obvious and valueless transformation of the spec." The ceremony did not buy correctness — the implementation shipped with a plain bug.

François Zaninotto (Marmelab), [*Spec-Driven Development: The Waterfall Strikes Back*](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html): displaying a date produced 8 files and 1,300 lines of text. Named modes: reviewers "hunting for basic mistakes hidden in overly verbose, expert-sounding prose"; the **double code review** (the technical spec contains code, so you review it twice); and "**Diminishing Returns**: SDD shines when starting a new project from scratch, but as the application grows, the specs miss the point more often and slow development… For large existing codebases, SDD is mostly unusable."

[Thoughtworks Technology Radar Vol. 33](https://www.thoughtworks.com/radar/techniques/spec-driven-development) places SDD in **Assess**, warning that tools "generate lengthy spec files that are hard to review," that "it's sometimes unclear who their intended user is," and that "we may be relearning a bitter lesson — that handcrafting detailed rules for AI ultimately doesn't scale." Hidde de Smet's [hidden costs](https://hiddedesmet.com/the-hidden-costs-of-spec-driven-development) enumerates a **context maintenance tax** whose symptom is teams holding "three 'almost current' files" and asking "which file is the source of truth?" — a precise description of Leitspace failure mode 2.1.

### 6.2 Drift, staleness, and the plan that outlives its assumptions

The community diagnosis on [HN](https://news.ycombinator.com/item?id=45935763) is mechanical: "as soon as you want quick changes you have to abandon the spec. Iterating the spec and the code quickly is impossible… SDD will fail for the same reason Waterfall has failed. The constant increasing of complexity … required to keep code and spec consistent." And on the Kiro/Spec-Kit/Tessl [thread](https://news.ycombinator.com/item?id=45610996): "I was always left wondering 'when does it merge all this specs into a single ground truth'. I never got there and it felt like a huge missing step."

[*The Stale /Plan Problem in Coding Agents*](https://medium.com/@arijitdutta23/the-stale-plan-problem-in-coding-agents-cde2c741f8ab) names the resume hazard exactly: "when an agent adapts code but the plan file quietly stays behind, that stale plan looks harmless until it becomes the source of truth again when you resume the agent session at a later stage." Mitigations named: re-read file contents before each execution step rather than caching from planning, and explicit re-planning checkpoints.

Spec Kit's own `/speckit.analyze` — a dedicated cross-artifact consistency command detecting "Duplication," "Coverage Gaps," "Inconsistency," and "terminology drift (same concept named differently across files)" — is evidence that the pipeline drifts by default. Antmay's `reconcile-*` family is the same admission in a different shape.

### 6.3 Invented requirements, observed

Eberhardt caught Spec Kit inventing the rationale "Poor mobile UX renders the app unusable in its primary context" — fabricated reasoning about glove-wearing users that appeared nowhere in his input. Zaninotto: "Specs contain many repetitions, imaginary corner cases, and overkill refinements." On Kiro, practitioners report a small bug fix expanding into "4 user stories with 16 acceptance criteria" and task lists of "12+ tasks with 4+ sub-tasks each" ([HN](https://news.ycombinator.com/item?id=45610996)). The vendor-neutral mechanism is well stated: omitting a spec section "creates a gap the agent fills with hallucinated assumptions," because agents "do not fill gaps with engineering judgment but generate statistically plausible completions." The countermeasure that recurs is an explicit **"Not Included" / out-of-scope section** as a hallucination boundary.

This is the clearest external validation of Antmay's first field-report finding, and of *why* the current `spec` → `reconcile-spec` pair exists. It also shows the pair is fighting a structural cause: a spec agent handed a lossy input and asked for a complete document *must* invent, because completeness is the deliverable.

### 6.4 Stale artifacts poisoning future reads

The mattpocock quote is real and sits in [`docs/engineering/research.md`](https://github.com/mattpocock/skills/blob/main/docs/engineering/research.md): a research artifact "otherwise becomes cruft of work and can poison future repo reads," because "a research file records what was true on the day it was written, so a stale one is worse than none." Independent corroboration comes from Roo's Context Poisoning page (§5.1) and from ["Context Rot in AI-Assisted Software Development"](https://arxiv.org/pdf/2606.09090), which defines context rot as persistent `CLAUDE.md` / `AGENTS.md` / `.cursorrules` files going stale and reports "on at least two occasions, outdated context documents caused agents to generate code that conflicted with recent refactors," concluding "specification staleness was a primary failure mode."

One mechanical countermeasure found in the wild is worth naming because it inverts Antmay's approach: [SPEC-AGENTS.md](https://github.com/yibie/SPEC-AGENTS.md) keeps `.spec-agents/state/STATUS.md` listing **only active specs**, their blockers, and the next permitted action, with finished specs removed from it. Authority is an **allow-list of what is current**, rather than a marker on what is historical. Every artifact not on the list is, by construction, not authoritative.

## 7. Synthesis for Antmay

### 7.1 Where does the source of truth for a change's design live, and what shape dominates?

**A per-change specification document dominates, overwhelmingly.** Kiro (`requirements.md` + `design.md`), Spec Kit (`spec.md`), OpenSpec (`changes/<id>/` deltas), BMAD (`SPEC.md`), superpowers (a design doc, for architectural work only), agent-os v3 (`plan.md` + `shape.md`), Tessl (`*.spec.md`), spec-workflow-mcp and cc-sdd — all put a change's design in one document written before implementation.

The second-most common shape is a **plan or task file that becomes the operative truth during implementation**: `tasks.md` in Kiro and Spec Kit, `tasks.json` in Taskmaster, `fix_plan.md` in Ralph, `stories.yaml` plus story files in BMAD, the PR description for Copilot's coding agent. This is where truth *actually* lives while code is written, which is why plan staleness is the most-reported failure in §6.2.

A **living spec per capability** is rare and has essentially one serious instance: OpenSpec's `openspec/specs/<capability>/spec.md`, fed by merged deltas. Tessl aspires to it and has stepped back from it.

Three combinations are common:

1. **Per-change spec + a project-level durable layer.** By far the most common, and effectively universal in 2025–2026. Spec Kit pairs `specs/` with `constitution.md`; Kiro pairs specs with steering files; agent-os v3 pairs a spec folder with `standards/` and `product/`; BMAD pairs a spec with a verified `AGENTS.md` block maintained by `bmad-project-context`; Ralph pairs `specs/` with `AGENTS.md`; Pocock pairs nothing-per-change with `CONTEXT.md` + ADRs; MUSUBI pairs specs with `steering/memories/`. **Every serious toolkit surveyed has a project-level durable layer. Antmay is the outlier in having none**, which is field-report finding (5) confirmed from the outside.
2. **Per-change delta merged into a living spec.** OpenSpec, and spec-workflow-mcp in weaker form.
3. **No per-change durable artifact at all.** Pocock's skills; superpowers for its spike and bounded tiers (two of its three ceremony levels produce no file); agent-os v3's smallest path; every plan mode.

What is **rare** is a per-change decision *log* as the origin of the design. What is essentially absent is a per-change decision log kept **alongside** a spec and a plan as a co-equal artifact — which is Antmay's arrangement.

### 7.2 Is anyone else keeping a per-change append-only decision log with supersession?

**Yes: BMAD, and it independently reached Antmay's design for a reason worth taking seriously.** `.memlog.md` lives in each spec folder and is written through `_bmad/scripts/memlog.py`, whose invariants are append-only chronology ("there is no edit or delete subcommand by design; history is never rewritten"), write-only/blind writes ("the caller never re-reads the file mid-session… the one time the file is read is on resume"), and **no lifecycle status field**, because "whether the work is done, blocked, or paused is itself a fact that happened." Supersession is by appending: "a later entry supersedes an earlier one on the same point while the history stays intact."

Its relationship to the spec is Antmay's, stated more strongly: `.memlog.md` is canonical, `SPEC.md` and its companions are **re-derived on each run**, and a hand-edit to `SPEC.md` is unsupported and overwritten. BMAD's stated rationale is the best argument on the record for Antmay's current shape:

> "Deriving the contract from a living log instead of editing the contract in place is what lets the steps around the spec (PRD, UX, architecture, epics) run in any order and feed the same spec without merge drift: the log only accumulates, the artifact is re-rendered."

**But four differences explain why BMAD's derivation does not produce Antmay's infer-then-strip loop, and they are the whole finding.**

1. **BMAD's log is not lossy.** Entries are typed from an open vocabulary the host skill names — `decision | constraint | capability | assumption | question | direction | note | event` — and capabilities carry stable `CAP-N` identifiers. The log therefore contains the *material* of the spec, not only the choices made about it. Antmay's `decisions.md` records decisions and nothing else, so a spec agent asked for a complete document must supply the rest from inference. That is not a prompt problem; it is an information-theoretic one, and it is the mechanical cause of field-report finding (1).
2. **Entries are one line with the reason folded in**, not Context/Decision/Rationale blocks, so the log stays cheap to write and cheap to read end-to-end.
3. **There are no record IDs and no supersession pointers.** Last-write-wins is resolved by the deriving agent reading the whole log in order. Nothing can dangle.
4. **The log is not read during the session**, only on resume and at derivation — so it never competes for context with the work.

Two nearer misses exist. OpenSpec has a Decisions *section* inside `design.md`, whose known weakness is that archiving hides it from future proposals — which is why a community schema pulls ADRs out of the change folder entirely. And the informal `decision-log.md`-in-the-feature-folder practice circulates in blog posts without tooling behind it. Everything else — Tessl, Traycer, Factory, Devin, Amp, Aider, SpecStory, Copilot, Amazon Q, AGENTS.md, all plan modes, all orchestrators, spec-workflow-mcp, cc-sdd, superpowers, Taskmaster, Kiro, Spec Kit — has none.

**Why is it so rare?** Three converging reasons the literature supports. First, the ADR tradition that invented supersession scoped it to *project-level, architecturally significant* decisions and bounded the volume ("an AD log with more than 100 entries will probably put your readers to sleep"; median real adoption 1–5 records). Leitspace's CB1 produced 31 records for one thread — an order of magnitude past the format's design point. Second, supersession without tool enforcement rots: `adr new -s N` writes both sides in one command, and hand-maintained links are the most-reported ADR defect. BMAD's answer is to make the log a *script*, not a discipline. Third, most toolkits assume the conversation is available, so they never pay for a durable log; the ones that admit the cost (Pocock: "the most substantive open complaint about the skill") still decline to pay it. And agent-os is the cautionary case of a project that *did* pay and then removed the artifact as "rarely used."

Antmay's field report calls the log "the best artifact in the project," and that judgement is well supported — it is the one thing Antmay has that Pocock's users explicitly miss and that superpowers has no answer for. The problem is not the log. The problem is that a chronological, supersession-carrying, decisions-only log is being used as the **sole input to a regeneration step**, which requires the generator to resolve every supersession *and* invent everything the log does not carry. That is exactly the work the spec agent and the reconcile agent each do badly, from opposite directions.

### 7.3 In-place versus append-only

**(a) For per-change design records the evidence favours in-place, with two conditions.** The joelparkerhenderson catalogue is the only source that states both positions from experience, and its report is "In practice, mutability has worked better for our teams. We insert the new info the existing ADR, with a date stamp, and a note that the info arrived after the decision." Malte Ubl's Google guidance is "If the designed system hasn't shipped yet, then definitely update the doc" — a per-change record is *pre-ship by definition*, so it falls squarely inside the update rule. Ralph rewrites `fix_plan.md` every iteration. Cline rewrites `activeContext.md` every session. Cursor and Claude Code both rewrite memory in place and both fight growth by merging and dropping entries. The two conditions are that (i) the edit is date-stamped or otherwise attributed, and (ii) an independent history exists — which, for anything in a git repository, it does. Git is a Merkle-DAG append-only journal; a rewritten `decisions.md` under version control has not lost its history, it has moved it to where nobody has to read it to get the current answer.

**(b) For project-level decision records the evidence favours append-only with status.** IETF ("RFCs do not change after publication"), PEP 1 ("no longer substantially modified after… Accepted, Final, Rejected or Superseded"), Rust ("once accepted, RFCs should not be substantially changed"), Nygard ("keep the old one around, but mark it as superseded"), arc42 (superseded ADRs retained with references to their replacements). The reason the asymmetry holds is scope: a project-level record binds work that has not been conceived yet, so a future reader must be able to ask "why is this so?" and get the reasoning *as it stood*, including the reasoning that was later abandoned. A per-change record is read by, at most, the next three steps of the same change.

The invariant across every tradition that freezes records is that **freezing is only safe when a separately maintained current-state document exists**. Rust made that obligation policy (RFC 1636). ADR practice did not, and produced the graveyard.

### 7.4 What mechanisms actually work for historical versus authoritative?

Ranked by the evidence, strongest first:

1. **Merging the delta into a living document and archiving the source.** OpenSpec's archive step is the only mechanism found that makes the question unaskable: after archiving, the current answer exists in exactly one place, and the change folder's continued existence cannot mislead because nothing points at it. Costs: a merge step that must be correct, and delta grammar (`ADDED` / `MODIFIED` / `REMOVED`) that constrains how requirements may be phrased.
2. **An allow-list of what is currently authoritative.** SPEC-AGENTS.md's `STATUS.md` lists only active specs; finished ones are removed. Claude Code's `MEMORY.md` index performs the same function for memory. An allow-list degrades safely: forgetting to remove an entry leaves one stale pointer, whereas forgetting to mark an artifact historical leaves an unbounded number of authoritative-looking files. Antmay already has the machinery for this — a project-level index that names the current durable documents would make every unlisted thread artifact non-authoritative by construction.
3. **A mandatory read order stated where the agent will actually read it.** Pocock's setup skill writes an instruction telling every downstream skill to read `CONTEXT.md` and the relevant ADRs before exploring, and to flag ADR conflicts explicitly. Kiro's steering files are loaded into every interaction by default. This is cheap and it works, but it is context, not enforcement — Claude Code's docs are explicit that memory files are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead."
4. **Dating every record.** Claude Code's `modified` frontmatter exists because "the timestamp shows how current the fact is." Cheap, universal, and partial: it lets a reader discount a record, it does not stop one from being read.
5. **Archive folders.** They work only when archiving is not optional. Leitspace never archived a single thread in thirteen days; Spec Kit's Flow-Forward model documents the cost as "duplication… related decisions can be spread across multiple feature directories." An archive path is a good marker and a bad policy when its application is discretionary.
6. **Status fields and banners.** The weakest. Nygard-style statuses have been in use for fifteen years and produced "supersession links nobody updated." Simon Brown's own question about ADR folders — "Do team members ever look at that folder of ADRs though?" — is about records that carry correct statuses.
7. **Explicit staleness tagging of a finding or record.** Traycer is the only tool surveyed that tags a review finding **Outdated** — "may have been relevant at an earlier stage but are no longer applicable given subsequent changes." Narrow, but it is the only mechanism found that detects staleness *after the fact* rather than avoiding it, and it is a natural fit for Antmay's `.pending-reviews/` bundles.
8. **Deletion.** Endorsed by Pocock's users ("ADRs yes. Everything else archive or delete after done") and effective, but it forfeits the one thing the Antmay field report singles out as working.

The pattern across 1–3 is that **the mechanisms that work move authority to a small, enumerable, current-state surface**; the mechanisms that fail annotate a growing historical surface and hope readers respect the annotation.

### 7.5 Multi-phase decomposition without stale downstream plans

The state of the art is unambiguous and Antmay's roadmap contradicts it.

Shape Up states the principle first and best (§1.9): planning up front "makes you blind to the reality along the way," and the imagined-versus-discovered distinction is precisely the Leitspace CB3 story. A roadmap that writes seven full child briefs on day one is guaranteed to be wrong by day two, and the fix is not a better brief.

The agent-specific instances agree:

- **Pocock's fog of war**: the planner refuses to chart what it cannot see; later work stays a coarse "Not yet specified" note and becomes a ticket only when the frontier reaches it.
- **Spec Kit's spec-of-specs**: a deliberately shallow roadmap that "names and orders the sub-features but does **not** design them," with immutable entry IDs, a scope boundary and a status per row, maintained **in place** ("Roadmap first, then reconcile") rather than appended to.
- **BMAD** carries a "Learnings from Previous Stories" section into each story, and runs `bmad-retrospective` at epic close to catch "the architecture that drifted" and reconcile spec against built code.
- **Rolling wave planning** is the classical name, and three agent projects adopt it explicitly, each naming Antmay's failure mode 2.2 as the motivation. `cyanluna.skills` makes it the default over a legacy `--big-bang` mode: "Refining everything upfront → earlier implementations change assumptions, later tasks become stale. Refining just-in-time → scope and interfaces are grounded in real code," keeping later entries as "title + high-level description only" until their turn. `agent-11` states the rule most usefully for a Roadmap recipe: "**the last task of each sprint writes the next sprint's spec**." `rolling-wave-engineering` reports that agents scoping the whole project up front "typically leave 10-30% of tasks incomplete."
- **OpenSpec** replaces the multi-phase plan outright with many small changes carrying `dependsOn` / `provides` / `requires` metadata, because "parallel work can accidentally reintroduce assumptions already removed by another change."

Every one of these keeps a **single, coarse, mutable index** and defers detail to the moment of execution. None of them writes detailed downstream briefs up front, and none of them uses an append-only feedback channel against a frozen plan. Antmay's `roadmap-feedback.md` is a mechanism no one else has, and the field report shows why: it makes the reader rebase N diffs onto a document nobody updates.

### 7.6 Recommendation

I recommend **a variant of B, which I will call D**, and I would not choose A or C.

**Why not C (Pocock-style, no thread trace).** Three reasons. Its own docs call the loss "the most substantive open complaint about the skill." It has no answer for reversing a closed decision — "there is no official guidance, and the agent's instinct is unhelpful: it tends to design around the bad decision rather than challenge it" — which is the exact case Antmay handles best today. And structurally, Antmay's CLI runs stages unattended across process boundaries, so an in-session-only design has nowhere to live between `spec` and `plan`; C is available to a method that assumes one continuous session and is not available to one with an unattended executor.

**Why not A.** The user's objection is corroborated: nowhere in the ecosystem does anyone maintain a whole design document during a live interrogation. The one counter-example, Pocock's `grill-with-docs`, writes *during* the session but only in one-line atomic units (a glossary term, an ADR). That is a useful distinction to keep: incremental durable writing during a grilling is fine when the write unit is a line, and unworkable when it is a document.

**D — decisions as a settled-state store, a spec that indexes rather than restates, and a project-level durable layer.** Concretely:

1. **`decisions.md` becomes the current set of settled points for the thread, maintained in place.** Each record keeps a stable `DR<N>` that is never reused, plus Context / Decision / Rationale and a `Settled:` date. Changing a decision **edits that record in place**, updates its date, and appends a one-line `Revised: <date> — <what changed and why>` note inside the record. Nothing is renumbered; nothing is deleted. This is the joelparkerhenderson middle path, it keeps rationale, and it removes the reader's obligation to resolve a supersession chain before knowing what is true. The append-only history is not lost — it is in git, where it belongs, because no downstream agent should have to read it to answer "what did we decide?".
2. **The spec stops being a derived expression and becomes the thread's design document, authored once, citing decisions rather than restating them.** A requirement that rests on `DR7` says so and does not paraphrase `DR7`. `reconcile-spec` shrinks to a *provenance check*: every design claim in the spec traces to a decision, to the seed, or to the project durable layer — and an untraceable claim is **either promoted to a decision or removed**, not silently stripped. That is the classical gold-plating remedy ("if the capability is important enough to be in the system, it needs to be documented as a requirement"), and implementing only the deletion half is what produced field-report finding (1). Antmay already owns the machinery for the promotion half: an untraceable-but-plausible design claim is a pending decision.
3. **Add a project-level durable layer with two artifacts and one index.** A glossary, an ADR log with globally stable numbers and append-only supersession (this is where §7.3(b) applies), and a short index naming what is currently authoritative. Promotion into the ADR log is gated — Zimmermann's criteria or the three-gate test — and promotion is a step at `finish`, when it is knowable whether a decision actually bound anything, rather than a guess at recording time. Cross-thread references then cite a global ADR number instead of `CB1 DR13`.
4. **Make the roadmap a living index with lazy children.** Destination, ordered entries with immutable IDs, a one-paragraph sketch and scope boundary each, "not yet specified," out of scope. Edit it in place; retire `roadmap-feedback.md`. A child is seeded when the frontier reaches it, against the durable layer as it stands then.
5. **Make historical mechanical by allow-list, not by banner.** The durable-layer index enumerates what is authoritative; every thread artifact is historical unless a durable document points at it. `finish` archives by default. Every reading skill carries the read order: durable layer, then active thread, then other threads only when explicitly cited.

**The serious alternative, and why I do not choose it.** BMAD's route — keep the append-only log, make it *lossless* by widening what it records (capabilities, constraints, assumptions, direction, not just decisions), drop record IDs and supersession pointers in favour of chronological last-write-wins, and fully re-derive the spec on every run — is a coherent answer to the same problem, and it is battle-tested. It preserves the merge-drift property BMAD names: several skills can feed one spec in any order because nothing is edited in place. If Antmay wants to keep regeneration, this is the way to do it, and it would require widening `decisions.md` into a typed thread log and making `spec.md` a machine-derived artifact nobody hand-edits.

I do not recommend it for Antmay for three reasons. It contradicts what the field report says worked — Antmay's records carry Context/Decision/Rationale and stable `DR<N>` numbers that were used, correctly, as cross-thread citations; BMAD's one-line untagged entries would lose that. It requires the spec to be genuinely non-hand-editable, which conflicts with Antmay's write-authority model where reconcile and targeted-fix operations edit the spec. And it does not address findings (2), (3) or (5) at all: BMAD still needs `bmad-project-context` for the durable layer and `bmad-retrospective` to reconcile spec against built code. D absorbs BMAD's real lesson — *the loss happens because the log does not carry what the spec needs* — without adopting its whole machine.

**Trade-offs, honestly.** D gives up the guarantee that a thread's `decisions.md` shows how thinking evolved without consulting git — a real loss for a reader doing archaeology in a repo they cannot run `git log` in, and a loss for PR review, where the diff of an edited record is less legible than a new appended block. It adds a promotion gate, which is a judgement call that will sometimes be made wrong; the mitigation is that a wrong call is cheap because the thread-local record still exists. It adds a merge-like burden at `finish` (promote decisions, update the durable index) that must not become the ceremony tax §6.1 describes. And a citing spec is less readable standalone than a restating one — the mitigation is that citations resolve within the same folder, and the alternative is the N-copies problem the reconcile family exists to fight.

What D does not do is throw away what worked. The decision log still catches every settled decision, still carries Context/Decision/Rationale, and still handles reversal explicitly — it just answers "what is true now" in one read instead of N.
