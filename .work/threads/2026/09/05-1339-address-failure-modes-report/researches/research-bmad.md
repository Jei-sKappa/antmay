# Research: BMAD Method — decisions, specs, plans, and durable truth

**Subject:** `bmad-code-org/BMAD-METHOD`, cloned at tag `v6.12.0` (2026-09-03) into `temp/mirrors/bmad/`. Paths below are relative to that mirror.

BMAD v6 has already fought the battle this thread is about, and its answer is a shape we have not listed. The settled record is an **append-only, one-line-per-entry, write-only memory log (`.memlog.md`) written by a script during the live conversation**, and the contract document (`SPEC.md`, `ARCHITECTURE-SPINE.md`) is a **projection re-derived from that log on every run and never hand-edited**. That is not option A (maintain a design doc during the grilling), not B (rewrite decisions in place), not C (no trace) — call it **option D: cheap typed appends during the session, full re-render at the end, one writer per artifact.** Around that core: inferred content is *labelled* (`Assumptions`, `Open Questions`) rather than stripped; a human-owned frozen region inside the implementation spec separates "intent was wrong" from "spec was wrong"; status lives in one deterministic ledger; and finished planning documents are handled by making them **physically unreachable**, not by marking them stale. Where BMAD has not solved our problems it says so: it has no durable project-level *planning* layer, its cross-artifact propagation is still a manual N-document edit, and its `deferred-work.md` feedback file is write-only in the shipped skills — our failure mode #4, reproduced independently.

A caveat for reading older BMAD literature: v6 retired most of what BMAD was famous for. `bmad-shard-doc` and `bmad-index-docs` were **removed outright**, and the `bmad-create-story` / `bmad-dev-story` pair — source of the famous story file with copied-in "Dev Notes" — was deprecated to `v6-shims/` (`CHANGELOG.md`, v6.11.0). Skills still *read* sharded documents (`skills/bmad-correct-course/SKILL.md:83-88`); nothing produces them.

## Artifact model

Two nested units, no per-work-item folder above them. The **epic** is a spec folder — `SPEC.md`, companions, `stories.yaml`, `.memlog.md` (`skills/bmad-spec/SKILL.md:42-51`). The **session** is one build spec, "a single user-facing goal within 900–1600 tokens" (`skills/bmad-build/workflow.md:21-29`); above 1600 the run offers a split and pushes the remainder to `deferred-work.md`.

Source of truth moves per phase and is stated at each. Planning: "the memlog (not the rendered `SPEC.md`) is the authority on what was decided and on capability IDs" (`skills/bmad-spec/SKILL.md:67`). Handoff: the rendered spec declares itself "the complete, preservation-validated contract for what to build" (`assets/spec-template.md:7`). Implementation: "the spec is the subagent's sole source of truth" (`skills/bmad-build/step-03-implement.md:32`). Codebase: "code access beats documentation access — a document describing the system loses to the source it describes" (`docs/existing-codebases/theory-of-project-context.md`).

Almost everything is lazy; the one eager artifact is the memlog, created the moment intent is confirmed and its path told to the user (`skills/bmad-product-brief/SKILL.md:79`).

## Decision capture

BMAD's best answer is a tool, not a discipline. `skills/bmad/scripts/memlog.py`'s docstring states three invariants: **append-only and chronological** ("There is no edit or delete subcommand by design; history is never rewritten"); **write-only / blind** ("Every command is an atomic, context-free write and echoes the new state as one line of JSON, so the caller never re-reads the file mid-session. The one time the file is read is on resume"); and **no lifecycle status** ("Whether the work is done, blocked, or paused is itself a fact that happened, so it is recorded as an entry […] never as frontmatter the log would have to mutate").

The file is flat: "there are no sections or grouping. Every entry is one line, recorded at the END in the order it happened. The chronology itself is the structure." Entries are `- (type) text` with an open vocabulary the *host skill* names — `decision|constraint|capability|assumption|question|direction|note|event` for spec (`skills/bmad-spec/SKILL.md:62`), `decision|change|override|assumption|event` for PRD (`skills/bmad-prd/SKILL.md:14`), plus `version` for architecture. Writes are atomic. `bmad-forge-idea` states the read discipline: "Don't read the memlog back except on resume" (`SKILL.md:78`).

Rationale is kept, and in the architecture skill kept *only* here: "Record decisions, not rationale (rationale lives in the memlog)" (`skills/bmad-architecture/SKILL.md:17`). A reversal is an append: "a later entry supersedes an earlier one on the same point while the history stays intact" (`skills/bmad-spec/SKILL.md:77`). Note what is absent: no supersession pointer, no record ID, no `Context/Decision/Rationale` shape. One line, "one-line gist, reason included", and last-write-wins is resolved by the deriving agent reading the log whole.

The nearest thing to an ADR set is the spine's `AD-n` blocks — `Binds` / `Prevents` / `Rule`, `[ADOPTED]` when reality already settled it, "stable ascending id (never reused/renumbered)" (`assets/spine-template.md:34-41`). These are decisions *without* rationale by design: the spine fixes "only the **invariants** keeping independently-built units from diverging […] the durable calls a future builder *can't* read off compliant code" (`SKILL.md:9`).

## Spec ↔ decisions

The derivation rule and its stated reason are the most useful lines in the repository for this thread:

> Deriving the contract from a living log instead of editing the contract in place is what lets the steps around the spec (PRD, UX, architecture, epics) run in any order and feed the same spec without merge drift: the log only accumulates, the artifact is re-rendered. So the spec is updated *only* by re-deriving it here — bmad-spec is its single writer; a hand-edit to `SPEC.md` from outside is unsupported and is overwritten on the next derive.
> — `skills/bmad-spec/SKILL.md:57`

Same session, not a fresh agent: the skill running the conversation appends as it goes and renders at the end. `bmad-architecture`: "The spine file itself is **distilled from the memlog at the end**, not written as you go" (`SKILL.md:35`), optionally in a subagent for a long run.

The validation step is **two-sided**, which is the crucial difference from our `reconcile-spec`. `bmad-spec` Self-Validate runs **Pass 1 Coherence** — fix weaknesses "without inventing content the input did not support. Calls made without direct confirmation become `assumptions[]`; gaps that could not be filled become `open_questions[]`" — and **Pass 2 Preservation** — "Walk the source claim by claim. Confirm each load-bearing claim landed in SPEC.md or a companion. Wrapper-ceremony drops are logged under 'Wrapper-only content' so the drop is on the record, not silent" (`SKILL.md:118-126`). Inferred design is never deleted; it is promoted into standing template sections (`assets/spec-template.md:39-49`). `bmad-prd` runs the coverage half as a ritual: "**Memlog audit.** Walk `.memlog.md` with the user; each entry captured in PRD, in addendum, or set aside", then "**Input reconciliation** […] Surface gaps — especially qualitative ideas (tone, voice, feel) the FR structure silently drops" (`SKILL.md:87-88`). The PRD itself is *not* re-derived — it is edited in place with the memlog as audit trail and resume memory ("whatever isn't logged is lost on resume"); a missing memlog on Update is bootstrapped by a subagent reverse-engineering a thin log from the PRD (`SKILL.md:14,34`).

Context exhaustion is handled without sharding: hard size budgets (900–1600 tokens for a build spec, 800–1500 for epic context); "Extract, don't ingest" — sources and reviews go to subagents that "return ONLY a compact summary […] the parent never holds full review text" (`skills/bmad-prd/SKILL.md:67,77`), and the diff is passed as a *path*; a build spec self-contained enough that "Implementation should work from the spec without being told the investigation again" (`step-02-plan.md:22`); and a published input ceiling of "roughly a 40-page document" beyond which the spec skill "silently loses the parts that mattered" (`docs/plan/choose-a-planning-path.md`).

## Historical vs authoritative

**Status fields, but only where they route.** The build spec's `status` frontmatter is the resume dispatcher; for `done`, step 1 says "ingest as context and proceed […] do not resume" (`step-01-clarify-and-route.md:22`). `stories.yaml` forbids one — "No `status` field, ever" (`assets/stories-schema.md:20`) — because status belongs to `sprint-status.yaml`, generated and merged by a Python script and repairable from evidence: "Repair is the only path that can mark a story as less complete than it was, because it reflects confirmed reality" (`docs/plan/break-work-into-stories-and-track-it.md`). The memlog has no status by design.

**Mechanical staleness, once.** `epic-<N>-context.md` is valid only when "no file in `{{.planning_artifacts}}` is newer" (`step-01-clarify-and-route.md:56`). It is the system's only mtime invalidation, and it guards a derived cache, not a source.

**Physical inaccessibility for finished planning.** This is BMAD's real answer to "later agents read old specs as authoritative":

> Feeding them textual descriptions of things they can already read there creates contradiction, ambiguity, and context-window bloat. That, oddly enough, includes the original greenfield context (PRD etc). **Keep it archived for the few sessions that need it, and out of reach of an ordinary change — an agent doing a small request should not even be able to find it by accident.**
> — `docs/existing-codebases/start-in-an-existing-codebase.md`

The brownfield flow follows: `bmad-project-context` replaced `bmad-document-project`, which "scanned an existing repo and generated a documentation tree […] Large, unverified, stale on arrival: the kind of context that makes agents worse" (`docs/existing-codebases/theory-of-project-context.md`).

## Project-level durable layer

Exactly one durable project-level artifact: the `bmad:context` block spliced into the repository's `AGENTS.md`. `theory-of-project-context.md` argues for keeping it small with cited results — repository instruction files measured "no improvement in success rate and +20% inference cost"; "randomly generated rules matched expert-curated ones"; but a *compressed index of knowledge the model lacks* scored 100% where the same file format restating the repo scored 53%. What earns a line: commands whose correct form is not the obvious guess, policy the code cannot express, conventions diverging from ecosystem defaults, pitfalls **from observed failure only**, cross-component rules. Excluded: what the code says, structure and file maps, overview documents, ecosystem defaults, **history and edit narration** ("Do not write 'We removed X because…'. Git holds history; the block states present truth only"), and aspirational state.

Maintenance is first-class — `setup | adopt | refresh | record | audit`. Refresh runs `git log --diff-filter=DR --name-only` since a recorded SHA against every line; audit "ends smaller or equal"; every removal is a user-approved ledger entry; and "A policy or pitfall is removed only when what it is about is gone […] Absence of recent failures is never grounds: a working rule erases the evidence that it is still needed" (`skills/bmad-project-context/SKILL.md:85,111`).

Crucially, BMAD names our gap and declares it unsolved: **implementation context** (checkable against code, stale per commit, loaded every session, must be tiny) versus **planning context** — "rationale, rejected approaches, ownership, domain meaning, org standards […] stale in months rather than hours, consulted in bursts. **That is a different capability, and it is coming separately.**" Consistent with that, the one glossary in the system is a *per-spec companion* beside `SPEC.md`, not a project artifact (`skills/bmad-spec/SKILL.md:93-98`).

Stories cite the durable layer by path list, not by copy: the build spec's `context: []` frontmatter holds "paths to project-wide standards/docs the implementation agent should load. Keep short — only what isn't already distilled into the spec body", and the implementation subagent loads them itself (`spec-template.md:8`, `step-03-implement.md:34`). Stable IDs exist per artifact and never travel: `CAP-N`, `AD-n`, PRD `FR` ids, story ids. The spine's "Capability → Architecture Map" is the one place they join.

## Large-effort decomposition

BMAD admits decomposition is lossy — "a requirement weakens, a constraint disappears, or two correct stories fail when combined" — and hedges three ways.

**The story list is provisional.** "The story list is an execution plan, not a promise that nothing will change. Update the spec and re-run Story Breakdown when earlier work reveals a missing constraint, a better division, or a conflict between stories" (`docs/plan/choose-a-planning-path.md`). Ids pin only once a story file exists: "Stories with no spec file yet may be renumbered, reordered, or removed freely on re-derive" (`assets/stories-schema.md:42-44`). A spec update notices rather than rewrites: "check the story descriptions against the updated spec; if any no longer matches, say so and offer to re-run Story Breakdown. The update itself never rewrites `stories.yaml`" (`skills/bmad-spec/SKILL.md:134`).

**Forward dependencies are forbidden.** "CRITICAL: Stories MUST NOT depend on future stories within the same epic", with the anti-example "Epic 1 Story 1 creates all 50 database tables" (`steps/step-03-create-stories.md`). Risky stories go first: "Early stories often settle the architecture […] Give those decisions human attention before automating repetitions of them." And Build loads the previous `done` story of the epic, extracting its "Code Map, Design Notes, Spec Change Log, and task list" as continuity (`step-01-clarify-and-route.md:66`).

The change-management workflow, `bmad-correct-course`, is the heaviest thing in the repo and the one skill still shaped like v4 (XML `<workflow>`, a 288-line checklist). It **FULL_LOADs** PRD, epics, architecture, UX, spec and the `AGENTS.md` block (`SKILL.md:63-73`), asks whether the change invalidates future epics, emits `sprint-change-proposal-<date>.md` with literal OLD/NEW blocks per artifact, and classifies blast radius Minor/Moderate/Major. Propagation is not automated: "it updates `sprint-status.yaml` and **hands the document edits off. Apply them**, then create the new or changed stories". Same posture at epic close: "**Spec reconciliations** arrive with the evidence attached, for you to apply to the project contract by hand. An uncertain interpretation never gets written into a spec on its own" (`docs/build/finish-an-epic.md`).

For roadmap-like inheritance, `bmad-architecture` has the mechanism our child briefs lack: a child spine loads the parent's ADs as "**binding, read-only** constraints […] Your job is only what the parent **left open** […] A new `AD` that contradicts or weakens an inherited one is a **conflict to surface**, not a local override" (`SKILL.md:31`).

## Duplication

BMAD duplicates deliberately and states when copying beats citing: "**Describe by purpose, not by source.** Write 'API responses must include pagination metadata' not 'Per PRD section 3.2.1, pagination is required.' **Planning doc internals will change; the constraint won't**" (`compile-epic-context.md:51`). The same file forbids verbatim copying and anything derivable from the codebase, caps its own size, and is regenerated wholesale on mtime change — regeneration, not a link, is what makes the copy safe.

Counting re-expressions of one decision: on the PRD path, brief → PRD (+addendum) → spine → `epics.md` (which copies the FR/NFR inventory and an "FR Coverage Map", `templates/epics-template.md:12-32`) → `epic-N-context.md` → build spec → code, i.e. five restatements. On the light path — memlog → `SPEC.md` → build spec → code — it is two, the first mechanical. The light path is now the documented default: "A short list of decisions is often enough on its own. You need a PRD when more than one person must agree on what the product is […] otherwise skip it."

Anti-duplication rules are pointed where they exist. `SPEC.md` "points at [companions] rather than copying them", and project-wide docs are "listed as **adopted companions**, never duplicated into SPEC.md" (`SKILL.md:101`). A story's `description` is "What this story covers, **pointing into `SPEC.md`** — not a story spec." The dispatch prompt may not restate the spec: "Do not add goal restatements, file lists, ownership boundaries, investigation detail, acceptance criteria […] the spec is the subagent's sole source of truth." And `bmad-project-context`: "No instruction lives in two loaded files, where it is paid for twice."

Alignment rests on four things — single-writer rules, regeneration over patching, mtime invalidation of the one cache, and one human-gated offer: "When a change overrides something that came from a source input, offer to update that source too, so upstream and the spec don't silently diverge" (`SKILL.md:154`). That offer is the entire upstream-propagation story.

## Known failure modes

**From the maintainers' own record.** The changelog reads as a list of failure modes being retired. Generated documentation makes agents worse — `bmad-document-project` deleted, `project-context.md` dropped as a deliverable, and v6.12 ships `persistent_facts` **empty** so no planning document auto-loads into a build any more (`skills/bmad-build/customize.toml:27`). Sharding was abandoned. Ceremony was cut hard: core went from fourteen skills to eight, v6.11 "deletes about 1,900 more lines than it adds", and v6.12's headline is "**Build decides how much ceremony a change needs after investigating it, not before.**" Findings were being dropped silently — fixed by the append-only `## Review Triage Log`. Hallucination is fought by evidence rules, not by stripping: "A claim you cannot point at […] is not a finding. Drop it" (`skills/bmad-retrospective/SKILL.md:10`). Two status layers still coexist, needing a sync procedure and a `fix sprint-status` repair intent.

**From issues and discussions.** Every one of our five field-report failure modes has a filed counterpart.

- *Propagation across N copies (#2).* [#2034](https://github.com/bmad-code-org/BMAD-METHOD/issues/2034) names the mechanism exactly: correct-course changes stories but leaves the epic outdated, and "when agents later read the `epics.md` for context … they will be fed stale information, leading to hallucinations or incorrect architectural decisions." [#334](https://github.com/bmad-code-org/BMAD-METHOD/issues/334): the PM has a correct-course task and the architect does not, "leading to a mismatch between the updated PRD and the existing `architecture.md`." [#1638](https://github.com/bmad-code-org/BMAD-METHOD/issues/1638), across ~12 runs: "Every time I run the Create Epics and Stories workflow, I end up making decisions that properly belong in the Architecture or PRD workflows […] I have to manually remember to go back and update the upstream documents." [Discussion #2778](https://github.com/bmad-code-org/BMAD-METHOD/discussions/2778), a three-week brownfield trial: "**the source of truth matters enormously. If the specification is spread across several places, the AI can end up following different interpretations.**"
- *Historical read as authoritative (#3).* [#1218](https://github.com/bmad-code-org/BMAD-METHOD/issues/1218): `document-project` "generates static documentation snapshots that become outdated as code evolves […] leading to **stale docs, AI agent hallucinations, and wasted debugging time when agents work from outdated context**." [#2649](https://github.com/bmad-code-org/BMAD-METHOD/issues/2649) (open) states the converse — without a reconciliation checkpoint, teams "silently treat code or tests as authority and leave the approved intent stale." [#1930](https://github.com/bmad-code-org/BMAD-METHOD/issues/1930) is the mirror-image hazard: correct-course "can silently rewrite the acceptance criteria of a story that was already committed and merged — erasing the historical record of what was actually built."
- *Write-only feedback channel (#4).* Confirmed in the code — `deferred-work.md` has five writers and no reader — and filed as [#2199](https://github.com/bmad-code-org/BMAD-METHOD/issues/2199): "After running code reviews on 10+ stories, the deferred backlog can grow to 30-40 items — including critical bugs and security fixes — with no workflow ever surfacing them."
- *Lossy compression between artifacts (#1).* [#2767](https://github.com/bmad-code-org/BMAD-METHOD/issues/2767): the anti-duplication rules in `compile-epic-context` silently delete any requirement that exists only as a pointer, and "the compiled context gives no sign that anything was dropped" — the agent "built the UI chrome without ever seeing the visual contract." [#1542](https://github.com/bmad-code-org/BMAD-METHOD/issues/1542) extracted four bullets from a 300-line UX spec.
- *Sharding, retired.* [#912](https://github.com/bmad-code-org/BMAD-METHOD/issues/912): sharding leaves the whole document in place while 15+ workflows prefer the whole document — "Wastes 50%+ of AI context window on redundant data […] Risk of editing one version while other becomes stale." [#1260](https://github.com/bmad-code-org/BMAD-METHOD/issues/1260): "Users have no way to shard documents via any documented BMAD workflow." The removal itself (PR #2603) is asserted, not argued: "legacy pre-skill utilities", "retired with no replacement."
- *Ceremony.* [#1199](https://github.com/bmad-code-org/BMAD-METHOD/issues/1199): "For 5-15 minute fixes, this is disproportionate overhead […] **ceremony costs more than the work**." [#2003](https://github.com/bmad-code-org/BMAD-METHOD/issues/2003) is a full structural critique from a real epic retrospective.
- *Invention, and its cause.* [#1693](https://github.com/bmad-code-org/BMAD-METHOD/issues/1693): the PRD workflow "**Invented a three-phase roadmap** (MVP / Growth / Vision) that does not exist", then propagated the labels through success criteria and architecture. [#2772](https://github.com/bmad-code-org/BMAD-METHOD/issues/2772) (open) measured a review-layer prompt that demands ten findings: "**at least 210 findings exist because the prompt requires them, independent of what the diff contains**." A quota manufactures content; the fix (PR #2805) was to drop the quota. Notably, **nobody reports the derived-spec model producing invention** — that failure clusters in review and in prose-authoring workflows.
- *Two live risks in the mechanism we want to copy.* [#2621](https://github.com/bmad-code-org/BMAD-METHOD/issues/2621) (open): `memlog.py`'s read-modify-replace has no inter-process lock — "Five consecutive runs on Windows 11 / Python 3.13 produced: 28–33 failed processes; only 17–24 of 50 entries present" when parallel agents journal to one log. [#2619](https://github.com/bmad-code-org/BMAD-METHOD/issues/2619) names the derived model's real cost: "**re-deriving `stories.yaml` rewrites the file, so a hand-added declaration is lost unless it was logged to `.memlog.md` first**."

## Verdict for Antmay

**Take option D, in this shape.** One append-only in-thread log, written by a *script* during the session — one line per entry, typed, atomic, never re-read mid-session — with every downstream artifact re-rendered from it by a single-writer skill rather than patched. That is option A's information model with option A's cost removed: the objection was maintaining a *document* during a live grilling, and the answer is that you do not maintain a document, you fire one cheap append per settled point and render at the end. `memlog.py`'s docstring is worth stealing nearly verbatim, including the two invariants we would otherwise get wrong: **write-only/blind** (never re-read mid-session, so appending stays cheap and the model is never re-anchored on its own notes) and **no lifecycle status** (a terminal moment is an `event` entry, never frontmatter to mutate).

1. **Keep `decisions.md` append-only but demote the record shape.** Our `Title / Scope / Context / Decision / Rationale` record *is* a document maintained during a grilling — which makes it expensive and, in practice, lossy, since an agent under conversational load writes thin Context. BMAD writes `- (decision) <one-line gist, reason included>` and gets a denser, more faithful log. Widen the vocabulary past decisions to `capability | constraint | assumption | question | direction | event`, so what the spec agent currently has to *infer* is captured when it arises. Direct fix for failure mode #1.
2. **Make `spec.md` a render, not an authored artifact, with exactly one writer.** Adopt the invariant verbatim: a hand-edit is unsupported and is overwritten on the next derive; updates happen by appending and re-rendering. This dissolves `reconcile-spec` as a separate skill and dissolves #2 for the decisions→spec hop — there are no two copies to align, only a log and a projection.
3. **Replace "strip what was invented" with "label what was inferred."** Highest-value single change. Two passes: Coherence (fix without inventing; unconfirmed calls become `Assumptions`, unfillable gaps become `Open Questions`) and Preservation (walk the source claim by claim; log every deliberate drop so it is on the record). Then make the labels bite: the artifact cannot leave draft while an Open Question remains.
4. **Adopt the frozen-region boundary in the implementation artifact.** A `<frozen-after-approval>` block around Intent, Boundaries and the I/O matrix, everything else agent-owned and re-derivable, makes triage mechanical: a finding routes to `intent_gap` when its root cause is *inside* the block and to `bad_spec` when *outside*, and only the first returns to the human. That is a sharper version of our "honest deviation vs. surface a decision" rule. Pair it with the file's append-only `Spec Change Log` and `Review Triage Log`, which give the deviation record without a second artifact.
5. **Keep the roadmap child brief as an inheritance contract, not a pre-written spec.** Parent decisions bind read-only by their original IDs under "Inherited Invariants"; the child's job is only what the parent left open; a contradiction is a conflict to surface, not a local override. Combine with the pinning rule — an unmaterialised child may be renumbered, reordered or deleted freely on re-derive, a materialised one is pinned — and #4's staleness stops mattering, because unstarted briefs become cheap to discard rather than documents to maintain.
6. **For #3, prefer inaccessibility to a status marker.** "Out of reach of an ordinary change — an agent doing a small request should not even be able to find it by accident" is stronger than any `Status: historical` header, because it does not depend on a later agent honouring one. Our archive move already gives path separation and our navigation skill already treats the archive as terminal; the residual gap is an *ad-hoc* agent reading an archived `spec.md` as current truth, and that closes by making archived planning material harder to reach and by having one small live project-level document such an agent finds first — not by stamping the archived file.
7. **Build the durable planning layer BMAD says it hasn't.** Its own doc names the split: implementation context (tiny, verified, loaded every session — we have this) versus planning context (rationale, rejected approaches, domain meaning). For the second, the transferable shape is the **architecture spine**, not an ADR pile: only the "durable calls a future builder *can't* read off compliant code", filtered by one test — "If two units one level down built this independently, could they choose incompatibly? Fix it here only when the answer is yes, **and** the call is non-obvious, **and** it's a real trade-off" — with `Binds` / `Prevents` / `Rule` per entry, stable IDs, and an explicit `Deferred` section. Everything structural is "seed: true at cold-start, owned by the code once it exists." Steal the maintenance triad too: refresh diffs the block against `git log --diff-filter=DR` since a recorded SHA, audit "ends smaller or equal", and a working rule goes only when the thing it guards is gone.

**Avoid four things.** (a) `bmad-correct-course` — a change workflow that FULL_LOADs five documents and emits before/after edit blocks for a human to apply by hand is the N-copies tax institutionalised; it exists *because* the PRD path has five restatements, and the right response is not to have them. (b) A second write-only queue: `deferred-work.md` has five writers and no reader, exactly like our roadmap-feedback channel — do not add a queue without a skill whose job is to drain it. (c) Two status layers: BMAD needs a sync procedure plus a repair intent to reconcile spec frontmatter against its ledger. If we adopt a routing `status:` anywhere, it must be the only one. (d) Deriving the *whole* chain — BMAD does **not** re-derive the PRD from its memlog, only the spec and the spine. Re-derivation is affordable for a terse contract with stable IDs, not for a long prose document a human negotiates. Render what is short and machine-facing, edit in place what is long and human-facing, and audit the log against the latter at finalize.

**Two costs to accept going in**, both filed against BMAD. Re-derivation means *anything not in the log is destroyed on the next render* (#2619) — so the log-first rule stops being a convention and becomes load-bearing, and every skill that settles something must append before it acts (we already have that rule for decisions; it would now cover assumptions and constraints too). And an append-only log with concurrent writers needs real serialisation (#2621) — our subagent implementation executor would corrupt a naively-implemented log, so either one writer holds the log or each writer gets its own file.

Option C is refuted by this codebase in passing: BMAD *did* ship trace-free generated documentation and deleted it, and the surviving thin layer is thin precisely because "intent, rationale, and what was deliberately rejected" are the only things not recoverable from source. Something must hold them. The memlog holds them cheaply.
