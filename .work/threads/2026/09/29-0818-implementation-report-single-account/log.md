- (direction) the implementation report is the one place a reader learns whether the plan completed and where the run departed from it or made a judgment call, answerable at a glance; material serving only the fidelity review stays but does not lead
- (decision) the run progress file stays, because it is what carries deviations, judgment calls and concerns through context compaction to the report written at the end, but it becomes an append-only file of typed one-line entries (a task done with its commit, a deviation, a judgment call, a concern) from which the report is folded; a bare event log of started/finished lines was rejected because it would keep resumability and lose exactly the content the report needs, and reply tokens and dispatch counts leave it
- (decision) the merged reviewer keeps writing its findings file, because the fix implementer receives the findings verbatim by path and they survive a compaction mid fix loop, which retyping them into the fix brief would not guarantee
- (decision) the implementer subagent no longer writes an outcome file: its assumptions and known risks travel in its reply and the orchestrator passes them into the reviewer brief, because that content is small and the file adds a handoff without protecting anything
- (decision) for a run that executed a plan, the report's changes section becomes a task ledger: one line per plan task with its ordinal, its title as the index gives it, and its commit, or not run or blocked where that applies, with a pointer to its deviation or judgment call when it departed; a task that followed its brief is not described. Dropping the section for plan runs was rejected because resume and the fidelity review would have to infer the task-to-commit mapping from commit subjects that carry no task numbers, and keeping it by area with a brevity instruction was rejected because brevity is not checkable. A run with no plan keeps describing its changes
- (decision) the report gains an optional judgment calls section, each entry naming the choice, the freedom or silence it filled, and why, kept apart from deviations as the glossary distinguishes them; both optional sections sit directly after the outcome and before the changes, so whether the run completed, departed, or made calls is read from the top of the report and left out when there is nothing to say. Folding judgment calls into deviations was rejected because the closing currency check reads deviations as departures from the spec, and leaving them to commit messages was rejected because nothing the reader opens would show them
- (decision) the final chat message restates nothing from the report: it gives one sentence of outcome, how many deviations and judgment calls the report records, any discovery with parent-level impact, the report path and its commit, then the terminal outcome line, so its only job is to tell the reader whether the report is worth opening now. Printing the top of the report in chat was rejected as a smaller copy that can drift from the report, and the terminal line alone was rejected because discoveries with parent-level impact must be surfaced in chat
- (decision) the three sections keep distinct questions: changes says where the work landed, verification says whether the code holds as a whole, acceptance maps each spec criterion to its method and evidence. Verification lists only the checks run against the final state, such as the project gates and whole-change suites or builds, plus every check that failed or was deliberately skipped with its reason; a per-task check that passed is not listed, because every commit in the ledger passed the baseline gate by rule. Listing each task's checks was rejected as a restatement of the plan's verification blocks, and merging verification into acceptance was rejected because a standing gate or a failed check is not a criterion
- (decision) a run with no plan uses the same task ledger in its changes section, each implicit task carrying a one-line description of what it did in place of an index title, with its commit, or not run or blocked, and pointers to its deviations and judgment calls; describing changes by area or path was rejected because it would give the section two shapes and lose the task-to-commit link the review relies on
