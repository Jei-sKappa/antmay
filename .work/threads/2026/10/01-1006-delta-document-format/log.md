- (decision) an edit delta document is modelled on the Claude Code Edit/MultiEdit tools: an ordered list of edits, each an exact old_string, a new_string and an optional replace_all, where old_string must be unique in the target unless replace_all is set, edits apply in sequence against the result of the previous one and the document lands all-or-nothing, an edit whose old_string is absent but whose new_string is present counts as done, a create is the literal target file at the mirrored path with no wrapper, and a delete carries no edits; the current add/replace/remove operations with under/after/end anchors were rejected, because the anchors are ambiguous about placement and quoted text was required to be found but not unique
- (decision) the suite ships one zero-dependency Node script as the only way a delta is checked and applied, with a check mode that reports every failure and writes nothing and an apply mode that runs check over the whole delta and then writes every document or none, used by close-thread for its dry run and landing and by spec and review-spec to check a delta right after it is drafted, because uniqueness, sequential application and the already-done rule are checks an agent applies unreliably by reading, and Node is present wherever the suite was installed with npx skills add
- (decision) the delta script is two zero-dependency files rather than one, check-delta.mjs holding parsing and validation and runnable on its own, and apply-delta.mjs importing check-delta.mjs by relative path, running the whole check and then writing every document or none; the manifest gives spec and review-spec only check-delta.mjs and close-thread both, so a skill that must not land a delta physically lacks the command to do it; one script with check and apply modes was rejected, because apply would sit in spec's folder ready to run by mistake, and a flag gating apply was rejected, because a flag written in a body is a text rule any agent can type, and two files with duplicated validation were rejected, because the copies would drift and a passing check would stop predicting a successful apply
- (constraint) check-delta.mjs decides whether it was run directly by comparing import.meta.url against pathToFileURL(realpathSync(process.argv[1])), because without resolving symlinks the guard silently skips the command when the path goes through a symlink, as macOS temporary paths do, which was observed when testing the import between the two files
- (decision) an edit or delete delta document is JSON, carrying the edits as exact strings, and check-delta.mjs renders each edit as an old/new block so humans and review-spec read that rendering rather than the escaped strings, because JSON.parse needs no bundled parser and JSON strings are exact including the trailing newline; YAML was rejected, because Node has no YAML parser and block-scalar chomping and indentation are where an exact old_string silently stops matching, and search/replace markers were rejected, because a line of = under text is a valid Markdown setext heading and the format has no place for document-level fields
- (decision) delta documents carry no hash: an edit document is its type and its edits, a delete is its type alone, and a conflict is exactly what check-delta finds through old_string matching, because the hash cannot say what changed around an edit, close-thread never commits so the landed diff is reviewed anyway, and the strict hash gate was rejected, because it blocks the close on every unrelated parallel change to the glossary or an agents file and costs a spec amendment each time
- (document) ADR: a create delta document is the literal target file at the mirrored path and an edit or delete is a JSON document whose edits follow the Edit tool model of an exact unique old_string applied in order and all-or-nothing, with no base hash, because a Markdown wrapper nested one document in another and its anchors and hash gate were ambiguous and brittle
- (document) ADR: a delta is checked and landed only by two shipped zero-dependency scripts, check-delta.mjs validating without writing and apply-delta.mjs checking everything then writing all or nothing, with apply-delta mirrored only into close-thread, so a skill that must not land a delta physically lacks the command
- (document) suite/AGENTS.md: add shared/references/scripts/ to the Layout tree as the delta scripts, mirrored into the declaring skills like any shared reference
- (document) glossary: delta document, redefined as a literal file for a create and a JSON document of Edit-model edits for an edit or delete, with no recorded hash
- (document) glossary: shared reference, redefined to include the scripts kind alongside formats, instructions and tracker material
