# Decompose checkpoint validation without weakening aggregate diagnostics Decision Log

## DR1: Scope is the cross-field pass and the coupling between the two passes

Context: `cli/src/state/checkpoint/validate.ts` runs two validation passes behind one exported `validateCheckpoint` coordinator. The field-shape sweep walks the document's fields in schema order, delegating each to one of about twenty purpose-named private helpers. The cross-field pass is one unbroken block of six comment-delimited sections — `stageIndex` bounds by condition, observed-harness coverage, `workspace.path`/`execution.cwd` equality, attempt-level invariants, the executing-attempt position rule, and recovery resolution — and the two passes communicate through five mutable intermediates (`stageInfos`, `observedHarnesses`, `stageCount`, `condition`, `stageIndexValid`). The shape-valid aggregate cross-field regression this thread was opened to add already exists in `cli/src/state/checkpoint.test.ts`, asserting exact ordered diagnostics for four independent cross-field faults, so no work here is gated on writing it.

Decision: The thread changes the cross-field pass and the coupling between the two passes, and nothing else. Delete all five shared intermediates so the cross-field pass takes only the narrowed `RunCheckpoint` — sound because that pass runs only after the field sweep reported no errors, at which point each of the five is either readable off the typed checkpoint or unconditionally true. Then name the six cross-field sections as collaborators the coordinator runs in order, making the invariant set enumerable and making "every invariant runs" visible rather than inferred. Leave the field-shape sweep and every existing private helper unchanged. Introduce no schema-validation dependency. The file's overall length is expected to change little, and that is accepted rather than treated as a shortfall.

Rationale: The cross-field pass is the one part of the module carrying a defect the repository's own standard names — a function long enough to need internal section comments is a set of collaborators that has not been named yet — and the five shared intermediates are the actual coupling that makes the pass boundary hard to see. The field sweep has no such defect: its length is the document's field count, so grouping it would invent divisions the schema does not have and cost a reader a jump per group for nothing. Decomposing it anyway would be motivated only by the module's line count, which is not a reason to change. A declarative schema library was rejected on two counts: precise aggregate prose diagnostics are this module's entire value and a schema's issue objects would degrade them, and the semantic invariants — a recovery reference that must name the final attempt in the ordered history — are not expressible as a schema, so it would replace the routine part and leave the interesting part while adding a second runtime dependency to a package that has exactly one.

## DR2: Cross-field invariants are pure functions driven from a declared table

Scope: `cli/src/state/checkpoint/validate.ts`

Context: DR1 settled that the cross-field pass becomes named collaborators the coordinator runs in order. What signature those collaborators take, and how the coordinator drives them, was open. The module's field-shape helpers accumulate diagnostics by pushing into a caller-supplied `errors` array, while the two artifact-contract validators it calls across a module boundary return `string[]` the caller spreads, so both conventions already coexist. Each of the six cross-field sections was confirmed to read only the checkpoint and to carry no state across sections.

Decision: Each cross-field invariant is a pure function of the narrowed checkpoint returning its own diagnostics — `(checkpoint: RunCheckpoint) => string[]` — and the coordinator runs them from a declared readonly table, flat-mapping that table into the accumulated errors rather than issuing six sequential calls. The table's order is the diagnostic order. The field-shape helpers keep their existing push signature; this governs the cross-field collaborators only.

Rationale: Six sequential calls would leave "every invariant runs" a property of the procedure, which a `return` inserted between two calls still defeats — the exact fragility DR1 exists to remove. A table cannot be short-circuited: suppressing an invariant means deleting a table entry, which a reviewer sees at a glance and which no plausible edit does by accident. The pure signature is also what makes each invariant testable on its own, because a collaborator that pushes into a caller's array can only be exercised through the caller. The cost is a few small per-call array allocations, immaterial against a document already parsed from JSON a handful of times per command invocation.

## DR3: The recovery-resolution invariant switches exhaustively over the recovery kind

Scope: `cli/src/state/checkpoint/validate.ts`

Context: The sixth cross-field invariant resolves a pause's recovery against the recorded attempt history. It currently enters on `recovery.kind !== "retry-stage"` and picks the required attempt result by comparing against `"resume-finalized-done"`, so a fifth recovery kind would silently inherit the `"waiting"` branch. `cli/src/architecture.test.ts` bans comparing a recovery kind to a literal everywhere except the checkpoint validator, and exempts the validator on the ground that parsing an untrusted document has no narrowed union to switch over — reasoning that covers the field-shape recovery parser but not this invariant, which runs only after the document has been accepted and therefore reads a narrowed `WaitingRecovery`.

Decision: The recovery-resolution invariant switches exhaustively over `recovery.kind`, over the `WaitingRecovery` union declared in `state/checkpoint/types.ts`, adding no dependency on `execution/recovery.ts` and requiring no change to the architecture guard's exemption. `retry-stage` contributes no diagnostics. `resume-finalized-done` runs the attempt-reference checks requiring result `"done"`, then the queue-resolution agreement check. `recheck-stage-contract` and `retry-git-finalization` run the attempt-reference checks requiring result `"waiting"`. Behavior for the four existing kinds is unchanged. The queue-resolution check remains independent of the reference lookup — it runs whether or not the referenced stage index matched and whether or not the referenced attempt was found — so a `resume-finalized-done` recovery that both names no recorded attempt and disagrees on queue resolution owes two diagnostics, the reference one first.

Rationale: A fifth recovery kind should fail to compile here rather than quietly acquire a required attempt result nobody chose for it, which is the property `execution/recovery.ts` and `execution/recovery-policy.ts` already hold and this is the one link in the recovery chain that lacks. The guard permits it without amendment because it deliberately does not match `case` clauses. The queue-resolution independence is called out because the natural rewrite nests that check under a successful lookup and silently drops a diagnostic, and the per-fault tests match a single regex each, so none of them would fail.

## DR4: The invariants stay inside the validator module

Scope: `cli/src/state/checkpoint/validate.ts`

Context: DR1 through DR3 settle what the decomposed cross-field pass is; where its six invariants and their table live was open, between keeping them in the validator, extracting a sibling module under `state/checkpoint/`, and a subdirectory holding one file per invariant. Once DR3's exhaustive switch is in place the architecture guard permits all three. The module's length is dominated by the twenty field-shape helpers DR1 leaves untouched.

Decision: The six invariants and their table stay in `state/checkpoint/validate.ts`, declared above the coordinator with the table between them and `validateCheckpoint`. No new module or directory is added under `state/checkpoint/`, and the description of the checkpoint's three-way split in `cli/AGENTS.md` needs no amendment. The module is expected to remain approximately its current length.

Rationale: The table is itself the enumeration of the invariant set, so a file boundary answers a reader's "which invariants exist" no better while costing a jump — the decoration case the CLI's engineering philosophy names. What makes the module long is the field-shape helpers, which stay either way, so extracting the invariants would trade one long file for a shorter one plus a new module without yielding a better thing to read. A per-invariant subdirectory was rejected as over-structure: six functions of five to thirty lines, all driven from one table in one place, in a part of the tree that has only ever held flat files. Should the invariant set later grow enough to justify its own module, moving a table and its entries is mechanical, so this choice forecloses nothing.

## DR5: Only the validator test relocates

Context: `state/checkpoint/` holds no test file at all, while the 1423-line `state/checkpoint.test.ts` is named for that directory but imports only `validateCheckpoint` and the checkpoint types, covering exactly one of the directory's three modules. `readCheckpoint` coverage sits in `state/persist.test.ts`. DR4 leaves `validate.ts` where it is, so no test file is being carried along by a production move.

Decision: Rename `cli/src/state/checkpoint.test.ts` to `cli/src/state/checkpoint/validate.test.ts` with `git mv`, fixing the three affected import specifiers, and change nothing else about it. Every `readCheckpoint` case stays in `state/persist.test.ts`, and no `state/checkpoint/read.test.ts` is created. No shared checkpoint fixture is extracted into `test-helpers/`; the validator test's two-stage `waiting-for-user` fixture and the persistence test's minimal one-stage `ready` fixture remain separate. `vitest.config.ts` needs no change, since it already includes `src/**/*.test.ts`.

Rationale: The rename fixes something a reader actually encounters — a directory that looks untested beside the most heavily tested module in `state/`. Relocating the `readCheckpoint` cases fixes nothing by comparison: three of the five uses in `persist.test.ts` are the instrument of a `writeCheckpoint` assertion rather than tests of the reader, and the leftover-temp-file case exists because the writer creates `.state.json.<hex>.tmp` files, so its subject is that writer/reader pairing and it belongs where the writer is tested. Only the missing-`state.json` case is a standalone read test, and it is four lines. Paying for that with a third duplicated fixture, or with a shared fixture that flattens two deliberately different documents into one parameterized helper, would make more call sites read worse than it improves.

## DR6: Aggregate cross-field coverage reaches every invariant, and pins the recovery invariant's two-diagnostic case

Scope: `cli/src/state/checkpoint/validate.test.ts`

Context: The invariant table of DR2 makes suppression across invariants structurally impossible, and a deleted table entry still fails that invariant's own per-fault test, so the residual aggregate risk is an invariant that owes several diagnostics returning after the first. Three invariants can owe more than one from a single call: observed-harness coverage, attempts agreement, and recovery resolution. The existing cross-field aggregate regression reaches four of the six invariants — it never reaches the executing-attempt-position rule, and never reaches recovery resolution, because the shared fixture's recovery is `retry-stage`, for which that invariant contributes nothing by design. Recovery resolution is therefore both the invariant able to owe the most diagnostics and the one with no aggregate coverage at all, and it is where DR3 requires the queue-resolution check to stay outside the reference lookup.

Decision: Extend the existing shape-valid cross-field document with a fifth independent fault — a second attempt with result `"executing"` carrying neither `endedAt` nor `headAfterAttempt`, which is shape-valid and trips the executing-attempt-position rule — keeping the case's exact ordered array assertion. Then add a separate aggregate case in which recovery resolution alone owes two diagnostics: a `waiting-for-user` document with `stageIndex: 0`, one recorded attempt numbered 1 with result `"done"` and a `DONE` token, and a `resume-finalized-done` recovery naming attempt 2 with `queueResolution: "advance"` against a current stage that declares `"rerun"`. The reference resolves to no recorded attempt and the queue-resolution disagreement is still reported, so the case asserts both diagnostics as an exact ordered array, reference first.

Rationale: Recovery resolution needs its own document because it reads `checkpoint.stageIndex`, and the existing document's opening fault is a deliberately out-of-range `stageIndex`, so any attempt reference placed there would yield a "must name the current stage" diagnostic that is a consequence of that fault rather than an independent one. The second case is the load-bearing addition: it is the only test that fails if the queue-resolution check is nested under a successful reference lookup. The two existing tests that appear to cover this ground each carry one fault and assert with a single regex over `errors.some(...)`, so neither notices a second owed diagnostic going missing.

## DR7: The thread carries no documentation or demo-scenario obligation

Context: The thread changes one production module and its test file. Whether it also owes documentation or scenario work was open, because checkpoint-validation diagnostics do reach a user — through `commands/resume/preflight/load-checkpoint.ts` into the preflight renderer — and the CLI requires a demo scenario for every change that introduces or modifies user-visible terminal output.

Decision: The thread edits no documentation and adds or extends no demo scenario; it delivers code and tests only. `cli/AGENTS.md` and `cli/README.md` are both left unchanged. The queue-resolution independence constraint DR3 establishes is recorded as a comment on the test DR6 adds to enforce it, rather than as module memory.

Rationale: Every diagnostic's wording and order is preserved, so no rendering changes and the scenario requirement is never engaged. The published coupling between the CLI's stages and the skill suite is untouched — no skill, catalog entry, target rule, artifact-state interpretation, or stage prerequisite moves — so the stage-support table stays correct without an edit. And an invariant table declared above the coordinator is structure apparent from reading the code, which the repository's documentation rules keep out of AGENTS.md; module memory is for non-obvious constraints, and the one non-obvious constraint this thread produces is enforced and explained at the place it applies.

## DR8: The no-short-circuit boundary begins after field-shape validation

Scope: `spec.md` and `cli/src/state/checkpoint/validate.ts`

Context: DR2 requires the six cross-field invariants to be invoked together from a declared readonly table, while DR4 places that table at module level before `validateCheckpoint`. The field-shape sweep inside `validateCheckpoint` remains unchanged under DR1 and necessarily contains conditionals and early returns before the checkpoint is narrowed. The planning-readiness review identified that `spec.md` AC-2.3's phrase “between the table's declaration and that expression” would literally include this sweep and conflict with those settled constraints.

Decision: Keep DR2's table-driven invariant design and DR4's module-level table placement unchanged. The no-short-circuit constraint begins only after the field-shape error guard has passed and the document has been narrowed to `RunCheckpoint`: from that boundary through the table's single flat-mapping invocation, the coordinator contains no conditional, no `return`, and no per-invariant call site. The corresponding acceptance criterion in `spec.md` is to state this boundary explicitly.

Rationale: Field-shape validation must retain its control flow so untrusted shapes are rejected before cross-field invariants inspect them. Once narrowing succeeds, invoking the full table as one expression is the point that guarantees no invariant can be skipped or short-circuited. Clarifying that interval resolves the textual contradiction without changing implementation scope, table placement, or aggregate diagnostic behavior.
