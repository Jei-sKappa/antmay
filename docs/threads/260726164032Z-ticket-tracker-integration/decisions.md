# Decisions — Ticket tracker integration for thread creation and closure

## DR1: Tracker writes are authorized by deliberate invocation, never inferred from a reference

Context: The method documents external tracker references as passive (`docs/thread-model.md`, "External references"), and `open-thread` and `finish` forbid tracker writes outright. Every capability this thread adds — creating a ticket, opening a thread from one, closing one — is a tracker write, so the thread had to settle whether those capabilities contradict the passivity rule or are already sanctioned by it.

Decision: Passivity remains the default, and the rule stays a rule about *authorization* rather than a blanket prohibition: no operation may infer permission to mutate a tracker from the presence of an `External:` reference. Deliberate, user-invoked tracker operations supply the explicit intent the rule requires, and they are the sanctioned path for every tracker mutation. The external-references section of `docs/thread-model.md` gains an explicit statement naming those operations as that sanctioned path, so a reader does not have to infer it. `finish` gains exactly one scoped, user-confirmed tracker step (DR2); apart from that step its ban on unsolicited tracker writes stands unchanged, as does `open-thread`'s. No general relaxation is made anywhere else in the method.

Rationale: The existing rule is already about what authorizes a mutation, not about forbidding mutation as such, and `docs/skill-authoring.md` already lists "unclear tracker ownership" among the preflight conditions that refuse a run — evidence the conventions anticipate tracker-acting skills. Keeping passivity as the default confines the change to a documentation clarification plus one named exception, instead of reopening settled ground such as `finish`'s non-closing-reference rule. The trade-off is that the tracker boundary is stated in two places — the general rule and the one exception — rather than consolidated into a single new section.

## DR2: `finish`'s tracker step is disposition-aware, and prefers GitHub's closing keyword over an explicit close

Context: With tracker mutation sanctioned for deliberate operations (DR1), the thread considered having `finish` detect an open ticket for the thread being finished and offer to close it. Two facts constrain the design: `finish` runs *after* opening a pull request but *before* that PR merges, and a closing keyword in a PR body both creates GitHub's issue↔PR development link and closes the issue on merge — a link an explicit `gh issue close` cannot produce.

Decision: `finish` gains a tracker step that runs only when `seed.md` carries an `External:` value pointing at a GitHub issue and GitHub tooling is available. Absent any of those, the step is silently absent and `finish` behaves exactly as it otherwise does. When the step does run, it branches on the branch disposition the user already selected:

- **create PR** — offer to place a closing keyword in the PR body. When the PR's base is the repository's default branch, that completes the job: the link is created and GitHub closes the ticket on merge. When the base is not the default branch, state plainly that the keyword links the ticket but will not close it, and offer a non-closing `Related to <ticket>` reference instead.
- **merge into a confirmed target** — no PR exists to carry a keyword, so after a successful merge offer an explicit ticket close accompanied by a comment citing the merge commit, keeping a navigable pointer from the ticket to the code.
- **leave as-is** — offer nothing; no work was delivered.

Every branch is an offer the user accepts or declines, and declining always leaves the ticket untouched. No explicit close is offered on the create-PR path.

Rationale: Closing the ticket at `finish` time on the PR path would mark work delivered while it is still in review, leaving a closed ticket behind if the PR is reworked or rejected; the keyword defers the close to merge, which is the correct moment, and simultaneously preserves the native development link. Gating the whole step on a GitHub `External:` value keeps the tracker capability additive for users who have no tracker, so `finish` acquires no new dependency. The trade-off is that `finish` must know the repository's default branch to advise correctly, and that a ticket linked from a PR merged into a non-default branch stays open until someone closes it.

## DR3: Tracker specifics live in a synced shared reference, selected by host at runtime

Context: Several skills need tracker knowledge — command syntax, ticket URL and identifier forms, the marker-label convention, and GitHub's closing-keyword and default-branch semantics. The seed requires that vocabulary and boundaries be generic from the start so a second tracker can be added later without reshaping the skills, while `suite/AGENTS.md` forbids any skill from reading another skill's `references/` folder and sets a high bar for extracting a new primitive.

Decision: Tracker knowledge lives in canonical shared references under `shared/references/trackers/`, starting with a single `github.md`, declared in `shared/manifest.yaml` for every tracker-touching skill and mirrored into each one by `scripts/sync-shared-references.mjs`. The generated copies are never hand-edited; the canonical source is edited and the sync script re-run. Each skill body speaks only of *tickets* and carries the tracker flow it needs itself; no tracker-I/O primitive is created, and no skill delegates tracker access to another skill. Skill bodies do not hardcode the reference filename: they resolve which tracker applies from the ticket URL's host — or from the git remote's host when creating a fresh ticket — and then read the matching `references/trackers/<tracker>.md`. Adding a second tracker is therefore one new canonical file plus manifest entries, with no change to any skill body. Because every tracker-writing skill is a user-invoked entry point, its authorization is the user's deliberate invocation plus an explicit confirmation before the mutation (DR1); each such body states that confirmation requirement itself.

Rationale: The three tracker capabilities need different operations — create, read and list, comment and close — rather than one reused mechanism, so a primitive per operation would have a single caller each and fail the suite's extraction bar. The shared-reference idiom already exists and is already used for recipes and formats, so this adds no new architecture, and the mirrored copies are generated artifacts rather than maintained duplicates, leaving canonical knowledge in one authored place either way. It also keeps `finish` self-contained, which matters because DR2 requires its tracker step to be silently absent when tracker context is missing — a separately installable primitive would instead turn a partial installation into a broken invocation. The trade-off is that each skill body carries its own tracker flow, so consistency across the tracker skills rests on authoring discipline rather than on a single shared implementation.

## DR4: Opening a thread from a ticket extends `/open-thread`, and the marker label never gates it

Context: The thread needed a path from a tracker ticket to a thread. `/open-thread` already accepts an external ticket reference and states that the genesis narrative is drawn from the ticket's title and body, but it has no means of fetching a ticket — only a fallback asking the user to paste the content. Suite composition permits an entry point to invoke a primitive but never another entry point, and `/open-thread` composes the seed fields by judgment before delegating the single write to `/allocate-thread`.

Decision: Opening a thread from a ticket extends `/open-thread`; no sibling skill is added for it. `/open-thread` gains the ability to read the referenced ticket through the tracker reference resolved per DR3, derives the thread slug from the ticket, and keeps its existing paste fallback as the degradation path when tracker tooling or credentials are unavailable. It never inspects whether a ticket carries the marker label, and it offers no ticket-specific mode: any ticket reference, marked or unmarked, is valid input. The marker label serves only as a discovery aid when listing candidate tickets, and the affordance that lists marked tickets for selection is deliberately not part of `/open-thread`, which receives a ticket reference rather than searching for one.

Rationale: A sibling skill could not invoke `/open-thread` under the suite's one-way composition rule, so it would have to call `/allocate-thread` directly and duplicate the seed-composition judgment that is `/open-thread`'s whole purpose, creating a second place for that judgment to drift. Reading a ticket is not a mutation, so the extension stays within the passivity default and needs no new authorization beyond DR1. The trade-off is that a previously tracker-agnostic skill acquires tracker-reading behavior and a shared tracker reference.

## DR5: A ticket-opened thread's slug describes the subject and omits the ticket identifier

Context: `/open-thread` derives a thread slug when opening a thread from a ticket (DR4), and the thread folder is named `<YYMMDDHHMMSSZ-slug>`. The slug could describe the subject the way every existing slug does, or additionally carry the ticket's number so the tracker origin is visible in the folder name. The ticket→thread link already exists independently of the folder name, because `seed.md` carries `External: <url>`.

Decision: The slug is a short kebab-case description of the subject, derived from the ticket's title, exactly as it is for a thread opened from prose — a ticket numbered 123 and titled "Rate limiter drops burst traffic" yields a folder such as `260726164032Z-rate-limit-fix`. The ticket identifier appears nowhere in the folder name, so a ticket-opened thread is structurally indistinguishable from a prose-opened one. Any operation that needs to find the thread belonging to a ticket matches the `External:` value across thread seeds, and must normalize ticket references before comparing them: a full issue URL, the same URL with a trailing slash, and a short `#123` form all denote the same ticket.

Rationale: `External:` is already the authoritative and unambiguous link, so putting the number in the folder name would be a second, weaker encoding of the same fact, and a bare number is ambiguous as soon as more than one repository or tracker is in play while a URL never is. Embedding a tracker identifier in the path also drifts toward the stable-ID-in-path scheme `docs/thread-model.md` explicitly disclaims. The trade-off is that tracker origin is not visible from a directory listing, and that URL normalization becomes load-bearing for every ticket→thread lookup rather than merely advisable.

## DR6: No sweep skill is built for checking whether marked tickets were already implemented

Context: The seed named three capabilities, the third being a way to check whether marker-labelled tickets have already been implemented by a thread so they can be closed, and left open whether implementation-checking belongs in a skill at all. Such a skill would have been the suite's first thread-less capability, scanning the whole `docs/threads/` tree including the archive and cross-referencing marked tickets against thread seeds.

Decision: No sweep, survey, or listing skill is built in this thread. Closure is handled solely by `finish`'s disposition-aware step (DR2) for threads delivered through `finish`. Tickets left open outside that path — work delivered without `finish`, and the non-default-branch case DR2 leaves open by design — are closed by the user directly, with no skill mediating it. The affordance for discovering which marked tickets could be picked up is likewise not a skill: listing the marker label through ordinary tracker tooling answers it, and any result is handed to `/open-thread` as an ordinary ticket reference. Should a sweep prove necessary later, it is authored then, against the concrete cases that actually accumulated.

Rationale: The discovery half needs no logic beyond a single label-filtered ticket listing, so a skill would wrap a one-line query. The closure half would have had to infer delivery from a proxy — an `implementation-report.md` existing, or the thread being archived — and an archived thread may have been abandoned rather than completed, so the inference would be unreliable in exactly the cases a sweep exists to catch. Designing that heuristic before real orphaned tickets exist risks encoding the wrong rule; deferring costs little because such a skill is read-mostly and defines no format or contract that other skills would depend on. The trade-off is accepted: until then, a ticket whose thread shipped outside `finish` stays open until someone notices it by hand.

## DR7: `/open-thread` warns, without blocking, when a thread already exists for the ticket

Context: DR5 requires ticket references to be normalized for any ticket→thread lookup, but after DR6 removed the sweep, no operation performed that lookup any more — `finish` reads `External:` directly out of the seed, and `/open-thread` creates a new thread rather than searching for one. The remaining candidate consumer was a guard against opening a second thread for a ticket that already has one, which happens silently when a teammate has already started the work or when context was lost between sessions.

Decision: Before delegating to `/allocate-thread`, `/open-thread` searches thread seeds under `docs/threads/` — including the archive — for an `External:` value matching the supplied ticket, comparing normalized references per DR5. When a match exists it names the matching thread folder and asks whether to continue. The check never blocks: a confirmed continue proceeds through the ordinary creation path unchanged, because a second thread on the same ticket is sometimes legitimate follow-up or superseding work. This guard is the consumer that keeps DR5's normalization requirement live.

Rationale: The failure it prevents is silent and expensive — duplicate threads on one ticket, typically discovered once both carry artifacts, with no clean way to merge them — while the guard itself is a search inside a skill already being modified. That is the inverse of the trade-off rejected in DR6, where a whole new skill resting on an unreliable completion proxy would have addressed a failure that is visible and trivial to fix by hand. The warning is deliberately advisory because the method's conventions guide rather than govern, so blocking would contradict the stance stated in `docs/README.md`.

## DR8: `open-ticket` exists as an entry point in `capture-discussion/`, justified by a seed-grade body contract

Context: The thread needed to settle whether creating a tracker ticket from a rough idea deserves a dedicated skill at all, given that an agent can be asked free-form to file an issue. What distinguishes the skill is a two-sided contract with `/open-thread`: `/open-thread` lifts a ticket's title and body into the seed's genesis narrative, so a ticket whose body already is a genesis narrative is thread-ready, whereas a free-form request typically yields a pseudo-spec carrying acceptance criteria, a task breakdown, and a proposed design, which then has to be reverse-engineered back into intent.

Decision: A user-invoked entry point named `open-ticket` is added at `skills/capture-discussion/open-ticket/`, pairing with `open-thread` in both name and group. Its shape:

- It takes a rough idea in prose and composes a **title** — a human-readable one-liner in the same register as a thread's `Title`, never in the kebab-case form of a thread slug — and a **body written as a genesis narrative**: the restrained, need-shaped account of what triggered the work and its intended outcome, carrying no acceptance criteria, no task breakdown, and no proposed design.
- It resolves the target repository from the git remote, asking when that is ambiguous rather than guessing, and reads the tracker reference resolved per DR3.
- It shows the composed title, body, and label for exactly one round of corrections, then creates the ticket. That confirmation is the explicit authorization DR1 requires.
- It writes nothing to disk — no thread exists at creation time, and none is created.
- It reports the created ticket's URL and stops. It suggests no next action, and in particular does not point the user at `/open-thread`: filing a ticket is an act of deliberately deferring the work, so proposing to start it immediately works against the purpose of the invocation.

Rationale: The value the skill encodes is a writing discipline that makes the tracker entry consumable by `/open-thread` without reinterpretation, and encoding disciplines is what the suite's skills do — the skill is comparable in weight to `open-thread` itself. It lives in `capture-discussion/` rather than a new `tracker/` group because the tracker is a substrate several groups touch, not a capability group: the other tracker-touching changes belong to `open-thread` in this same group and to `finish` in `finish-navigate/`, so a `tracker/` folder would hold one third of the capability and mislead. Chaining directly into thread creation is impossible in any case, since suite composition forbids an entry point invoking another entry point. The trade-off is a skill whose worth rests on the body contract rather than on a mechanism; without that contract the skill would not be justified.

## DR9: The marker label is `antmay`, applied by default with an opt-out

Context: The seed proposed optionally applying a marker label so Antmay-managed tickets are identifiable, with `antmay` and `thread` as candidate names. After DR6 dropped the sweep skill, no automated consumer of the label remains: `/open-thread` never inspects it (DR4), and `finish` works from the seed's `External:` value rather than from labels, so the label's only present use is a manual label-filtered ticket listing.

Decision: The marker label is named `antmay`. `open-ticket` applies it by default, and the user may opt out during the single confirmation pass. When the label does not yet exist in the target repository, its creation is named explicitly in that confirmation pass rather than performed silently. The label's meaning is "this ticket's body is a seed-grade genesis narrative", which is what makes it thread-ready; it does not mean the ticket is owned or managed by any automation, and no skill branches its behavior on the label's presence.

Rationale: `thread` is far too generic a label to introduce into a real repository, where it collides with unrelated threading concepts, while `antmay` is self-identifying and unambiguous. Applying the label by default is worth its near-zero cost even with no automated consumer, because labels are only useful retroactively: a sweep built later (DR6) could only scan tickets already labelled, and the label cannot be backfilled onto unlabelled tickets without reviewing them by hand. Applying it now therefore preserves optionality rather than building speculatively. The trade-off is a convention that currently earns its keep only through manual filtering.

## DR10: `open-ticket` composes before it writes, and hands the composed text over when the write is impossible

Scope: `open-ticket`

Context: Degradation when tracker tooling or credentials are unavailable is settled for the other two paths — `finish`'s tracker step is silently absent (DR2) and `/open-thread` falls back to asking the user to paste the ticket's title and body (DR4). `open-ticket` is the only path whose entire purpose is a tracker write, so it cannot simply proceed without one, and per DR8 the value it adds is the composition rather than the API call.

Decision: `open-ticket` performs its work in a fixed order — compose the title and body, confirm them with the user, and only then attempt the tracker write. When tooling or credentials turn out to be unavailable, it prints the composed title and body in chat and tells the user to file the ticket manually. It never probes for tracker availability before composing. This degradation is handled conversationally; `open-ticket` emits no terminal outcome, consistent with `open-thread` and `finish`, which are likewise interactive and emit none.

Rationale: Ordering composition before the availability check means an unavailable tracker costs only the API call, leaving the user with the seed-grade text that is the skill's actual contribution; probing first would refuse the invocation before producing anything useful. It is the mirror of `/open-thread`'s paste fallback — there the human supplies text the tool cannot fetch, here the tool supplies text the human must post. The trade-off is that the user may complete a confirmation pass for a ticket that is never filed automatically.
