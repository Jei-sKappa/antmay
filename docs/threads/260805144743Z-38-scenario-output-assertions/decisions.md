# Required-Output Assertions for the Demo Scenario Catalog Decision Log

## DR1: One piped child path, with color forced, for every scenario invocation

Context: A scenario's required-output assertion needs the driver to hold the child's bytes, but `scripts/demo.mjs` spawns every invocation with `stdio: "inherit"` and therefore sees nothing. Piping the child makes `process.stdout.isTTY` false, and `isTTY` has exactly one consumer in the CLI — `useColor = options.isTTY && !options.noColor` in `src/display/format.ts` — so a piped child renders identically to an inherited one apart from color codes. Reviewing the colored stream is how a demo run is actually read, and several scenarios exist for renderings that carry meaning in color. A pty wrapper is not available as a way to keep both: macOS `script` requires a TTY on its own stdin and fails with `tcgetattr/ioctl` without one, which is precisely the case when a batch runner spawns the demo with pipes.

Decision: The driver runs every invocation one way: the child's stdout and stderr are piped, each chunk is written straight through to the driver's own stdout as it arrives so the stream stays live, and the accumulated text is what required-output markers are matched against after ANSI escapes are stripped. The child environment carries a switch that makes the display emit color even though its stdout is not a TTY, so the rendering a developer reviews and the rendering the driver asserts are the same bytes. There is no separate colored-but-unasserted mode: a scenario run manually checks its markers exactly as a batch run does. Resolving that switch is a production change to how `DisplayOptions` is built in `src/program.ts` and the three command modules, and it is in scope for this work.

Rationale: The assertions exist as a net that fails loudly before the two refactors that follow this work land, and a marker checked only in a mode that is not used while writing the scenario cannot be confirmed correct when it is written and rots silently afterward. One child path also keeps a single meaning for the driver's `[PASS]` line. The trade-off accepted is that this work no longer changes zero production code, so its sequencing rests on the change being confined to the one place `isTTY` is consumed and exercised by the scenarios built alongside it, rather than on being risk-free by construction. Merging two pipes makes cross-stream ordering approximate, which is still stricter than the present trace transcripts, where all of stderr is concatenated after all of stdout.

## DR2: Color is forced through the standard `FORCE_COLOR`, and `NO_COLOR` outranks it

Scope: color resolution feeding `DisplayOptions`

Context: DR1 requires a switch that makes the display emit color when stdout is not a terminal. The CLI emits only basic ANSI — eight colors plus bold and dim — so no color-level vocabulary is needed, and it already honors `NO_COLOR` by treating any non-empty value as off. The alternative considered was a developer-only variable on the pattern of `ANTMAY_TEST_ENABLE_SCRIPTED_HARNESS`; `cli/AGENTS.md` holds the demo to exercising the same path a user would rather than reaching for a demo-only hook, which is what decided against it.

Decision: The CLI honors the standard `FORCE_COLOR` environment variable: a value that is non-empty and not `0` turns color on regardless of whether stdout is a terminal, and `0` leaves it off. `NO_COLOR` takes precedence when both are set, so an explicit off never loses to an on switch exported by a wrapper. The demo driver exports `FORCE_COLOR` into every child environment unconditionally, and the driver's own `--no-color` keeps working by exporting `NO_COLOR` alongside it. No color-level values are interpreted, and no new command-line flag is added.

Rationale: Using the conventional name makes the piped-and-colored rendering a path a real user reaches by piping the executor into a pager or a CI log, so the scenarios assert a rendering that exists outside the demo; a test-only gate would have made the asserted rendering unreachable for users, which undercuts the reason to assert it. The precedence rule is the one that keeps an explicit user choice authoritative and simultaneously lets the driver export the on switch without conditioning it on its own flags.

## DR3: A sibling script owns the whole-catalog run; `demo.mjs` stays single-scenario

Scope: `cli/scripts/`

Context: The assertions are meant to fail loudly across the catalog before the two refactors that follow this work land, but `demo.mjs` runs exactly one scenario and the only existing whole-catalog runner is `npm run trace`, whose scenario pass/fail reporting is incidental to its purpose as a call-tracing diagnostic. `trace.mjs` already establishes the shape a batch runner takes here: build the CLI once, then spawn `demo.mjs --scenario <id> --cli-binary <built>` per scenario with piped stdio.

Decision: Whole-catalog running belongs to a new sibling script under `scripts/`, not to a mode inside `demo.mjs`. It builds the CLI once, runs every scenario in sequence through the existing `--cli-binary` seam, and prints one progress line per scenario. A failing scenario's captured transcript is printed in full so the failure is diagnosable without re-running it; a passing scenario prints nothing beyond its line. The whole catalog runs before anything is reported rather than stopping at the first failure, and the script exits non-zero when any scenario failed. It runs scenarios serially and prints its own wall clock. It does not pass `--no-color`, so batch and manual runs assert byte-identical output. `demo.mjs` gains no batch mode, no reporting, and no second display path. This script does not join `npm run check` as part of this work.

Rationale: Keeping the batch concern in its own file preserves `demo.mjs` as one scenario, one fixture, one live stream, and reuses a pattern already proven in this directory. Because the batch runner captures the demo's stdout, the pass-through required by DR1 needs no batch-specific mode — the parent decides what a human sees. Reporting the full catalog rather than the first failure is what makes the result usable after a refactor touches many renderings at once. Serial execution with a printed wall clock exists because the open question of whether this suite joins the check gate is to be settled by measurement, and the measurement is this script's byproduct; the fixtures are already isolated per scenario, so concurrency remains available once that number has been read.

## DR4: What a required-output marker is

Scope: `cli/scripts/`

Context: Each scenario invocation needs a declaration of the output that identifies the rendering it exists to show, checked alongside its expected exit code. Three facts constrain the shape. The banner vocabulary is small and heavily shared — across the current 32 transcripts `BLOCKED` appears in 24, `Continue` in 19, `WAITING FOR USER` in 4 — so no single banner identifies one scenario's rendering. Some renderings are defined by repetition rather than presence: the heartbeat scenario's subject is the `· still working — elapsed …` line recurring. And the values that vary between runs, chiefly the run id in the pause's `Resume:` line, are already available to a scenario through the driver's `ctx`, which supplies `runId()` to the `(ctx) => …` functions steps already accept.

Decision: A marker is a plain string, or a function of `ctx` returning a string, matched by substring containment against the invocation's accumulated output with ANSI escapes stripped. A marker may instead take the form `{ text, atLeast: n }` to require at least `n` occurrences. Markers attach to the invocation step next to `expectExit`, so a multi-invocation scenario declares per invocation what that invocation must show. A step fails when its exit code does not match or when any marker is missing, and the driver names the missing markers. What identifies a rendering is the conjunction of a scenario's markers, not any one of them, so a marker set pairs the banner with the line that distinguishes the scenario from its neighbours. Regular expressions are not accepted, marker order is never asserted, and there is no "must not appear" form.

Rationale: Every marker actually needed is a literal, and the varying run id resolved from `ctx` asserts the correct id rather than any id, which is strictly stronger than a wildcard; excluding regexes also removes the on-ramp to the transcript-snapshot over-specification this work rejects, since a marker can then only ever claim that a string appears. Order is unasserted because DR1 merges two pipes, making cross-stream sequence approximate, and an assertion that is only nearly deterministic is worse than one that is deterministic and weaker. Negative markers are omitted because the failure they would guard — an invocation that fails preflight instead of reaching its subject while still matching its declared exit code — is already caught by the required markers, a preflight refusal being unable to contain the subject's banner.

## DR5: The thread delivers the mechanism, the backfill, and full rendering coverage

Context: The work divides into three separable bodies: the marker mechanism with markers filled into all 32 existing scenarios; the nine pause renderings in `src/execution/pause.ts` that no scenario reaches (`queueBlocked`, `queueUnreadable`, `prerequisiteUninspectable`, `contractUninspectable`, `refreshPendingBundles`, `refreshQueueUnreadableHoldingDone`, `refreshPromiseUninspectable`, `refreshPromiseUnmet`, `refreshBoundaryRefused`); and the two renderings tracked as issue #37, the at-rest interrupted run summary and the `warning:` line. `cli/AGENTS.md` states as a contract that every distinct terminal rendering has a demo scenario, and that contract is currently false.

Decision: All three bodies are in scope for this thread, and issue #37 is closed by it. Two things stay out: whether the scenario suite joins `npm run check`, and any reduction of `src/display/terminal.test.ts`. The thread delivers in sequence rather than atomically — the mechanism and the 32-scenario backfill land first, and the previously unreached renderings follow — since a marker cannot be written before markers exist, and the mechanical low-risk part should not wait on the per-rendering judgments.

Rationale: Deferring the unreached renderings would knowingly leave a documented module contract false, and the thread that discovered the violation is the one that should end it. Internal sequencing removes what would otherwise be the cost of this scope: the safety net that the two following refactors depend on arrives with the backfill, not after nine independent judgment calls are settled. The coverage claim rests on the call-trace report being a trustworthy inventory, which holds at the level it is used: every renderer in `src/display/` and every builder in `pause.ts` is a top-level function declaration, so none of them can hide in the report's uninstrumented list. An unexercised branch inside a function that is called remains invisible to that report, which is a limit of the inventory rather than of this scope.

## DR6: Reaching an unreached rendering is the default; consolidation requires three coincidences

Scope: the previously unreached renderings in `src/execution/pause.ts`

Context: Each rendering with no scenario can be resolved either by adding a scenario that reaches it or by consolidating it into a neighbour, and `cli/AGENTS.md` already supplies the distinctness test: outputs differing only in interpolated values may share a scenario, while outputs differing in sections, ordering, causal explanations, corrections, wrapping-sensitive content, or interaction paths require separate ones. Consolidation is not a scenario-file edit — it deletes or merges a builder in `pause.ts`, whose waiting objects are what checkpoints persist and what `waitingEquals` compares field by field. Recoveries do not correspond one-to-one with renderings: `queueUnreadable` and `queueBlocked` both carry `retry-stage` while explaining different things, and `contractUninspectable` and `contractViolated` both carry `recheck-stage-contract`.

Decision: Adding a scenario is the default resolution. Consolidating a rendering away requires the rendered text, the ordered diagnostic reasons, and the recovery all to coincide with the neighbour it would merge into, judged on actual rendered output rather than on similarity between builders. Two of the three is not sufficient. Where text coincides but the recovery differs, the finding is a rendering defect rather than a consolidation opportunity: the screen is failing to tell a reader that a different resume is available, and the resolution is to make the rendering distinguishable and give it a scenario, never to merge two resume behaviors behind one screen.

Rationale: Every unreached pause rendering inspected differs from its nearest reached neighbour on a ground the existing test already treats as requiring its own scenario — a different causal message for `prerequisiteUninspectable` against `prerequisiteUnmet` and for `contractUninspectable` against `contractViolated`, and a resume-only interaction path for the whole refresh family — so the expectation is a scenario for each rather than a mix, five of them multi-invocation. The three-coincidence bar exists because consolidation is a production change, and the merge that is most tempting on a screen-similarity basis is precisely the one that would erase a distinction between resume behaviors. `refreshPromiseUnmet` further branches its detail line on worktree cleanliness, so the count of renderings to reach exceeds the count of unreached builders.

## DR7: Every invocation must declare at least one marker

Scope: `cli/scripts/demo/steps.mjs`

Context: With markers attached to invocation steps, the question is whether a step may omit them. Optional markers would let the backfill across the existing scenarios be silently partial and let every scenario written afterwards skip them while still reporting a pass — the same class of false pass this work exists to close, moved out of the driver and into the declarations. Every invocation in the catalog produces output, including those that exist only to establish state for a later step, so there is no invocation for which naming a marker is impossible.

Decision: `run()`, `resume()`, and `list()` each require at least one marker and throw when none is supplied or the list is empty, in the same way they already throw on a non-integer `expectExit`. A setup-only invocation is not exempt. An unannotated scenario therefore fails at load rather than passing review.

Rationale: Making the declaration mandatory at the point of construction is what prevents the mechanism from decaying by omission, and the step factories already establish that a malformed step is a load-time error. An exemption for setup-only invocations was rejected because qualifying for it is a judgement the driver cannot check, which would make the exemption the new hole; naming the rendering a setup step passes through costs little and states what that step is actually doing.

## DR8: Two scenarios may not declare the same marker set

Scope: `cli/scripts/demo.mjs`

Context: DR7 prevents markers from being omitted but not from being degenerate. Since a banner like `BLOCKED` appears in most transcripts, many scenarios could each declare only that one string, every one of them would then pass on any other's output, and the suite would report green while asserting nothing about which rendering was reached. The driver already imports every scenario module on every run, in `loadScenarios`, so the whole catalog's declarations are available even when one scenario was selected.

Decision: The driver validates the catalog it loads: it collects each scenario's plain-string markers across all of that scenario's invocations as one set, and fails when two scenarios' sets are identical. The comparison unit is the scenario rather than the individual invocation, because one scenario's setup invocation may legitimately reach the rendering another scenario exists to show. Only identity fails; one set being a subset of another is permitted, since a plain rendering and an elaborated neighbour can stand in exactly that relation. Markers supplied as functions of `ctx` do not participate in the comparison. The check runs on every invocation of the driver, including a single-scenario manual run, so a degenerate declaration surfaces while it is being written.

Rationale: Identical marker sets always mean at least one of the two scenarios does not pin its own rendering, which makes it a defect rather than a style question, and the moment the temptation exists is the backfill — precisely when a check that only ran in a batch would be least likely to fire. Excluding `ctx` functions only ever weakens the check, and restricting failure to exact identity avoids forcing a distinction between renderings that genuinely differ by addition. The trade-off accepted is that a malformed catalog stops a run of an unrelated scenario, which matches how a malformed step already behaves.
