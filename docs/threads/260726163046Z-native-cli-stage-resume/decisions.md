# Decisions — Expose provider session IDs so AFK stages can be continued in the native Codex/Claude Code CLIs

## DR1: Capture the provider session ID from the live raw stream, with Sandcastle's result as the authority

Scope: `cli/src/harness/sandcastle.ts`

Context: Antmay must obtain the provider session ID for a stage attempt so it can be persisted and shown to a human. Sandcastle exposes the ID on `RunResult.iterations[n].sessionId`, but a `RunResult` exists only when `run()` resolves: on rejection — idle timeout, provider error, abort — there is no result object at all, and only `StructuredOutputError` carries an ID (a path Antmay never reaches, since it passes no `output`). Reading the result alone would therefore leave the ID absent for exactly the opaque attempts a human most wants to reopen. Sandcastle separately delivers every provider stdout line verbatim to the `onAgentStreamEvent` callback Antmay already wires, as `{ type: "raw", line, iteration, timestamp }`, and the provider's init line carrying the ID arrives at the start of an attempt — before any timeout or interruption.

Decision: The adapter watches the raw stream for the provider's session-identity line and holds the first match for the lifetime of the attempt: Codex `{ "type": "thread.started", "thread_id": … }` and Claude Code `{ "type": "system", "subtype": "init", "session_id": … }`, each guarded against non-JSON lines. The captured ID may be attached to any outcome, failed ones included. On the resolve path, where both sources exist, `result.iterations.at(-1)?.sessionId` takes precedence and the sniffed value is the fallback used only when Sandcastle's is absent; the sniff is therefore a supplement to Sandcastle's own extraction rather than a replacement for it. When both values are present and disagree, or Sandcastle produced an ID and the raw-stream match did not, the adapter emits exactly one warning through the display.

Rationale: The motivating case — a `spec` stage reporting DONE with pending decisions — is covered by the result field alone, so reading only the result is defensible on YAGNI grounds. It was rejected because an idle-timed-out or interrupted attempt is precisely the state whose conversation a human needs to inspect, and that path would record nothing. The trade-off accepted is that `cli/src/harness/sandcastle.ts` now knows two provider wire shapes, duplicating parsing Sandcastle performs internally; this is contained in the one module whose purpose is already to know about Codex and Claude Code. Keeping Sandcastle authoritative on the resolve path bounds the damage from that duplication: a Sandcastle mapping change degrades to an unnecessary fallback rather than to a wrong ID, and the disagreement warning makes the divergence visible on real runs, which no offline test can observe.

## DR2: Guard the raw-stream matcher with a CI fixture-agreement test and an opt-in real-provider verifier

Scope: `cli/src/harness/`

Context: DR1 has the adapter match two provider wire shapes itself, which can silently stop finding a session ID in two independent ways. Sandcastle may change which shape it maps to a session ID, diverging from Antmay's copy; or a provider may rename the field, in which case Antmay and Sandcastle both stop finding it and still agree on any fixture line — no offline test can detect that, because the fixture encodes the same assumption. Sandcastle's `parseStreamLine(line)` is part of its public `AgentProvider` interface and is callable from a test with no provider binary, credentials, or network. Antmay's `tsup` build has the single entry `src/main.ts`, so `dist/` exports nothing importable and a dependency-free script under `scripts/` cannot reach the adapter; `vitest` is the only tool configured here that loads TypeScript source, and its `include` of `src/**/*.test.ts` excludes any other filename from the default run.

Decision: Two guards, aimed at the two failure modes.

For Sandcastle-side drift, a case in `cli/src/harness/sandcastle.test.ts` asserts one fixture line per provider twice over: that Antmay's matcher extracts the expected ID, and that `codex(model).parseStreamLine(line)` / `claudeCode(model).parseStreamLine(line)` yields a `session_id` event carrying the same value. It runs inside `npm run check`.

For provider-side drift, `cli/src/harness/session-id.manual.ts` run by a new `npm run verify:session` (`vitest run --include 'src/**/*.manual.ts'`), which needs no `vitest.config.ts` change and is never collected by `npm test`. It holds two independent cases, one per provider, each invoking `createSandcastleInvoker()` in a throwaway temporary directory with a trivial prompt, `dangerouslySkipPermissions: true`, and a short idle timeout. Each asserts that an ID was captured and that the two sources agree, then prints the native resume command for a human to paste. Missing credentials fail the case rather than skipping it. The manual smoke checklist in `cli/README.md` gains a pointer to this command.

Rationale: The split follows the detectability of each failure: one is free and belongs in CI, the other costs real model calls and cannot run unattended, so it is opt-in and deliberately loud when run. Asserting the last mile — that `codex resume <id>` genuinely reopens the conversation — needs an interactive terminal and stays a human step. A standalone `.mjs` script under `scripts/` was rejected because it could only drive the built CLI as a subprocess, requiring a thread, settings, a clean repository, and a lock to read back one field; a vitest file reaches the adapter directly. A case that skips on absent credentials was rejected as the most likely way for this guard to rot unnoticed.

## DR3: Warn about the clean-worktree precondition in the renderer, not the checkpoint

Scope: `cli/src/display/`

Context: `antmay afk resume` requires a clean worktree for every waiting kind except `git-policy-violation` and `commit-error`, and a DONE-with-pending-bundle pause is governed by `pending-queues`, so it requires one. A human who accepts the invitation to continue the stage's conversation in the native CLI will typically leave the worktree dirty — `resolve-pending-decisions` appends to `decisions.md`, which the stage's own boundary commit had already committed, and that skill issues no commit of its own — so resuming afterwards fails with exit `1` until those changes are committed or reverted. The pause taken on a DONE-finalized stage carries no `nextAction`, so its block currently says nothing about uncommitted changes, unlike a non-DONE pause which carries the unvalidated-changes note.

Decision: Wherever a pause block prints the native resume command, the same block also states that the worktree must be clean before `antmay afk resume` — commit or revert whatever the conversation changed. This lives entirely in the terminal renderer, composed from information it already receives; no `nextAction` is added to the DONE-finalized pause path and no new field enters the checkpoint. `resume` keeps its clean-worktree rule unchanged.

Rationale: Advertising a native conversation without naming its exit condition would let a human invest a whole conversation before discovering the constraint, and the recovery they need — committing before leaving the session — is knowledge they must have beforehand for it to help. Putting the sentence in the checkpoint's `nextAction` was rejected on two counts: it writes interface prose into a durable state document, and on that path `nextAction` means something narrower and factually different — that an attempt's changes never passed the terminal-outcome gate — which is untrue of a human's deliberate edits. Relaxing the clean-worktree rule for this case was rejected outright: `resume` cannot distinguish a human's deliberate edits from an agent's unvalidated ones, and that distinction is the rule's entire basis.

## DR4: Persist the session as an optional self-contained `agentSession` on every attempt that captured one

Scope: `cli/src/state/checkpoint.ts`

Context: The captured provider session ID must become durable run state. The checkpoint is at `schemaVersion: 0`, and `cli/AGENTS.md` fixes it there while the format is unstable, forbidding migrations and compatibility shims and accepting that existing run directories may become unreadable — so no version bump is in question, and the handoff's premise of a `schemaVersion: 1` document needing a `2` is stale. That same policy forbids weakening a field to optional merely so previously written state validates. The runner settles every attempt by replacing its last record on four paths, one of which — the pre-launch interruption — settles an attempt that never invoked the harness and so can carry no session. A provider may also emit no session line at all.

Decision: `AttemptRecord` gains `agentSession?: { harness: HarnessId; id: string }`, validated in `validateAttempt` as an optional object whose `harness` is a known harness id and whose `id` is a non-empty string. The field is optional because its absence is a real state, not a compatibility concession. It is written on every attempt for which an ID was captured regardless of that attempt's result — `done`, `waiting`, and `interrupted` alike — rather than on a subset selected by outcome. `harness` is stored alongside the ID even though it is derivable from the snapshotted stage profile, so any reader can compose the native resume command from the attempt record alone. The value is attached only on the settle-time write the runner already performs, which gives the interruption helper an optional session parameter supplied at its post-abort call site and absent at its pre-launch one.

Rationale: Uniform capture is cheaper to implement and to explain than an outcome-conditioned policy, and reopening the conversation of a stage that already advanced is a real need — asking why a finished stage wrote what it did — not only a recovery path. Duplicating `harness` trades a derivable byte for a self-contained record and removes a reach through `stageIndex` into the stages array; the two values cannot diverge, since both come from one resolved profile within a single attempt. Persisting the ID mid-attempt the moment it arrives was rejected: it costs an extra fsync per attempt to protect a state the CLI already reports as unverified, and the raw provider line remains in the attempt log either way.

## DR5: The pause block prints the paste-ready native command for the attempt that just ended

Scope: `cli/src/display/`

Context: Every pause a human acts on is rendered by one call — the DONE-with-pending pause, BLOCKED, REFUSED, a malformed outcome, an idle timeout, a harness error, a boundary violation, and a mid-attempt signal all route through the runner's pause rendering. The block's action section is a sequence of key/value lines whose stated purpose is that the last thing on screen is the thing to type next, and it already prints the literal `antmay afk resume <run-id>`. The two providers spell continuation differently: `codex resume <id>` and `claude --resume <id>`. The session ID cannot be shown when an attempt starts, because it arrives on the stream seconds later.

Decision: When the attempt a pause is about carries an `agentSession`, the action section gains one line whose value is the exact native command for that harness — `codex resume <id>` or `claude --resume <id>` — under a generic key alongside `Log` and `Resume`. No separate harness-name label is rendered: the harness is legible from the binary name in the command itself. The session shown is always the one belonging to the attempt this pause is about, so no attempt-selection rule applies. A pause taken before any attempt was allocated, such as the pre-attempt queue gate, shows no such line, exactly as it already shows no log path. Antmay treats the ID as an opaque reference and never inspects `~/.codex/sessions/` or `~/.claude/projects/` to confirm a transcript still exists.

Rationale: A paste-ready line matches the action section's established idiom and removes the one detail a human is least likely to remember, which is each provider's differing flag shape. Printing the ID with only a harness name was considered, on the grounds that a user with shell aliases or habitual flags has their own way to invoke a provider; it was rejected because a printed command is a suggestion an alias user adapts in a second, whereas an identity alone taxes every user with recomposing the line. Verifying transcript existence before printing was rejected because it would couple Antmay to two provider-private storage layouts to buy a slightly better error than the provider CLI already gives for an unknown ID.

## DR6: `antmay afk list` shows the run's most recent session; a per-attempt session view is deferred

Scope: `cli/src/commands/list.ts`

Context: A session belongs to an attempt, but a `list` row describes a run, and a run accumulates one session per attempt across its stages — so a single column can only show one of several. The retrieval floor is already met without any `list` change: DR4 puts every captured session in `state.json`, and each attempt log retains the provider's raw init line. A row's stage position and the latest attempt can disagree, because the cursor may have advanced past the stage that last attempted; for a run waiting on a human, however, the latest attempt is always the current stage's, since a pause happens on the stage the cursor sits at. Disagreement is therefore confined to `ready` runs, which persist only between two checkpoint writes, and to completed runs, where nothing is blocked.

Decision: `renderRow` gains one column showing the session of the most recent attempt that carries one, rendered as `<harness>/<session-id>` to reuse the row's existing `harness/model` idiom, and omitted for a run that captured none. `cli/README.md` states that selection rule. A complete per-attempt view — a way to see every session a run produced, which was the substance of a rejected `antmay afk session` subcommand — is deferred to a future thread, to be designed together with the wider rework of this command's output.

Rationale: The column is a few lines plus a test, is correct precisely in the state where a human hunts for a conversation, and forecloses nothing: the pre-release notice lets a later redesign replace it outright. Deferring the column as well was considered, since the underlying multi-session presentation problem is genuinely unsettled; it was rejected because the scenario this whole feature exists for is a human who walked away, and after their scrollback is gone that option leaves them opening `state.json` by hand. Aiming the deferral at the complete surface instead keeps this thread unblocked without reducing retrieval to a manual file read.

## DR7: Reshape `AttemptOutcome` so the session and its capture diagnostic sit beside the result

Scope: `cli/src/harness/types.ts`

Context: DR1 requires the captured session to be attachable to a failed attempt as well as a completed one, and calls for one warning when Antmay's raw-stream matcher disagrees with Sandcastle's own extraction. Neither is expressible today: `AttemptOutcome` is a two-variant union discriminated by `kind`, and the only callback an adapter receives is `onEvent`, whose `HarnessEvent` union carries agent text and tool calls for live display. The `Display` is held by the runner, not by any adapter. DR1 attributes the warning's emission to the adapter; this record locates it in the runner, with the adapter supplying its content.

Decision: `AttemptOutcome` becomes an object with three members: an optional `session?: { id: string }`, an optional `sessionWarning?: string`, and a `result` holding the existing `completed` / `failed` union unchanged. Hoisting `session` out of the union is what states that a session is independent of how the attempt ended. `sessionWarning` is prose written by the adapter and forwarded verbatim by the runner to `display.warn`; it is a sibling of `session` rather than a field inside it, because it describes the health of Antmay's capture mechanism and not the identity of the conversation, and it is never persisted. No new callback and no new `HarnessEvent` variant is introduced. The `harness` half of the persisted `agentSession` is not carried on the outcome: the runner composes it from the stage profile it already holds. Every consumer moves with the shape — the Sandcastle invoker, the scripted invoker, the fake harness in `cli/src/test-helpers/`, and the runner's classification, where `outcome.kind` becomes `outcome.result.kind`.

Rationale: A diagnostic enum nested under `session` was drafted first and rejected: it forced a reader to look for a relationship between a concrete `id` and a `drift` marker that does not exist — the ID stays correct in every warning case, since Sandcastle takes precedence — and it would have made the runner hold a translation table for the adapter's private failure modes. Free-form prose keeps the runner a pipe and matches how `errorMessage` already passes through verbatim. Duplicating `sessionId?` and a diagnostic onto both union members would keep the diff narrow but leaves a type that no longer says a session is orthogonal to the outcome; the wide change is mechanical, `npm run check` locates every site, and the pre-release notice licenses the redesign. Routing the warning through `onEvent` was rejected because it would render an executor diagnostic inline among agent output as though the agent had said it.

## DR8: The scripted invoker reports an obviously fake session so both new renderings stay demo-covered

Scope: `cli/src/harness/scripted/`, `cli/scripts/scenarios/`

Context: `cli/AGENTS.md` holds that a change giving the terminal something new to draw is unfinished until a scenario shows it, and this change draws two new things: the pause block's continuation line and the run listing's session column. The listing is reachable by seeding, since `scripts/scenarios/18-list.mjs` writes checkpoints straight into the state root from one shared shape and its `expectExit: 0` already forces every seed through the real checkpoint validator. A pause block cannot be seeded — it is drawn by a live run, and every demo run goes through the scripted invoker, which contacts no provider and so holds no session ID. The same file also requires that a scripted attempt frame fabricate no sandbox, branch, or timing.

Decision: `createScriptedInvoker` reports a deterministic and self-evidently synthetic session of the form `scripted-session-<stage-id>-<attempt>`. `scripts/scenarios/04-waiting-for-user.mjs` then renders the continuation line with no change to the scenario itself, since the line follows from the outcome, and `scripts/scenarios/18-list.mjs` gains `agentSession` in its shared seed shape. No new scenario file is added, and the scenario table in `cli/README.md` is updated for whatever its rows now say. The capture-diagnostic warning gets no scenario: `display.warn` renders one generic yellow line, so it is visually indistinguishable from any other warning, and identical renderings do not earn separate scenarios — which also means the scripted invoker needs no fabricated disagreement case, leaving that path covered by unit tests alone.

Rationale: The shape of the value is what resolves the tension with the no-fabrication rule, rather than declining to emit one. That rule exists so no reader believes a sandbox or branch existed; `scripted-session-spec-1` cannot be mistaken for a real conversation and nobody will paste it expecting a provider to accept it. Emitting nothing and covering the line only in the terminal unit tests was rejected because it satisfies the automated gate while leaving a rendering no human ever sees, which is the exact decay the scenario catalog exists to prevent.

## DR9: Leave the earlier executor thread untouched and restate its constraints self-containedly

Context: The seed instructs an implementer to update or supersede records in `docs/threads/260723121015Z-afk-workflow-executor/`, including that thread's `decisions.md` and `spec.md`, should this work change product semantics. The method forbids it: `docs/thread-model.md` holds that a skill does not modify other threads while working from the current thread, and its single narrow exception explicitly excludes editing another thread's `decisions.md`. No supersession is warranted in any case. That thread's records disable Sandcastle-managed session capture and session resumption and state that every stage invocation starts a fresh agent conversation; this work keeps `captureSessions: false`, still never passes `resumeSession` or `forkSession`, and still starts every stage attempt in a fresh conversation. The human reopens a conversation out of band in their own terminal, leaving executor behavior unchanged. In those records "agent-session capture" names Sandcastle's `captureSessions` option, listed there alongside `approvalsReviewer` and `permissionMode` as an invocation option — recording a session identity is not session capture. Their requirement to parse only the single captured result governs what feeds the terminal-outcome gate, which the session match never does.

Decision: Nothing under `docs/threads/260723121015Z-afk-workflow-executor/` is edited, and the spec states that prohibition explicitly because the seed invites the opposite. The spec expresses the constraints it inherits in its own words, as self-contained facts: the executor never enables Sandcastle session capture, never passes a resume or fork session, and starts every stage attempt — including a resumed stage — in a fresh agent conversation. Any mention of the earlier thread is provenance only and must be removable without leaving a sentence incomplete, and where mentioned it carries the full repo-relative thread path, since this thread has its own `DR7` distinct from that thread's.

Living documentation updated in the same change, all under `cli/`: `README.md` gains the run-listing session column and its selection rule, a pointer to `npm run verify:session` on the manual smoke checklist, and whatever its scenario table row now says; `AGENTS.md` gains `npm run verify:session` in its toolchain command list and the scripted invoker's synthetic session in its scripted-harness section. The command-surface description is unchanged, no fourth subcommand having been added.

Rationale: A thread is a historical, self-contained record, so a spec that depends on a reader resolving another thread's record numbering is fragile in three ways at once — the path breaks when that thread is archived, the `DR<N>` numbering collides across threads, and the reader must leave the document to understand it. Keeping the reference as removable provenance preserves the answer to "why does Antmay not reuse the conversation?" without making comprehension depend on it. Deleting the reference outright was rejected for that reason; editing the earlier thread was rejected as a method violation that is also unnecessary, since none of its decisions are reversed.

## DR10: A dedicated `vitest.manual.config.ts` selects the manual verifier

Scope: `cli/vitest.manual.config.ts`, `cli/package.json`

Context: Supersedes the invocation named in DR2 — `vitest run --include 'src/**/*.manual.ts'`, justified there as needing no `vitest.config.ts` change — which cannot run under the pinned toolchain. `cli/package-lock.json` resolves vitest to 2.1.9, whose CLI exposes `-c, --config <path>`, `--dir <path>`, and `--exclude <glob>` but no `--include`; passing one aborts with `CACError: Unknown option --include`. Test selection there is config-only in both directions: positional arguments filter within the configured `include` rather than widening it, `--dir` narrows the scan while `include` still applies, and `--exclude` can only add, since `resolveConfig` appends the CLI value onto the resolved `exclude` array. No command line can therefore either reach a file the config's `include` misses or lift an exclusion the config declares. `cli/vitest.config.ts` pins `include: ["src/**/*.test.ts"]` with 30 s `testTimeout`/`hookTimeout` budgeted for Git-backed cases under concurrent load — a budget the manual verifier's real Codex and Claude Code calls exceed. `cli/tsconfig.json` includes all of `src`, so the manual file is typechecked by `npm run typecheck` under any selection route.

Decision: `npm run verify:session` is `vitest run --config vitest.manual.config.ts`. A new `cli/vitest.manual.config.ts` declares `include: ["src/**/*.manual.ts"]`, `environment: "node"`, and its own `testTimeout`/`hookTimeout` sized for real provider round trips rather than the default 30 s. `cli/vitest.config.ts` is not modified: the manual file stays outside `npm test` and `npm run check` because the default config's `include` never matches it, not because an exclusion rule holds it back. Should the two configs later need shared settings, the manual one imports and spreads the base rather than restating it. Every other part of DR2 stands unchanged — the verifier lives at `cli/src/harness/session-id.manual.ts`, holds two independent per-provider cases, fails rather than skips on absent credentials, and is pointed at from the manual smoke checklist in `cli/README.md`.

Rationale: DR2 exists to catch a provider renaming its session field, and its every other choice serves the guard being loud rather than convenient — which is why absent credentials fail a case instead of skipping it. A separate config is the only route where the manual file's absence from the default run is structural: nothing in `vitest.config.ts` mentions it, so no later edit can pull real provider calls into `npm run check` by deleting a line. The trade-off is a second config file to keep in step with the first. A single config branching on an environment variable was rejected because it makes what a run collects unreadable from the config alone, and forces the timeout split through the same branch; a workspace with two named projects was rejected because a bare `vitest run` would then execute both, putting live provider calls in the default run. The clause this supersedes was reasoning from a flag that never existed, so its "no config change" premise carries no weight against these.

## DR11: The `Continue` line is sourced from the persisted attempt record, so every pause block carries it

Scope: `cli/src/display/`, `cli/src/runner/runner.ts`, `cli/src/commands/resume.ts`

Context: DR5 has a pause block print the native resume command for "the attempt this pause is about", phrased as though every pause were drawn by the process that just ran that attempt. It is not. `cli/src/commands/resume.ts` renders a pause block from six of its own call sites, none of which runs an attempt in that process: four pass an attempt read back from the checkpoint (a re-scan whose queues are still non-empty, a failed re-scan, and the two boundary paths that end in `git-policy-violation` or `commit-error`), and two pass `null` because no attempt was ever allocated. One of those four is the motivating case of this thread re-printed — a run paused on a `.pending-decisions/` bundle, resumed before the bundle was resolved, whose pause is re-rendered from the durable checkpoint with its queues refreshed. Those sites already recover the attempt's log path from the persisted `AttemptRecord` via `attemptLogAbs`. The runner holds the same settled record at every point it renders a pause, having just persisted it.

Decision: A pause block shows the `Continue` line exactly when the attempt the block is about carries `agentSession` on its persisted record — independently of which command renders the block and of whether that attempt ran in the current process. The line is therefore composed from the `AttemptRecord`, the same source the `Log` line already uses, and not from the live `AttemptOutcome`; both the runner's pause paths and `resume`'s own six render it under that one rule. A pause about no attempt shows no `Continue` line, exactly as it shows no `Log` line. This settles the harness half of the command as well: the record's own `agentSession.harness` selects the spelling, so no renderer reaches for the stage profile. `resume` gains no behavior beyond this rendering — its clean-worktree rule, its checkpoint writes, and its exit codes are untouched.

Rationale: The person this feature exists for is the one who walked away, and the command that person types on returning is `antmay afk resume`. Sourcing the line from the live outcome would leave every block that command draws without it, which is a regression against the very block the runner had printed minutes earlier for the same pause. Reading the persisted record instead gives one rule that covers both commands, keeps the `Continue` and `Log` lines derived from one object, and needs no second plumbing path. The trade-off is that the change reaches `cli/src/commands/resume.ts`, which the earlier scoping did not name, and that the display's pause input now carries an attempt record rather than a session lifted off an outcome. A consequence follows from DR4 and is accepted: a run recovered as `executing` after its process was killed has no `agentSession` on the in-flight record, so its pause shows a `Log` line and no `Continue` line.

## DR12: Persist the session the moment it is captured, treating the settle-time value as final

Scope: `cli/src/state/checkpoint.ts`, `cli/src/runner/runner.ts`

Context: Supersedes the timing clause of DR4 — that `agentSession` is attached only on the settle-time write the runner already performs. Everything else in DR4 stands: the field's shape, its optionality, its validation, and its presence on every attempt that captured a session whatever that attempt's result. The timing clause leaves one gap. A process killed mid-attempt — a sleeping laptop, `SIGKILL`, a closed terminal — leaves the checkpoint `executing` with an attempt that never settled and therefore carries no session, and per DR11 the pause block `antmay afk resume` then draws is sourced from that record. The conversation a human most wants to reopen, belonging to the longest-running stage, would be the one case reachable only by reading the raw provider line out of the attempt log — the manual workflow this thread exists to remove. The same gap makes the `list` column of DR6 lag for every `executing` run. The provider's init line arrives seconds into an attempt, so the value is available long before any crash.

Decision: The runner writes `agentSession` onto the executing attempt record as soon as the adapter reports a captured ID, and writes it again on the settle-time write. The mid-attempt value is provisional and the settle-time value is final: DR1 keeps Sandcastle's `result.iterations` value authoritative on the resolve path, so when the two differ the settle-time write overwrites the provisional one. Only the raw-stream match is available mid-attempt, since Sandcastle's own value exists only once `run()` resolves. A run recovered as `executing` therefore carries the session of its in-flight attempt, its pause block offers the `Continue` line, and its `list` row shows the current conversation rather than an earlier one. `agentSession` stays optional: the pre-launch interruption settles an attempt that never invoked the harness, and a provider may emit no init line at all. The harness half of the field is composed by the runner from the resolved stage profile at both writes.

Rationale: A crashed long-running stage is the case with the most to lose and the least recourse, and the extra checkpoint write costs one fsync on a path that already writes the executing record moments earlier. Recovering the `executing` `list` row as a side effect removes the one condition where that column would otherwise show a stale conversation. The trade-off is a second write per attempt and a window in which the checkpoint holds a provisional ID that a later write may replace; the window is harmless because the two values differ only when Antmay's matcher has drifted, which DR1 already surfaces as a warning and DR2 guards against. Keeping the settle-time write authoritative rather than skipping it when a provisional value exists preserves DR1's precedence rule unchanged.

## DR13: The adapter reports the capture through a dedicated `onSessionCaptured` callback, and a failed provisional write warns without stopping the run

Scope: `cli/src/harness/`, `cli/src/runner/runner.ts`

Context: Supersedes the clause of DR7 stating that no new callback is introduced and that the session reaches the runner only in the invoker's return value. DR12 requires the runner to learn the ID while the attempt is still running, which the return value cannot deliver. DR7's other provisions stand: `AttemptOutcome` keeps its `session`, `sessionWarning`, and `result` members, `HarnessEvent` gains no variant, and the capture diagnostic is still prose the adapter writes and the runner forwards verbatim to `display.warn` once per attempt at settle time. The reason DR7 kept the session off `onEvent` is that a `HarnessEvent` is rendered to the terminal as agent output, and an executor's own information must not appear as though the agent said it. The runner holds both the `Display` and every checkpoint write; the adapter holds neither. The runner's writes are fatal by convention — a failure prints the `runFailed` block and exits `1` — and the write that precedes launch already stops a run whose state root is unwritable before a single token is spent.

Decision: The harness request gains an optional `onSessionCaptured` callback, a sibling of `onEvent`, carrying the Antmay-owned `{ id: string }` the raw-stream matcher produced. The Sandcastle adapter fires it once, on the first match of the attempt; the scripted invoker fires it with its synthetic session; the fake harness accepts it and may ignore it. `HarnessEvent` stays purely the vocabulary of what the terminal draws. The runner performs the provisional write from that callback. A failure of that write is not fatal: the runner emits one `display.warn` naming it and the attempt continues.

Rationale: A dedicated callback supersedes DR7's letter while keeping the reasoning it protected — executor information stays off the agent-output path, and a typed, self-describing seam member says what it is better than a session smuggled through a display event would. A mutable holder the runner polls was rejected because it makes the capture moment unobservable, which is the one thing the runner needs. The write is non-fatal because it records nothing about what happened: the attempt is already durably `executing`, and the settle-time write puts the session there regardless, so a transient failure costs nothing and a persistent one is still caught, fatally, at settle. Making it fatal would additionally require aborting the in-flight harness call from inside a callback and teaching the abort path to distinguish a checkpoint failure from a signal — new control flow through the runner's signal handling — to buy a spend saving only in the narrow case where a state root that worked before launch breaks during the attempt.

## DR14: The clean-worktree caution follows the precondition, not the invitation

Scope: `cli/src/display/`

Context: Supersedes the condition under which DR3 renders its caution — "wherever a pause block prints the native resume command" — while keeping everything else in that record: the caution lives in the terminal renderer, no `nextAction` is added to the DONE-finalized pause path, no new field enters the checkpoint, and `resume`'s clean-worktree rule is untouched. That condition is wrong in one direction and arbitrary in another. `antmay afk resume` requires a clean worktree for every waiting kind except `git-policy-violation` and `commit-error`, so a caution printed on either of those two boundary pauses would state a precondition that does not hold. Meanwhile every non-DONE pause and both boundary pauses already carry `nextAction: UNVALIDATED_CHANGES_NOTE`, rendered as a `Next` line telling the reader to revert or deliberately commit before resuming; the DONE-with-pending-bundle pause is the only block that says nothing about worktree state, and it is the pause this thread's motivating case produces.

Decision: A pause block states the clean-worktree precondition when both hold: `antmay afk resume` would require a clean worktree for that pause's governing waiting kind, and the block carries no `nextAction` note already saying so. Whether the block also shows a `Continue` line does not enter the condition. Today exactly one block satisfies it — the DONE-with-pending pause — which therefore states its precondition whether or not a session was captured, while the two boundary pauses never state it. The predicate deciding which waiting kinds require a clean worktree lives in exactly one module, shared between the renderer and `cli/src/commands/resume.ts`, rather than being restated in the display.

Rationale: The caution answers what must be true before `antmay afk resume` will run, which is a property of the pause, not of whether a provider happened to emit a session line — tying it to the `Continue` line would make one pause state its precondition on one harness and omit it on an attempt where capture failed, a distinction no reader could interpret. Rendering it wherever the precondition holds regardless of the existing note was rejected because it puts two sentences saying nearly the same thing on the most common pause kind. Deriving the condition from a predicate shared with `resume` keeps the renderer from drifting out of step with the rule it describes, which is the failure this record exists to correct.

## DR15: Delegate live session parsing to Sandcastle's provider

Scope: `cli/src/harness/sandcastle.ts`

Context: Supersedes DR1's provider-specific raw-stream matcher and its comparison diagnostic. Antmay needs the session ID before `run()` settles so rejected or abruptly terminated attempts can retain it, but Sandcastle's public `AgentProvider.parseStreamLine(line)` already translates each provider's wire format into a normalized `session_id` event. Maintaining a second Codex/Claude parser in Antmay duplicates that dependency logic and creates disagreement states that exist only because two parsers were introduced.

Decision: The adapter builds the Sandcastle provider once for the attempt and passes each raw stdout line through that provider's `parseStreamLine()` method. It retains the first normalized `session_id` event and reports that ID immediately to the runner. When `run()` resolves without a live-captured ID, `result.iterations.at(-1)?.sessionId` is used as a settle-time fallback. Antmay implements no provider-specific session JSON matcher, performs no comparison between independently parsed IDs, and produces no capture-source disagreement diagnostic.

Rationale: Sandcastle remains the single authority for provider wire formats while Antmay still learns the ID early enough to preserve failed and killed attempts. The result field provides a cheap fallback for a resolved run without becoming a second parsing authority. This removes the matcher-drift failure mode and the warning/type machinery created to manage it; the trade-off is that Antmay deliberately relies on the pinned Sandcastle parser instead of independently detecting provider protocol changes.

## DR16: Serialize the immediate session checkpoint write before settlement

Scope: `cli/src/runner/runner.ts`

Context: Supersedes DR12's checkpoint-write timing. Persisting the session while an attempt is still executing protects recovery after an abrupt process death, but the `onSessionCaptured` callback is synchronous while checkpoint persistence is asynchronous. If the provisional write and the attempt's settlement write overlap, atomic replacement protects each individual document from corruption but does not prevent the older provisional write from completing last and replacing a settled checkpoint with stale `executing` state.

Decision: The first captured session starts exactly one provisional checkpoint write, whose promise the runner retains. No later checkpoint write for that attempt may overlap it. After the harness resolves or rejects, the runner awaits the provisional write before performing interruption or ordinary settlement persistence. The settlement record includes the captured session again. When no session is reported while the attempt is live, no provisional write occurs and a session supplied only by DR15's resolved-result fallback is recorded at settlement.

Rationale: Immediate persistence is worth one additional fsynced checkpoint write because preserving the native conversation after a killed long-running attempt is a core outcome of this feature. Explicit serialization retains that recovery property without allowing an older `executing` document to win a race against the final state. The trade-off is a small amount of promise coordination in the runner and, after the harness ends, waiting for any still-pending provisional write before the final transition.

## DR17: Preserve the discriminated attempt outcome union

Scope: `cli/src/harness/types.ts`

Context: Supersedes DR7's nested `result` shape and capture-diagnostic member. That redesign existed to carry a session independently of completion or failure together with the disagreement warning produced by DR1. DR15 removes the independent parser and its warning, while the existing `AttemptOutcome` union already gives every consumer a direct `kind` discriminant for classification.

Decision: `AttemptOutcome` remains the existing `completed` / `failed` discriminated union and gains a shared optional `session?: { id: string }` property. It has no nested `result` member and no `sessionWarning`. Classification continues to read `outcome.kind`. The dedicated `onSessionCaptured` request callback remains separate from the outcome because it reports the ID while the invocation is still live for DR16's early persistence; `HarnessEvent` gains no session variant.

Rationale: The narrow additive type expresses that either outcome may carry a session without mechanically reshaping every adapter, fake, classifier, and runner call site. Keeping live capture separate also preserves the boundary between executor metadata and agent output. The trade-off is that session orthogonality is expressed through a shared intersection or duplicated optional field rather than through a wrapper object, which is less architecturally emphatic but materially simpler.

## DR18: Test Antmay's session flow automatically and native resumption manually

Scope: `cli/src/harness/`, `cli/src/runner/`, `cli/src/display/`, `cli/README.md`

Context: Supersedes DR2 and DR10, plus their `npm run verify:session` documentation requirements in DR9. Those records introduced parser-agreement fixtures and a credential-dependent real-provider Vitest configuration to guard the Codex and Claude wire matcher owned by Antmay. DR15 removes that matcher and delegates provider parsing to Sandcastle, so the drift relationship those tests existed to detect no longer exists. A non-interactive provider call can confirm that an ID was returned, but only opening the printed command in an interactive terminal proves the user-visible outcome.

Decision: Automated tests cover only Antmay-owned behavior: consuming Sandcastle's normalized `session_id` event, retaining and reporting the first ID, attaching it to successful and failed outcomes, serializing early checkpoint persistence before settlement, validating the persisted record, and rendering the pause and list surfaces through the scripted harness and existing demo scenarios. The implementation adds no `session-id.manual.ts`, no `npm run verify:session`, and no `vitest.manual.config.ts`. `cli/README.md` instead carries a concise manual smoke checklist that runs whichever real provider is configured, confirms the checkpoint received its session ID, pastes the emitted native resume command, and verifies that the same conversation opens.

Rationale: The automated suite remains deterministic, free of credentials and model charges, and focused on Antmay's contract. The manual check covers the only evidence the dedicated verifier could not automate: successful interactive continuation in the provider CLI. The trade-off is that provider integration drift is discovered when the smoke checklist is intentionally run rather than through a standalone diagnostic command.

## DR19: Leave clean-worktree presentation outside the session feature

Scope: `cli/src/display/`, `cli/src/commands/resume.ts`, `cli/README.md`

Context: Supersedes DR3 and DR14. A person who edits the repository while continuing the native provider conversation must commit or revert those changes before `antmay afk resume` can proceed, but that clean-worktree requirement already exists and the resume command already rejects a dirty tree with corrective guidance. Capturing and exposing a provider session does not change the predicate or its enforcement.

Decision: This feature adds no clean-worktree caution to pause rendering, introduces no shared clean-worktree predicate for the renderer, and otherwise leaves resume's existing validation and error text unchanged. The documented native-session journey and manual smoke checklist state that repository changes made while continuing the conversation must be deliberately committed or reverted before resuming the Antmay run.

Rationale: Documentation gives the motivating journey the needed instruction while keeping the implementation focused on session identity, persistence, retrieval, and native continuation. Existing enforcement still prevents an unsafe resume. The trade-off is that a person who did not read the journey may learn the precondition only when `resume` rejects a dirty worktree rather than seeing a proactive pause-block caution.

## DR20: Shell-quote session IDs in native continuation commands

Scope: `cli/src/display/`, `cli/src/harness/`

Context: Supersedes DR5's unquoted command spelling while preserving its pause behavior and DR11's persisted-record source. Antmay validates a captured session ID only as a non-empty opaque string. A command described as paste-ready cannot also assume that the value consists solely of characters that the user's shell will interpret literally.

Decision: One Antmay-owned command-composition helper maps the captured harness to its native resume syntax and applies POSIX-safe shell quoting to the session ID, including correct encoding of embedded single quotes. An ordinary ID renders as `codex resume '<id>'` for Codex or `claude --resume '<id>'` for Claude Code. Every surface that presents a native continuation command uses that helper. Antmay continues to treat the ID as opaque and does not inspect or verify the resumed conversation's transcript.

Rationale: Quoting makes every valid persisted ID safe to paste while remaining harmless and readable for the UUID-like values providers normally emit. Centralizing the mapping prevents display surfaces from drifting apart. The trade-off is a small quoting helper and its focused tests instead of direct string interpolation.

## DR21: Treat a failed early session write as recoverable

Scope: `cli/src/runner/runner.ts`, `cli/src/display/`

Context: Restates DR13's provisional-write failure policy after DR15–DR17 simplified session capture and the attempt outcome. The early write protects recovery from an abruptly terminated process, but it does not describe a stage transition or affect the harness result. Stopping an already-running invocation would require cancellation and a separate checkpoint-error path, and could discard useful agent work.

Decision: If the provisional session checkpoint write fails, the runner reports one warning and allows the harness attempt to continue. It still observes the failed write before settlement as required by DR16, includes the session on the settled attempt, and performs the ordinary final checkpoint write. A failure of that final write retains the runner's existing fatal checkpoint-write behavior. The feature adds no retry loop, harness cancellation, or durable warning field.

Rationale: Continuing preserves useful work and gives the normal settlement write another opportunity to persist the captured ID. If persistence remains unavailable, the existing raw attempt log remains the manual recovery source and the final write failure is surfaced normally. The trade-off is that an abrupt process death after the provisional failure but before successful settlement can still leave the session absent from the checkpoint.

## DR22: Persist only the session ID on an attempt

Scope: `cli/src/state/checkpoint.ts`, `cli/src/display/`, `cli/src/commands/`

Context: Supersedes DR4's `agentSession` shape and DR11's rule that the attempt record carries its own harness. Every attempt already names its stage by index, and the checkpoint contains an immutable snapshot of that stage's resolved execution profile, including its harness. Persisting the same harness again beside the session ID would introduce duplicated state and require a cross-field invariant solely to prevent the two copies from disagreeing.

Decision: An attempt optionally persists `agentSession?: { id: string }`. A consumer that needs the native continuation command resolves the harness from `checkpoint.stages[attempt.stageIndex].profile.harness` and passes it with the ID to the shared command-composition helper from DR20. Pause rendering, run listing, validation, scripted fixtures, and tests use this ID-only persisted shape.

Rationale: The checkpoint keeps one authority for the harness while still preserving the only new provider value this feature needs to capture. The existing immutable stage snapshot makes the lookup deterministic for old and current attempts. The trade-off is that rendering a continuation command requires checkpoint context rather than an attempt record alone.

## DR23: Make the scripted session ID discoverable in its attempt log

Scope: `cli/src/harness/scripted/`, `cli/README.md`, `cli/AGENTS.md`

Context: A real Sandcastle attempt retains the provider's raw session event in its verbose attempt log, so the provider session ID remains recoverable there independently of checkpoint persistence. The scripted invoker owns a deterministic synthetic ID rather than a provider raw event. Attempt-log inspection is a recovery surface in both modes and must expose the identity produced by a completed or interrupted attempt.

Decision: Every valid launched scripted attempt appends its deterministic `scripted-session-<stage-id>-<attempt>` identity to the attempt log as explicit scripted-harness metadata before executing the selected case. The line is not emitted through `onEvent`, so terminal transcripts remain limited to agent progress and tool calls. Pre-launch validation and interruption paths that produce no session append no session line.

Rationale: Attempt-log inspection should expose the session identity in both real and scripted runs. An explicit synthetic metadata line preserves the scripted harness's provider-neutral and visibly fake identity while avoiding fabricated provider JSON. Writing it before case execution gives the scripted log the same recovery role as the real verbose stream if later scripted work fails or is interrupted.

## DR24: Stop adapter-side parsing after the first session identity

Scope: `cli/src/harness/sandcastle.ts`

Context: Supersedes DR15's requirement that the adapter pass every raw stdout line through the attempt provider's `parseStreamLine()` method. Sandcastle itself parses every raw line through that provider as part of running the attempt. The adapter invokes the parser separately only to obtain the first normalized session identity early enough for provisional checkpoint persistence.

Decision: The adapter passes raw stream lines to the attempt provider's `parseStreamLine()` method until it receives the first `session_id` event with a non-empty ID. It retains that ID, reports it once through `onSessionCaptured`, and stops its own additional parsing for the remainder of the attempt. Sandcastle remains responsible for parsing the complete provider stream, and later session events do not replace the first captured identity.

Rationale: The feature requires one early, stable session identity rather than a second full-stream parse. Stopping the adapter's additional parser calls after capture avoids redundant work and avoids depending on repeated parser invocation remaining harmless, while preserving first-ID selection, callback cardinality, settlement retention, and Sandcastle's complete stream processing.
