# Decisions — Expose provider session IDs so AFK stages can be continued in the native Codex/Claude Code CLIs

## DR1: Capture the provider session ID from the live raw stream, with Sandcastle's result as the authority

Scope: `cli/src/harness/sandcastle.ts`

Context: Antmay must obtain the provider session ID for a stage attempt so it can be persisted and shown to a human. Sandcastle exposes the ID on `RunResult.iterations[n].sessionId`, but a `RunResult` exists only when `run()` resolves: on rejection — idle timeout, provider error, abort — there is no result object at all, and only `StructuredOutputError` carries an ID (a path Antmay never reaches, since it passes no `output`). Reading the result alone would therefore leave the ID absent for exactly the opaque attempts a human most wants to reopen. Sandcastle separately delivers every provider stdout line verbatim to the `onAgentStreamEvent` callback Antmay already wires, as `{ type: "raw", line, iteration, timestamp }`, and the provider's init line carrying the ID arrives at the start of an attempt — before any timeout or interruption.

Decision: The adapter watches the raw stream for the provider's session-identity line and holds the first match for the lifetime of the attempt: Codex `{ "type": "thread.started", "thread_id": … }` and Claude Code `{ "type": "system", "subtype": "init", "session_id": … }`, each guarded against non-JSON lines. The captured ID may be attached to any outcome, failed ones included. On the resolve path, where both sources exist, `result.iterations.at(-1)?.sessionId` takes precedence and the sniffed value is the fallback used only when Sandcastle's is absent; the sniff is therefore a supplement to Sandcastle's own extraction rather than a replacement for it. When both values are present and disagree, or Sandcastle produced an ID and the raw-stream match did not, the adapter emits exactly one warning through the display.

Rationale: The motivating case — a `spec` stage reporting DONE with pending decisions — is covered by the result field alone, so reading only the result is defensible on YAGNI grounds. It was rejected because an idle-timed-out or interrupted attempt is precisely the state whose conversation a human needs to inspect, and that path would record nothing. The trade-off accepted is that `cli/src/harness/sandcastle.ts` now knows two provider wire shapes, duplicating parsing Sandcastle performs internally; this is contained in the one module whose purpose is already to know about Codex and Claude Code. Keeping Sandcastle authoritative on the resolve path bounds the damage from that duplication: a Sandcastle mapping change degrades to an unnecessary fallback rather than to a wrong ID, and the disagreement warning makes the divergence visible on real runs, which no offline test can observe.

## DR2: Guard the raw-stream matcher with a CI fixture-agreement test and an opt-in real-provider verifier

Scope: `cli/src/harness/`

Context: DR1 has the adapter match two provider wire shapes itself, which can silently stop finding a session ID in two independent ways. Sandcastle may change which shape it maps to a session ID, diverging from Antmay's copy; or a provider may rename the field, in which case Antmay and Sandcastle both stop finding it and still agree on any fixture line — no offline test can detect that, because the fixture encodes the same assumption. Sandcastle's `parseStreamLine(line)` is part of its public `AgentProvider` interface and is callable from a test with no provider binary, credentials, or network. Antmay's `tsup` build has the single entry `src/main.ts`, so `dist/` exports nothing importable and a dependency-free script under `scripts/` cannot reach the adapter; `vitest` is the only tool configured here that loads TypeScript source, and its `include` of `src/**/*.test.ts` excludes any other filename from the default run.

Decision: Two guards, aimed at the two failure modes.

For Sandcastle-side drift, a case in `cli/src/harness/sandcastle.test.ts` asserts one fixture line per provider twice over: that Antmay's matcher extracts the expected ID, and that `codex(model).parseStreamLine(line)` / `claudeCode(model).parseStreamLine(line)` yields a `session_id` event carrying the same value. It runs inside `npm run check`.

For provider-side drift, `cli/src/harness/session-id.manual.ts` run by a new `npm run verify:session` (`vitest run --include 'src/**/*.manual.ts'`), which needs no `vitest.config.ts` change and is never collected by `npm test`. It holds two independent cases, one per provider, each invoking `createSandcastleInvoker()` in a throwaway temporary directory with a trivial prompt, `dangerouslySkipPermissions: true`, and a short idle timeout. Each asserts that an ID was captured and that the two sources agree, then prints the native resume command for a human to paste. Missing credentials fail the case rather than skipping it. The manual smoke checklist in `cli/README.md` gains a pointer to this command.

Rationale: The split follows the detectability of each failure: one is free and belongs in CI, the other costs real model calls and cannot run unattended, so it is opt-in and deliberately loud when run. Asserting the last mile — that `codex resume <id>` genuinely reopens the conversation — needs an interactive terminal and stays a human step. A standalone `.mjs` script under `scripts/` was rejected because it could only drive the built CLI as a subprocess, requiring a thread, settings, a clean repository, and a lock to read back one field; a vitest file reaches the adapter directly. A case that skips on absent credentials was rejected as the most likely way for this guard to rot unnoticed.

## DR3: Warn about the clean-worktree precondition in the renderer, not the checkpoint

Scope: `cli/src/display/`

Context: `antmay afk resume` requires a clean worktree for every waiting kind except `git-policy-violation` and `commit-error`, and a DONE-with-pending-bundle pause is governed by `pending-queues`, so it requires one. A human who accepts the invitation to continue the stage's conversation in the native CLI will typically leave the worktree dirty — `resolve-pending-decisions` appends to `decisions.md`, which the stage's own boundary commit had already committed, and that skill issues no commit of its own — so resuming afterwards fails with exit `1` until those changes are committed or reverted. The pause taken on a DONE-finalized stage carries no `nextAction`, so its block currently says nothing about uncommitted changes, unlike a non-DONE pause which carries the unvalidated-changes note.

Decision: Wherever a pause block prints the native resume command, the same block also states that the worktree must be clean before `antmay afk resume` — commit or revert whatever the conversation changed. This lives entirely in the terminal renderer, composed from information it already receives; no `nextAction` is added to the DONE-finalized pause path and no new field enters the checkpoint. `resume` keeps its clean-worktree rule unchanged.

Rationale: Advertising a native conversation without naming its exit condition would let a human invest a whole conversation before discovering the constraint, and the recovery they need — committing before leaving the session — is knowledge they must have beforehand for it to help. Putting the sentence in the checkpoint's `nextAction` was rejected on two counts: it writes interface prose into a durable state document, and on that path `nextAction` means something narrower and factually different — that an attempt's changes never passed the terminal-outcome gate — which is untrue of a human's deliberate edits. Relaxing the clean-worktree rule for this case was rejected outright: `resume` cannot distinguish a human's deliberate edits from an agent's unvalidated ones, and that distinction is the rule's entire basis.

## DR4: Persist the session as an optional self-contained `agentSession` on every attempt that captured one

Scope: `cli/src/state/checkpoint.ts`

Context: The captured provider session ID must become durable run state. The checkpoint is at `schemaVersion: 0`, and `cli/AGENTS.md` fixes it there while the format is unstable, forbidding migrations and compatibility shims and accepting that existing run directories may become unreadable — so no version bump is in question, and the handoff's premise of a `schemaVersion: 1` document needing a `2` is stale. That same policy forbids weakening a field to optional merely so previously written state validates. The runner settles every attempt by replacing its last record on four paths, one of which — the pre-launch interruption — settles an attempt that never invoked the harness and so can carry no session. A provider may also emit no session line at all.

Decision: `AttemptRecord` gains `agentSession?: { harness: HarnessId; id: string }`, validated in `validateAttempt` as an optional object whose `harness` is a known harness id and whose `id` is a non-empty string. The field is optional because its absence is a real state, not a compatibility concession. It is written on every attempt for which an ID was captured regardless of that attempt's result — `done`, `waiting`, and `interrupted` alike — rather than on a subset selected by outcome. `harness` is stored alongside the ID even though it is derivable from the snapshotted stage profile, so any reader can compose the native resume command from the attempt record alone. The value is attached only on the settle-time write the runner already performs, which gives the interruption helper an optional session parameter supplied at its post-abort call site and absent at its pre-launch one.

Rationale: Uniform capture is cheaper to implement and to explain than an outcome-conditioned policy, and reopening the conversation of a stage that already advanced is a real need — asking why a finished stage wrote what it did — not only a recovery path. Duplicating `harness` trades a derivable byte for a self-contained record and removes a reach through `stageIndex` into the stages array; the two values cannot diverge, since both come from one resolved profile within a single attempt. Persisting the ID mid-attempt the moment it arrives was rejected: it costs an extra fsync per attempt to protect a state the CLI already reports as unverified, and the raw provider line remains in the attempt log either way.

## DR5: The pause block prints the paste-ready native command for the attempt that just ended

Scope: `cli/src/display/`

Context: Every pause a human acts on is rendered by one call — the DONE-with-pending pause, BLOCKED, REFUSED, a malformed outcome, an idle timeout, a harness error, a boundary violation, and a mid-attempt signal all route through the runner's pause rendering. The block's action section is a sequence of key/value lines whose stated purpose is that the last thing on screen is the thing to type next, and it already prints the literal `antmay afk resume <run-id>`. The two providers spell continuation differently: `codex resume <id>` and `claude --resume <id>`. The session ID cannot be shown when an attempt starts, because it arrives on the stream seconds later.

Decision: When the attempt a pause is about carries an `agentSession`, the action section gains one line whose value is the exact native command for that harness — `codex resume <id>` or `claude --resume <id>` — under a generic key alongside `Log` and `Resume`. No separate harness-name label is rendered: the harness is legible from the binary name in the command itself. The session shown is always the one belonging to the attempt this pause is about, so no attempt-selection rule applies. A pause taken before any attempt was allocated, such as the pre-attempt queue gate, shows no such line, exactly as it already shows no log path. Antmay treats the ID as an opaque reference and never inspects `~/.codex/sessions/` or `~/.claude/projects/` to confirm a transcript still exists.

Rationale: A paste-ready line matches the action section's established idiom and removes the one detail a human is least likely to remember, which is each provider's differing flag shape. Printing the ID with only a harness name was considered, on the grounds that a user with shell aliases or habitual flags has their own way to invoke a provider; it was rejected because a printed command is a suggestion an alias user adapts in a second, whereas an identity alone taxes every user with recomposing the line. Verifying transcript existence before printing was rejected because it would couple Antmay to two provider-private storage layouts to buy a slightly better error than the provider CLI already gives for an unknown ID.

## DR6: `antmay afk list` shows the run's most recent session; a per-attempt session view is deferred

Scope: `cli/src/commands/list.ts`

Context: A session belongs to an attempt, but a `list` row describes a run, and a run accumulates one session per attempt across its stages — so a single column can only show one of several. The retrieval floor is already met without any `list` change: DR4 puts every captured session in `state.json`, and each attempt log retains the provider's raw init line. A row's stage position and the latest attempt can disagree, because the cursor may have advanced past the stage that last attempted; for a run waiting on a human, however, the latest attempt is always the current stage's, since a pause happens on the stage the cursor sits at. Disagreement is therefore confined to `ready` runs, which persist only between two checkpoint writes, and to completed runs, where nothing is blocked.

Decision: `renderRow` gains one column showing the session of the most recent attempt that carries one, rendered as `<harness>/<session-id>` to reuse the row's existing `harness/model` idiom, and omitted for a run that captured none. `cli/README.md` states that selection rule. A complete per-attempt view — a way to see every session a run produced, which was the substance of a rejected `antmay afk session` subcommand — is deferred to a future thread, to be designed together with the wider rework of this command's output.

Rationale: The column is a few lines plus a test, is correct precisely in the state where a human hunts for a conversation, and forecloses nothing: the pre-release notice lets a later redesign replace it outright. Deferring the column as well was considered, since the underlying multi-session presentation problem is genuinely unsettled; it was rejected because the scenario this whole feature exists for is a human who walked away, and after their scrollback is gone that option leaves them opening `state.json` by hand. Aiming the deferral at the complete surface instead keeps this thread unblocked without reducing retrieval to a manual file read.

## DR7: Reshape `AttemptOutcome` so the session and its capture diagnostic sit beside the result

Scope: `cli/src/harness/types.ts`

Context: DR1 requires the captured session to be attachable to a failed attempt as well as a completed one, and calls for one warning when Antmay's raw-stream matcher disagrees with Sandcastle's own extraction. Neither is expressible today: `AttemptOutcome` is a two-variant union discriminated by `kind`, and the only callback an adapter receives is `onEvent`, whose `HarnessEvent` union carries agent text and tool calls for live display. The `Display` is held by the runner, not by any adapter. DR1 attributes the warning's emission to the adapter; this record locates it in the runner, with the adapter supplying its content.

Decision: `AttemptOutcome` becomes an object with three members: an optional `session?: { id: string }`, an optional `sessionWarning?: string`, and a `result` holding the existing `completed` / `failed` union unchanged. Hoisting `session` out of the union is what states that a session is independent of how the attempt ended. `sessionWarning` is prose written by the adapter and forwarded verbatim by the runner to `display.warn`; it is a sibling of `session` rather than a field inside it, because it describes the health of Antmay's capture mechanism and not the identity of the conversation, and it is never persisted. No new callback and no new `HarnessEvent` variant is introduced. The `harness` half of the persisted `agentSession` is not carried on the outcome: the runner composes it from the stage profile it already holds. Every consumer moves with the shape — the Sandcastle invoker, the scripted invoker, the fake harness in `cli/src/test-helpers/`, and the runner's classification, where `outcome.kind` becomes `outcome.result.kind`.

Rationale: A diagnostic enum nested under `session` was drafted first and rejected: it forced a reader to look for a relationship between a concrete `id` and a `drift` marker that does not exist — the ID stays correct in every warning case, since Sandcastle takes precedence — and it would have made the runner hold a translation table for the adapter's private failure modes. Free-form prose keeps the runner a pipe and matches how `errorMessage` already passes through verbatim. Duplicating `sessionId?` and a diagnostic onto both union members would keep the diff narrow but leaves a type that no longer says a session is orthogonal to the outcome; the wide change is mechanical, `npm run check` locates every site, and the pre-release notice licenses the redesign. Routing the warning through `onEvent` was rejected because it would render an executor diagnostic inline among agent output as though the agent had said it.

## DR8: The scripted invoker reports an obviously fake session so both new renderings stay demo-covered

Scope: `cli/src/harness/scripted/`, `cli/scripts/scenarios/`

Context: `cli/AGENTS.md` holds that a change giving the terminal something new to draw is unfinished until a scenario shows it, and this change draws two new things: the pause block's continuation line and the run listing's session column. The listing is reachable by seeding, since `scripts/scenarios/18-list.mjs` writes checkpoints straight into the state root from one shared shape and its `expectExit: 0` already forces every seed through the real checkpoint validator. A pause block cannot be seeded — it is drawn by a live run, and every demo run goes through the scripted invoker, which contacts no provider and so holds no session ID. The same file also requires that a scripted attempt frame fabricate no sandbox, branch, or timing.

Decision: `createScriptedInvoker` reports a deterministic and self-evidently synthetic session of the form `scripted-session-<stage-id>-<attempt>`. `scripts/scenarios/04-waiting-for-user.mjs` then renders the continuation line with no change to the scenario itself, since the line follows from the outcome, and `scripts/scenarios/18-list.mjs` gains `agentSession` in its shared seed shape. No new scenario file is added, and the scenario table in `cli/README.md` is updated for whatever its rows now say. The capture-diagnostic warning gets no scenario: `display.warn` renders one generic yellow line, so it is visually indistinguishable from any other warning, and identical renderings do not earn separate scenarios — which also means the scripted invoker needs no fabricated disagreement case, leaving that path covered by unit tests alone.

Rationale: The shape of the value is what resolves the tension with the no-fabrication rule, rather than declining to emit one. That rule exists so no reader believes a sandbox or branch existed; `scripted-session-spec-1` cannot be mistaken for a real conversation and nobody will paste it expecting a provider to accept it. Emitting nothing and covering the line only in the terminal unit tests was rejected because it satisfies the automated gate while leaving a rendering no human ever sees, which is the exact decay the scenario catalog exists to prevent.

## DR9: Leave the earlier executor thread untouched and restate its constraints self-containedly

Context: The seed instructs an implementer to update or supersede records in `docs/threads/260723121015Z-afk-workflow-executor/`, including that thread's `decisions.md` and `spec.md`, should this work change product semantics. The method forbids it: `docs/thread-model.md` holds that a skill does not modify other threads while working from the current thread, and its single narrow exception explicitly excludes editing another thread's `decisions.md`. No supersession is warranted in any case. That thread's records disable Sandcastle-managed session capture and session resumption and state that every stage invocation starts a fresh agent conversation; this work keeps `captureSessions: false`, still never passes `resumeSession` or `forkSession`, and still starts every stage attempt in a fresh conversation. The human reopens a conversation out of band in their own terminal, leaving executor behavior unchanged. In those records "agent-session capture" names Sandcastle's `captureSessions` option, listed there alongside `approvalsReviewer` and `permissionMode` as an invocation option — recording a session identity is not session capture. Their requirement to parse only the single captured result governs what feeds the terminal-outcome gate, which the session match never does.

Decision: Nothing under `docs/threads/260723121015Z-afk-workflow-executor/` is edited, and the spec states that prohibition explicitly because the seed invites the opposite. The spec expresses the constraints it inherits in its own words, as self-contained facts: the executor never enables Sandcastle session capture, never passes a resume or fork session, and starts every stage attempt — including a resumed stage — in a fresh agent conversation. Any mention of the earlier thread is provenance only and must be removable without leaving a sentence incomplete, and where mentioned it carries the full repo-relative thread path, since this thread has its own `DR7` distinct from that thread's.

Living documentation updated in the same change, all under `cli/`: `README.md` gains the run-listing session column and its selection rule, a pointer to `npm run verify:session` on the manual smoke checklist, and whatever its scenario table row now says; `AGENTS.md` gains `npm run verify:session` in its toolchain command list and the scripted invoker's synthetic session in its scripted-harness section. The command-surface description is unchanged, no fourth subcommand having been added.

Rationale: A thread is a historical, self-contained record, so a spec that depends on a reader resolving another thread's record numbering is fragile in three ways at once — the path breaks when that thread is archived, the `DR<N>` numbering collides across threads, and the reader must leave the document to understand it. Keeping the reference as removable provenance preserves the answer to "why does Antmay not reuse the conversation?" without making comprehension depend on it. Deleting the reference outright was rejected for that reason; editing the earlier thread was rejected as a method violation that is also unnecessary, since none of its decisions are reversed.

## DR10: A dedicated `vitest.manual.config.ts` selects the manual verifier

Scope: `cli/vitest.manual.config.ts`, `cli/package.json`

Context: Supersedes the invocation named in DR2 — `vitest run --include 'src/**/*.manual.ts'`, justified there as needing no `vitest.config.ts` change — which cannot run under the pinned toolchain. `cli/package-lock.json` resolves vitest to 2.1.9, whose CLI exposes `-c, --config <path>`, `--dir <path>`, and `--exclude <glob>` but no `--include`; passing one aborts with `CACError: Unknown option --include`. Test selection there is config-only in both directions: positional arguments filter within the configured `include` rather than widening it, `--dir` narrows the scan while `include` still applies, and `--exclude` can only add, since `resolveConfig` appends the CLI value onto the resolved `exclude` array. No command line can therefore either reach a file the config's `include` misses or lift an exclusion the config declares. `cli/vitest.config.ts` pins `include: ["src/**/*.test.ts"]` with 30 s `testTimeout`/`hookTimeout` budgeted for Git-backed cases under concurrent load — a budget the manual verifier's real Codex and Claude Code calls exceed. `cli/tsconfig.json` includes all of `src`, so the manual file is typechecked by `npm run typecheck` under any selection route.

Decision: `npm run verify:session` is `vitest run --config vitest.manual.config.ts`. A new `cli/vitest.manual.config.ts` declares `include: ["src/**/*.manual.ts"]`, `environment: "node"`, and its own `testTimeout`/`hookTimeout` sized for real provider round trips rather than the default 30 s. `cli/vitest.config.ts` is not modified: the manual file stays outside `npm test` and `npm run check` because the default config's `include` never matches it, not because an exclusion rule holds it back. Should the two configs later need shared settings, the manual one imports and spreads the base rather than restating it. Every other part of DR2 stands unchanged — the verifier lives at `cli/src/harness/session-id.manual.ts`, holds two independent per-provider cases, fails rather than skips on absent credentials, and is pointed at from the manual smoke checklist in `cli/README.md`.

Rationale: DR2 exists to catch a provider renaming its session field, and its every other choice serves the guard being loud rather than convenient — which is why absent credentials fail a case instead of skipping it. A separate config is the only route where the manual file's absence from the default run is structural: nothing in `vitest.config.ts` mentions it, so no later edit can pull real provider calls into `npm run check` by deleting a line. The trade-off is a second config file to keep in step with the first. A single config branching on an environment variable was rejected because it makes what a run collects unreadable from the config alone, and forces the timeout split through the same branch; a workspace with two named projects was rejected because a bare `vitest run` would then execute both, putting live provider calls in the default run. The clause this supersedes was reasoning from a flag that never existed, so its "no config change" premise carries no weight against these.
