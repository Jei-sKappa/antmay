# Separate the local binding vocabulary from the documents that carry it Decision Log

## DR1: The binding vocabulary is a declarations-only module, and the timing defaults are not part of it

Context: `cli/src/config/execution.ts` declares the local binding vocabulary (`AgentBinding`, `StageBinding`, `StageBindingMap`, `ExecutionProfile`, `ResolvedStageBinding`, and the three result types), holds the two intrinsic timing default constants, validates the settings and execution-profile documents, and resolves one selected stage's binding. Outside that module and its own test, only four symbols are used anywhere: `ResolvedStageBinding` by `state/checkpoint/types.ts` (type-only), `StageBindingMap` by the three run preflight steps, `ExecutionProfile` by `commands/run/preflight/load-profile.ts`, and the three exported functions. `AgentBinding`, `StageBinding`, and both `DEFAULT_*` constants have no consumer outside the module. The two defaults are applied in exactly one place, the `??` fallbacks inside `resolveStageBindings`.

Decision: the split produces a vocabulary module that holds all of the binding types — including both documents' shared `AgentBinding` and `StageBinding` — and nothing executable: type imports and exported type declarations only, in the same form `state/checkpoint/types.ts` takes. `DEFAULT_IDLE_TIMEOUT_SECONDS` and `DEFAULT_HEARTBEAT_SECONDS` are not part of it; they move next to the resolution code that applies them. The document schemas and the resolution rule each become their own module alongside.

Rationale: the checkpoint needs exactly one type, and it is the resolved shape — what exists once both documents are out of the picture — so a vocabulary module that provably cannot run anything is what makes the checkpoint's dependency honest. Keeping it declarations-only means the existing guard written for the checkpoint vocabulary can be pointed at this module as well, turning "the vocabulary declares and does nothing" from a property that happens to hold into one that is enforced. The trade-off accepted: the contract that an omitted timing field falls back to an intrinsic default is stated on the optional type but implemented one module away, so the two are linked in prose rather than co-located. Splitting the vocabulary itself by lifetime — document shape with the schemas, resolved shape with the resolver — was rejected because it would put the checkpoint's import on a module that performs resolution arithmetic, while `AgentBinding` would remain shared by both halves regardless.

## DR2: Each document is a pure validator and a separate loader, over one shared stage-binding schema

Context: the settings document and the execution-profile document accept the identical stage-binding shape — `{ agent: { harness, model }, idleTimeoutSeconds?, heartbeatSeconds? }` keyed by catalog stage ID — validated today by four private functions shared verbatim by both, about 130 lines of the module. What differs per document is small: the envelope (`afk.stages` against `schemaVersion`/`name`/`stages`), the emptiness rule (settings may bind zero stages, a profile may not), the missing-file semantics (settings treats a missing file as the canonical empty document, a profile treats it as an error), and the failure shape (the settings result carries the resolved `sourcePath`, the profile result does not). The contract requires both documents' diagnostic wording and order to survive the split unchanged, so any shape that duplicates the shared schema is a drift hazard by construction.

Decision: the document side becomes five modules. One shared stage-binding schema module validates the agent pair, the optional timing fields, one binding, and a map of bindings, and holds no opinion about emptiness. Each document then gets a pure validator module — envelope validation over an already-parsed root, no filesystem access — and a separate loader module that reads its path, parses JSON, delegates to its validator, and applies its own missing-file semantics and failure shape. Each document applies its own emptiness rule at its own call site rather than passing a flag into the shared schema, which removes the `requireNonEmpty` boolean; an empty map produces no per-key diagnostics, so neither wording nor order moves.

Rationale: every resulting file states one purpose, and the pure validators become filesystem-free by construction, which is the shape that is straightforward to test and to read. The cost accepted is more files and one extra hop from a document's validation to its loading than the code strictly forces — the validate/read precedent in `state/checkpoint/` was earned by two genuinely different consumers, whereas here each validator has exactly one caller, its own loader. That cost was judged worth paying for uniform granularity across the whole area rather than a shape that varies with how many consumers each part happens to have today. Keeping both documents on one shared schema module is not a preference but the contract: duplicated validation is how the two documents' wording drifts apart.

## DR3: The shared stage-binding schema stays one module

Context: the shared schema DR2 establishes is four functions in a strict chain — a stage map validates each binding, a binding validates its optional timing fields and its agent object, and the agent object validates the harness/model pair. Each has exactly one caller within the chain, and only the map-level entry point is imported by anything outside it.

Decision: those four validators live together in one module. The schema is not split by function, by depth, or along the agent pair.

Rationale: they are one schema expressed at four depths rather than four purposes, and they answer the single question a reader brings — what a stage binding may contain and what each violation says. Splitting them would scatter that one answer across files whose only content is a function with a single caller, which costs a reader jumps and returns no seam. This is the deliberate limit on the granularity DR2 applies elsewhere: the unit is a purpose, not a function.

## DR4: Layout is three concern-named folders under `config/`, with checkpoint-style file names

Context: DR1 through DR3 produce seven modules — the binding vocabulary, the shared stage-binding schema, resolution with the timing defaults, and a validator plus a loader for each of the two documents. `config/` holds `roots.ts` and `references.ts` alongside them, and `state/checkpoint/` is the repository's existing precedent for grouping a subject into a folder of `types.ts`, `validate.ts`, and `read.ts` with unprefixed names.

Decision: the modules land as `config/binding/types.ts`, `config/binding/schema.ts`, `config/binding/resolve.ts`, `config/settings/validate.ts`, `config/settings/read.ts`, `config/execution-profile/validate.ts`, and `config/execution-profile/read.ts`. `config/execution.ts` ceases to exist and no barrel, index, or re-export replaces it; every consumer imports the one module it needs.

Rationale: the three directory names are the three reasons to change that this separation exists to isolate, so the directory listing states the argument for the split without a filename prefix re-encoding it. `validate.ts` and `read.ts` carry the same names and the same meanings they already carry under `state/checkpoint/`, so the two areas read alike. The trade-offs accepted: the `execution.ts` name disappears, and `config/binding/` groups three genuinely different kinds of module — declarations, validation, and resolution — which is a weaker grouping than either document folder.

## DR5: The declarations-only guard generalizes to cover both vocabularies

Context: `cli/src/architecture.test.ts` guards `state/checkpoint/types.ts` as a module that declares and does nothing — it asserts the module anchors on the document type it exists to declare, that every line at column zero opens or closes a declaration, that the source holds no runtime construct, and that the module reaches neither the execution nor the display domain. DR1 keeps `config/binding/types.ts` free of the timing default constants specifically so that the same property holds of it, and nothing enforces that property unless this thread extends the guard.

Decision: the existing guard is generalized to run over a set of declaration-only vocabulary modules containing both `state/checkpoint/types.ts` and `config/binding/types.ts`, rather than gaining a second block. Each module keeps its own anchor assertion naming a type it must declare, so the guard still proves which file it is reading, and the execution/display inversion check applies to both. `cli/AGENTS.md`'s contract line describing this guard is reworded from the singular in the same change.

Rationale: duplicating the declaration and runtime-construct patterns into a second block would put the same two definitions of "declaration-only" in two places, where one can be relaxed without the other. A binding type has no more business naming an engine or renderer type than a checkpoint field does, so the inversion rule transfers unchanged. The cost accepted is that comments written to justify one module's guard become slightly more abstract when they must justify a category.

## DR6: Tests follow the modules, and the twin-run becomes a base-path wiring check

Context: `cli/src/config/execution.test.ts` covers the whole area in five blocks — the settings container, the shared stage-binding schema, catalog stage coverage, the execution-profile document, and selected stage binding resolution. Its schema block is a fifteen-case table run twice, once through a settings document and once through a profile, which is the current executable proof that the two documents accept and reject identically. Every case reaches the schema by writing a real file to a temporary directory and calling a loader, which DR2 makes unnecessary for validation.

Decision: the test file divides to follow the modules. The schema case table runs once, directly against the shared validator with no filesystem, and absorbs both catalog-coverage cases. Each document's validator test covers its own envelope, plus a small number of cases asserting the field path its diagnostics carry — `afk.stages.<stage>.…` for settings against `stages.<stage>.…` for a profile — so that each document is proven to delegate to the shared schema at the right base path. Each document's loader test covers the missing-file semantics, JSON syntax errors, and the failure shape that loading it produces. Resolution gets its own test beside `config/binding/resolve.ts`.

Rationale: the twin-run existed because the two documents' schemas could drift apart; once both delegate to one module, the import graph fixes that and re-running fifteen cases through two envelopes asserts it a second time for nothing. What is not structural is which base path each document hands the schema — get it wrong and every diagnostic in that document names a field path the user cannot locate — so that one property is kept as a handful of cases rather than dropped with the rest of the duplication.

## DR7: Validators return a discriminated union, and the disk-facing file is `load.ts`

Context: supersedes the file-name half of DR4, which named the disk-facing module in each document folder `read.ts`. The validators being separated by DR2 currently take an `errors: string[]` out-parameter and return a partial value, leaving the caller to notice failure by inspecting the array — workable while they are private functions, but a poor module boundary. The two documents' failure shapes differ for a substantive reason: the settings loader computes its own path from the config root, so its result is the only way a caller can name the file, while the profile loader is handed an already-resolved path that its caller uses directly in a refusal.

Decision: each validator takes a parsed root and returns a discriminated union, with no out-parameter and no partial value returned alongside a separate error list; `config/binding/types.ts` declares those unions alongside the result types it already owns. The profile validator and profile loader both return the same profile result union. The settings validator returns a union carrying the stage map or the errors, and its loader returns that same outcome with the resolved `sourcePath` attached on failure, because only the loader knows the path. Diagnostic content and order are unaffected — what changes is which module assembles the outcome. The disk-facing file in each document folder is named `load.ts`, and the exported functions keep the names `loadStageSettings` and `loadExecutionProfile`.

Rationale: a union makes an unhandled failure a compile error rather than a forgotten length check, and matches how the checkpoint declares its own validation outcome once and returns it from both validation and loading. The settings asymmetry is preserved rather than designed away because it reflects who resolves the path, and flattening it would change what a refusal can display. On naming, renaming the exported functions to `read*` purely for filename parity with `state/checkpoint/` would churn every call site and the module-layout prose to buy symmetry in a word; the parity worth keeping is structural — a folder of declarations, pure validation, and one disk-facing module — and naming the file after the verb its function already uses keeps the two agreeing.

## DR8: Documentation is two `cli/AGENTS.md` edits, and no scenario or README change is owed

Context: two lines of `cli/AGENTS.md` name the module this thread separates — a behavior bullet under "Execution model" that states the binding resolution rule and names the path parenthetically, and the `config/` entry in the module layout that lists `roots.ts`, `references.ts`, and `execution.ts`. Two standing repository rules also have to be answered: every distinct terminal rendering must be exercised by a demo scenario, and `cli/README.md`'s stage-support table must be updated whenever either side of the skill/CLI coupling moves.

Decision: the behavior bullet points at `config/binding/resolve.ts`, the one module that now implements the rule it describes. The module-layout entry names the three folders rather than the seven files, and carries the two facts a directory listing cannot give: that the binding vocabulary declares and does nothing, so the checkpoint can name a resolved binding without reaching a document loader, and that both documents validate their stage maps through one shared schema, which is what keeps their diagnostics from drifting apart. No demo scenario is added or extended, and `cli/README.md` is untouched, including its stage-support table.

Rationale: the layout entry earns an enumeration only where it attaches a constraint a reader cannot infer, which is how its neighbouring entries are written; listing seven filenames whose folders already name them would be an inventory of what the code plainly says. The two standing rules are answered by what this change cannot do: every rendering, diagnostic, and diagnostic ordering is held fixed, so no scenario reaches a screen it did not already reach, and nothing touches a skill's posture, the stage catalog, target resolution, artifact-state interpretation, or a stage prerequisite, so neither answer the README table gives can move.
