# Decisions — Let users choose and compose the stages a run executes

## DR1: Trusted stage catalog and declarative pipeline composition

Context: Users need to start an existing pipeline after work they have already completed and create custom pipelines from Antmay's supported unattended capabilities. A stage carries safety-critical behavior beyond its skill name, including its invocation target, Git policy, queue handling, prerequisites, and promised outputs. Whether a sequence can run depends on the selected thread's artifacts and on artifacts produced by earlier selected stages, rather than on a fixed list of allowed adjacent stages.

Decision: The CLI will own a catalog of supported stage definitions. Each definition adapts one supported Antmay skill into an unattended stage and fixes its invocation target, Git policy, queue behavior, artifact prerequisites, and promised artifact outputs. User-authored JSON pipeline documents may select and order entries from this catalog but may not define new skills or override the catalog's safety behavior. The built-in Standard pipeline will be expressed through the same pipeline-document schema as custom pipelines. Before allocating a run, the CLI will strictly validate the complete pipeline document and verify that each selected stage's prerequisites are satisfied either by the thread's current artifacts or by the declared outputs of earlier selected stages. It will recheck concrete prerequisites immediately before each stage and verify promised outputs after a successful attempt.

Rationale: This boundary gives users meaningful composition—such as choosing between strict-plan implementation variants or using the brief-plan implementation path—without exposing trusted Git and queue policies as user configuration. Artifact contracts admit a stage at the beginning when its input already exists and reject the same stage when it does not, whereas pairwise before/after rules would duplicate those contracts, reject valid entry points, and grow brittle as the catalog expands. Using one strict JSON schema for built-in and custom pipelines exercises the same validation path and provides a maintained working example.

## DR2: Portable pipelines and explicit local execution profiles

Context: Pipeline definitions should be shareable across users, while harness and model availability, cost tolerance, and operational preferences are local to one user's environment. A universal harness or model default can silently assign an expensive model to a newly supported stage or an inadequate model to a load-bearing stage. An optional alternate execution configuration therefore needs a safe fallback that does not reintroduce such a catch-all.

Decision: Pipeline documents will contain portable stage structure and may attach shared stage instructions, but they will contain no harness, model, idle-timeout, or heartbeat selections. The `afk.defaults` catch-all will be removed from `settings.json`; `afk.stages.<stage-id>` will instead hold the user's explicit local fallback binding for each supported stage. Named alternate execution profiles will be strict JSON documents under `<config-root>/profiles/<name>.json` and selected explicitly with `antmay afk run ... --profile <name>`. A selected profile may map any supported stage to a local execution binding and may omit stages, with omitted selected stages falling back to their explicit `settings.json` stage entry. A profile entry replaces the corresponding settings entry; its `harness` and `model` form a required pair, with local operational fields such as idle timeout and heartbeat allowed alongside them. If any selected stage has no complete binding after resolution, preflight will refuse before allocating a run. Resume will use the fully resolved profiles snapshotted in the checkpoint and will reread neither settings nor profile documents.

Rationale: Separating portable pipeline intent from local provider choices lets users share one pipeline while maintaining several named policies such as budget or maximum-quality. Per-stage settings make every newly supported stage fail closed until the user assigns it deliberately. A first-class profile document avoids coupling local choices to pipeline names inside `settings.json`, permits several execution policies for one pipeline, and keeps the common one-policy case simple because no profile file or flag is required.

## DR3: Enter a pipeline by stage ID

Scope: `antmay afk run`

Context: The primary abbreviated-run workflow is to omit an already completed prefix of an existing pipeline and begin with a later stage. Numeric skip counts become unstable when a pipeline changes, while general inline omission and reordering would duplicate the custom pipeline document format.

Decision: `antmay afk run` will accept an optional `--from <stage-id>` argument whose named stage is included in the run. The CLI will structurally validate the complete source pipeline, select the named stage and every stage after it, and validate that selected suffix against the thread's current artifacts without crediting outputs promised by skipped stages. The checkpoint will snapshot only the selected executable stages while retaining the source pipeline identity for display. Omitting `--from` selects the complete pipeline. An unknown stage ID or an unsatisfied selected-stage requirement will refuse before run allocation. A pipeline document must not contain the same stage ID more than once.

Rationale: Stable stage IDs make the invocation readable and resilient to unrelated insertions earlier in the pipeline. Treating the selected suffix as the actual run avoids falsely recording skipped work as completed. Unique stage IDs keep entry selection, execution-profile mappings, diagnostics, logs, and resume unambiguous; arbitrary omission and reordering remain expressible through a custom pipeline document without adding a second inline composition language.

## DR4: Symmetric pipeline and profile references with no bundled pipeline

Context: Pipelines are portable user-authored documents and execution profiles are local user documents, but both need a convenient config-root name form and an explicit path form. Resolving a reference by first testing whether a same-named file happens to exist would make command meaning depend on the working directory and could turn a mistyped path into an unintended config-root lookup. This decision supersedes DR1 only where DR1 calls the Standard pipeline built in, and extends DR2's profile selection beyond config-root names.

Decision: The CLI will bundle the trusted stage catalog but no runnable pipeline document. `antmay afk run` will require a pipeline reference, and `--profile` will accept an optional execution-profile reference. Both references use the same syntactic resolution: a bare kebab-case name resolves to `<config-root>/pipelines/<name>.json` or `<config-root>/profiles/<name>.json` according to its role, while a reference with an explicit directory component resolves as a filesystem path relative to the invocation working directory or as an absolute path. A bare filename such as `standard.json` is invalid and will instruct the user to choose either the bare name `standard` or the explicit path `./standard.json`. A missing explicit path will not fall back to name lookup, and a missing named document will not search the working directory. The README will publish a complete Standard pipeline document that a user can copy to `<config-root>/pipelines/standard.json`; automatic provisioning through an initialization command or installation hook is outside this thread.

Rationale: Matching pipeline and profile resolution makes the command predictable while supporting both shareable repository files and convenient user-local names. Syntactic resolution gives every invocation one stable meaning regardless of incidental filesystem state. Shipping only the stage catalog also keeps the CLI's trusted behavior in code while allowing every executed pipeline, including Standard, to pass through the same external-document loader and validator.

## DR5: Artifact-state contracts define fail-fast composition

Context: Stage compatibility depends on durable artifact state rather than adjacency. A selected stage may consume an artifact already present in the thread or one guaranteed by an earlier selected stage, and artifacts with the same root filename can have materially different shapes: `plan.md` may represent a brief plan or the index of a strict plan. The CLI can recognize artifact presence and bounded structural shape but cannot judge whether freeform Markdown is semantically adequate.

Decision: Every catalog stage will carry a declarative, serializable artifact-state contract describing its prerequisites and promised state transition. The generic artifact model will distinguish at least a valid thread, proposal presence, spec presence, plan state (`absent`, `brief`, or `strict`), and implementation-report presence. Before run allocation, the CLI will inspect the thread's concrete initial state, apply the `--from` selection, walk all selected stages in order, check each stage's prerequisites, and apply its promised transition to the simulated state used for subsequent stages. It will refuse the first impossible composition with diagnostics naming the stage, required state, observed or simulated state, and relevant preceding stages. Immediately before each stage, the runner will re-inspect concrete prerequisites; after a recognized `DONE`, it will verify the promised output state before advancing or committing the stage boundary. A missing or structurally mismatched promised output will pause as a stage-contract violation. The CLI's structural recognition will be bounded to facts such as non-empty artifact files and the presence or absence of a non-empty strict-plan task structure; each skill retains responsibility for deeper artifact consistency and semantic quality.

Rationale: Simulating artifact transitions rejects mismatches such as `plan-brief` followed by `implement-plan` before any agent is launched, while still allowing a later stage to begin a run when its prerequisite already exists. Rechecking the real state at each boundary prevents a terminal `DONE` from substituting for the promised artifact. Declarative serializable predicates preserve deterministic checkpoint and resume behavior without duplicating skill-specific semantic review inside the CLI.

## DR6: Initial catalog covers every eligible fixed-target skill

Context: A skill can participate in an unattended pipeline only when the executor can invoke it without live human input or missing invocation parameters, validate its artifact contract, and bound its tracked effects safely. Completion-oriented skills differ on those properties, so terminal-outcome support alone does not make a skill a valid stage.

Decision: The initial stage catalog will contain fourteen skills: `propose`, `reconcile-proposal`, `spec`, `reconcile-spec`, `review-spec`, `plan-brief`, `plan-strict`, `reconcile-plan`, `implement`, `implement-plan`, `implement-plan-with-subagents`, `roadmap`, `reconcile-roadmap`, and `review-roadmap`. A skill is eligible for a catalog entry when it is completion-oriented, accepts a deterministic invocation target derivable from the selected thread, exposes prerequisites and outputs through the artifact-state model, and keeps tracked changes within a statically bounded Git policy. The CLI README will include a user-facing table covering the Antmay skills, whether each is supported as a stage, and a useful explanation for every unsupported skill. Explanations will describe the user-visible limitation—such as needing live human decisions, caller-supplied candidate inputs, an explicit code reference, or dynamically created sibling threads—rather than internal development rationale.

Rationale: Covering every skill that already satisfies one coherent safety rule makes custom pipelines useful across proposal, delivery, and Roadmap authoring without expanding the runner into dynamic targets or broad Git authority. The explicit support matrix lets users predict which method capabilities can run unattended and why other capabilities remain deliberate human or separately parameterized operations.

## DR7: One object-only pipeline document schema

Scope: Pipeline JSON documents

Context: A pipeline stage may carry portable instructions, so supporting both bare stage-name strings and stage objects would create two equivalent representations and require normalization before validation, selection, display, and checkpointing. Pipeline identity and source provenance serve different purposes because an explicitly referenced file may be renamed without changing the identity its contents declare.

Decision: A pipeline document will be a strict JSON object with exactly three root fields: required `schemaVersion` equal to `0`, required non-empty kebab-case `name`, and required non-empty `stages`. Every `stages` entry will be an object with required `stage`, naming one catalog stage, and optional non-empty `instructions`; no string shorthand or pipeline-wide default instructions will exist. Stage IDs must remain unique per DR3, and unknown root or stage-entry fields will be validation errors. The declared `name` is the pipeline's display identity and need not match its filename; the checkpoint will separately retain resolved source provenance. Stage instructions will be appended after the catalog-owned skill trigger and target and will not alter artifact contracts, Git policy, or queue behavior.

Rationale: One canonical stage representation keeps authoring, strict validation, and checkpoint serialization deterministic while leaving room for intentional portable tailoring at the exact stage it affects. Separating declared identity from source location avoids turning ordinary file movement into a pipeline rename and preserves unambiguous diagnostics.

## DR8: Whole-stage local bindings use an atomic agent object

Scope: `settings.json` and execution-profile JSON documents

Context: A selected stage may obtain its local execution binding from an optional execution profile or fall back to global user settings. Merging harness and model independently could accidentally pair values intended for different providers, while requiring `settings.json` even when a selected profile covers every stage would add no safety. The term `executor` already names the Antmay process and checkpoint identity, so it cannot also name the external agent selection.

Decision: `settings.json` will contain optional `afk.stages.<stage-id>` bindings and no `afk.defaults`; the file itself will be optional and a missing file will behave as an empty stage map. An execution-profile document will require `schemaVersion: 0`, a non-empty kebab-case `name`, and a non-empty `stages` map, with unknown fields rejected and no requirement that the declared name match its filename. Both documents will use the same stage-binding shape: a required `agent` object containing required `harness` and non-empty `model`, plus optional positive-integer `idleTimeoutSeconds` and `heartbeatSeconds` siblings. The whole binding for a selected stage will come from its execution-profile entry when present, otherwise from `settings.json`; fields will not merge between those sources. Omitted operational fields will use the CLI's intrinsic defaults of 86,400 seconds for idle timeout and 300 seconds for heartbeat. Local bindings will contain no prompt or instructions. Profiles and settings may include unused supported stage IDs for reuse, but any unknown catalog stage ID will invalidate the containing document. If a selected stage resolves from neither source, preflight will refuse before run allocation.

Rationale: The `agent` object makes harness and model structurally indivisible while distinguishing the external agent choice from the Antmay executor. Whole-binding replacement prevents accidental cross-source combinations, optional settings permit a complete named profile to stand alone, and explicit per-stage coverage preserves the fail-closed behavior for newly added catalog stages.

## DR9: Defer proposal and Roadmap stages

Context: This supersedes DR6's initial catalog list. The proposal capabilities may change interaction posture, and the newer Roadmap capabilities need practical use before their unattended pipeline contracts are fixed. Technical eligibility is therefore a necessary condition for catalog support, not an obligation to expose a capability before its product behavior has settled.

Decision: The initial catalog will contain nine stages: `spec`, `reconcile-spec`, `review-spec`, `plan-brief`, `plan-strict`, `reconcile-plan`, `implement`, `implement-plan`, and `implement-plan-with-subagents`. `propose`, `reconcile-proposal`, `roadmap`, `reconcile-roadmap`, and `review-roadmap` will not be catalog stages in this release. The CLI README support table will label the proposal and Roadmap capabilities as planned and explain in user-facing terms that their unattended pipeline behavior is still being evaluated while those workflows mature, rather than presenting them as permanently unsupported or citing internal implementation constraints.

Rationale: A smaller catalog keeps the new composition contract on capabilities whose real unattended behavior is already understood. Marking the deferred capabilities as planned accurately communicates product direction without locking the CLI to stage contracts before the underlying suite workflows have been exercised and settled.

## DR10: Canonical prerequisites and state-resolved Plan Brief target

Context: Catalog stages are narrower unattended adapters around skills, but the CLI should enforce only artifact topology the skill genuinely requires. A header-only `decisions.md` is valid under the thread model, `proposal.md` is optional, and content sufficiency remains the invoked skill's responsibility. `plan-brief` can work directly from a valid thread or from a spec, and its explicit reverse-transition guard—not the CLI—decides whether a strict plan may be replaced.

Decision: The nine catalog stages will use these canonical prerequisites: `spec` requires only a valid thread; `reconcile-spec` and `review-spec` require a present spec; `plan-brief` requires only a valid thread; `plan-strict` requires a present spec; `reconcile-plan` requires a present strict plan governed by a present spec; `implement` requires a present brief plan; and both `implement-plan` variants require a present strict plan. The CLI will not require `proposal.md`, inspect the number of decision records, or assess whether durable input content is semantically sufficient. The `spec` target will be the thread root. The `plan-brief` target will resolve declaratively from the simulated artifact state: `spec.md` when a spec is already present or promised by an earlier selected stage, otherwise the thread root. That resolved repository-relative target will be snapshotted and inserted into the skill prompt. `plan-brief` may start with an absent, brief, or strict existing plan; its fixed Git policy will permit `plan.md` and the `plan-tasks/` subtree, and a successful attempt must leave a recognizable brief plan with no strict-plan task structure. When a strict plan exists, explicit replacement authorization may be carried in the pipeline stage's `instructions`; the skill interprets and enforces that authorization, while the CLI neither parses it nor blocks the invocation in advance.

Rationale: This division lets the CLI reject impossible artifact composition without duplicating content judgments and conditional authorization already owned by the skills. State-resolved targeting keeps direct `plan-brief` useful for lightweight work while ensuring `spec → plan-brief` actually hands the more precise spec to the planner. Allowing the skill's documented strict-to-brief branch preserves explicit user control, and the post-DONE brief-plan check still makes `plan-brief → implement-plan` fail during composition validation.

## DR11: Show the fully resolved execution before launch

Scope: `antmay afk run` startup display

Context: Per-stage local bindings eliminate implicit harness and model fallback, but a user may still forget an explicit choice made earlier. AFK execution is non-interactive, so visibility must not become a confirmation prompt that prevents unattended use.

Decision: After preflight succeeds and before the first agent attempt launches, the startup summary will display the pipeline's declared name and resolved source, the selected execution profile and its resolved source or `settings only`, the `--from` stage when present, and every selected stage in execution order with its resolved harness, model, and concrete repository-relative target. The display will be informational and will not ask for confirmation.

Rationale: Showing the complete resolved execution makes model cost, provider choice, entry point, and stage targeting auditable at the last useful moment without weakening unattended operation. It also lets users diagnose surprising resolution from terminal output rather than inspecting a checkpoint after an agent has already run.

## DR12: Document stage prerequisites in the support matrix

Scope: CLI README

Context: Users author pipeline documents by selecting catalog stage IDs and need to understand both which Antmay skills can run as stages and what artifact state each supported stage requires. A support-only table would force readers to infer prerequisites from validation errors or skill internals.

Decision: The CLI README's Antmay-skill support matrix will show every skill, whether it is supported as a catalog stage, and the prerequisite artifact state for every supported stage. For an unsupported skill, the same table will give the user-facing reason it is unavailable or mark the proposal and Roadmap capabilities as planned per DR9. The table will describe observable requirements and limitations rather than internal implementation rationale.

Rationale: Keeping support and prerequisites together gives pipeline authors one discoverable reference for valid composition and explains unavailable capabilities in terms relevant to their workflows.

## DR13: Recognize plan state through bounded filesystem structure

Context: Composition must distinguish a brief plan from a strict plan without duplicating the skills' deeper parsing and consistency checks. Ambiguous filesystem residue cannot safely count as either shape because it could route a pipeline to the wrong implementation skill.

Decision: The CLI will classify plan artifact state using bounded structural rules. `absent` means neither `plan.md` nor `plan-tasks/` exists. `brief` means `plan.md` is a non-empty regular file and `plan-tasks/` is absent. `strict` means `plan.md` is a non-empty regular file and `plan-tasks/` is a directory containing at least one non-empty regular Markdown task file. Every other observable combination is `malformed`, including task storage without an index, an empty or non-regular index, a non-directory `plan-tasks` path, a task directory with no recognizable non-empty Markdown task, or an inspection error. When selected-stage validation needs plan state, a malformed state will cause preflight refusal. A successful `plan-brief` attempt must leave `brief` state, and a successful `plan-strict` attempt must leave `strict` state. The CLI will not parse the strict index's task list or verify task ordinals and cross-file consistency; the consuming skills retain those deeper checks.

Rationale: These rules are sufficient to reject shape mismatches such as sending a brief plan to a strict-plan implementer and to verify authoring-stage postconditions, while leaving semantic Markdown validation with the skills that own the artifact formats.

## DR14: Keep stage discovery in documentation with one root maintenance rule

Context: Pipeline authors need a maintained support and prerequisite reference, but a dedicated catalog command would expand the v0 command surface and terminal-rendering obligations for information already documented in the CLI README. Changes affecting that table can originate in either the published skill suite or the CLI's stage interpretation, and repository guidance requires cross-module facts to live once at the root rather than be duplicated in module-specific agent files.

Decision: The CLI will not add an `antmay afk stages` command in this change. `cli/README.md` will remain the official user-facing stage-support and prerequisite reference per DR12. Root `AGENTS.md` will gain one cross-module synchronization rule requiring the README table to be updated in the same change whenever a suite skill's invocation posture, accepted inputs, durable outputs, or side-effect boundaries change in a way that affects stage eligibility or prerequisites, and whenever the CLI stage catalog, target resolution, artifact interpretation, or prerequisites change. This rule will not be duplicated in `cli/AGENTS.md` or `suite/AGENTS.md`.

Rationale: A precise repository-level maintenance obligation keeps documentation aligned with executable behavior without adding a runtime documentation command or violating the repository's one-fact-one-agent-file convention. Scoping the rule to behavior that can affect the table avoids ceremonial edits for unrelated skill wording or formatting changes.

## DR15: Pause and recover deterministically from runtime contract violations

Context: Pipeline preflight validates simulated artifact composition, but concrete thread state can change before a stage starts, and an invoked skill can return `DONE` without leaving the artifact state promised by its catalog contract. The executor must neither invoke a stage whose real prerequisite is absent nor treat a structurally invalid result as a successful stage boundary.

Decision: Immediately before every stage attempt, the executor will re-inspect the concrete artifact state and pause before invoking the agent when the stage prerequisite is unmet. After a recognized `DONE`, it will verify the stage's promised output before applying the Git boundary or advancing. An unmet postcondition will pause the run on the same stage with a `stage-contract-violation` that reports the expected and observed state. On resume, a prerequisite pause will be rechecked and the stage will start once its requirement is restored. For a postcondition pause, resume will first recheck the promised output: if a human repair now satisfies it, the executor will continue Git finalization without invoking the agent again; if it remains unsatisfied and the worktree is clean, the executor will start a fresh attempt of the same stage; if it remains unsatisfied and the worktree is dirty, the run will remain paused and require those changes to be repaired or reverted.

Rationale: Boundary checks preserve fail-fast safety after preflight without turning bounded artifact recognition into semantic validation. The recovery rules support deliberate human repair, avoid repeating a stage whose output has already been corrected, and provide a natural retry after an unsuccessful attempt has been discarded.
