# Decision Log

## DR1: Keep the four attempt dispositions and express them as union arms

Scope: `AttemptResult` and `AttemptRecord` in `cli/src/state/checkpoint/types.ts`

Context: `AttemptResult` names four dispositions — `executing`, `done`, `waiting`, `interrupted` — while `AttemptRecord` is one flat shape carrying every disposition's data as optional fields. Making that record precise raises whether the vocabulary itself has the right cardinality: a `done` attempt records `pendingFiles` when its post-attempt queue observation found pending work and records no such key otherwise, so a union keyed on the four existing values leaves that one field optional on the `done` arm. Splitting `done` into an advanced disposition and a queue-blocked one would make it required on exactly one arm.

Decision: The durable vocabulary keeps its four values, and `AttemptRecord` becomes a discriminated union over them. The `executing` arm carries `terminalResult: null` and neither `endedAt` nor `headAfterAttempt`. Both settled dispositions require `endedAt` and `headAfterAttempt`. The `done` arm requires a `terminalResult` whose token is `DONE`. The `waiting` and `interrupted` arms require `failure`, whose `kind` is typed as `WaitingKind` rather than a bare string. `execution/attempts.ts:attemptInterval` is removed: it exists only to re-derive the post-attempt `HEAD` observation that the settled arms now require, and its failure branch is unreachable once the type states it.

Rationale: Three of those four invariants are enforced nowhere today, and the fourth — the post-attempt `HEAD` observation — is what `attemptInterval` re-checks behind an `InvariantResult` failure that every caller threads onward and nothing can trigger, so the union both states the invariants and deletes real code. Splitting `done` was rejected because it mixes two axes: whether the thread's queue held pending work is a fact about the thread, while `AttemptResult` is the disposition of one attempt, which is identical in both cases. The relation that split appears to buy — a `resume-finalized-done` recovery naming the queue-blocked attempt — holds between `waiting.recovery` and one element of `attempts`, which no type expresses and checkpoint validation therefore owns regardless. The trade-off accepted is that `pendingFiles` stays optional on the settled arms; how a settled attempt records its queue observation is a question about that field's representation and is settled separately. Nothing outside checkpoint validation branches on `result`, so neither option was constrained by consumers, and a later split remains available if that separate question concludes the observation belongs in the disposition.

## DR2: A settled attempt records its queue observation as an explicit two-case value

Scope: the post-attempt queue observation on the settled arms of `AttemptRecord`, `cli/src/state/checkpoint/types.ts`

Context: DR1 leaves `pendingFiles?: string[]` optional on the settled arms of the attempt union, and the absence of that key carries meaning: settlement turns a failed queue scan into an empty list, and an empty list is then recorded as no key at all, so an absent key means either that the scan observed nothing pending or that it could not complete. The field has one consumer — the finalization of a saved `DONE`, which reads it to decide whether the stage's declared `rerun` queue resolution applies or the run advances — and that consumer treats both meanings as "nothing pending". It must read the recorded observation rather than scanning afresh, because the pause it is resuming from is where a human resolved the bundles, so a fresh scan would find them gone and a `rerun` resolution would never apply; reading the pause's own reason kinds instead is closed off by the rule that keeps resume paths from branching on them.

Decision: The settled arms carry the observation as a required value with two cases — observed, carrying the sorted list of pending files it found, which may be empty; and unavailable, carrying no list. The optional `pendingFiles` key on an attempt is replaced by it. The unavailable case carries no message, because the scan's failure is already reported as the pause's `gate-error` reason. The `executing` arm carries no observation at all, the observation being made at settlement.

Rationale: A failed scan is not an empty queue, and the one place that difference decides anything treats them alike today — which is reachable: a last-stage attempt whose queue scan fails and whose Git boundary is refused pauses, and the resume that finalizes it reads "nothing pending", advances the cursor past the final stage, and completes, the completion path running no queue gate. About half the catalog's stages declare `rerun`, so the ambiguity governs a live decision rather than a hypothetical one. Making the two cases distinct converts a silent default into a case the compiler requires an answer for. The trade-off accepted is that this forces a decision about what finalization does with an unavailable observation, which changes run behavior and is settled separately.

## DR3: An unavailable queue observation applies the stage's declared resolution

Scope: finalization of a saved `DONE`, `cli/src/execution/entry/finalize.ts`

Context: DR2 makes a settled attempt's queue observation an explicit two-case value, so the finalization of a saved `DONE` has to state what the unavailable case does. Only stages declaring the `rerun` resolution are affected, since an `advance` stage advances on either answer, and about half the catalog declares `rerun`. Pausing on the unavailable case alone is not available: the recorded observation cannot change, so every resume would re-decide it identically. Elsewhere the engine already answers this same unknown — a `DONE` attempt whose post-attempt queue scan fails while its Git boundary holds settles as `waiting` under a governing `gate-error` with a `retry-stage` recovery, so the stage runs again.

Decision: An unavailable observation applies the stage's declared queue resolution as though pending work had been observed. A `rerun` stage becomes ready and runs again; an `advance` stage advances. Finalization performs no queue scan of its own: the re-entered stage's queue gate makes the fresh observation, so bundles that are still present are caught there and a scan that fails again pauses with a `gate-error` on current evidence.

Rationale: This gives the same answer the engine already gives an unavailable scan one branch over, so the finalization path stops being the one place an unknown queue resolves to "nothing pending". It errs toward re-running a stage rather than carrying a run past work that may exist, and it adds no filesystem access to a module that owns the Git boundary — the queue gate it hands back to already performs that scan. The cost accepted is a wasted stage rerun when the scan failed and nothing was in fact pending, which for an implementation stage is a real expense. One gap stays open and outside this thread: an `advance`-resolution final stage reaches completion without any queue check, because the engine's completion path runs no gate.

## DR4: The waiting kind becomes a true discriminant, and the kind-to-evidence pairing is declared once

Scope: `WaitingKind` and `WaitingReason` in `cli/src/state/checkpoint/types.ts`

Context: `WaitingKind` names thirteen reasons a run pauses, and `WaitingReason` carries every kind's evidence as optional fields on one flat shape. A union keyed on the existing kinds would not fix that, because a kind does not determine its evidence: `stage-contract-violation` is assembled by four builders carrying, respectively, diagnostics; artifact mismatches; diagnostics with a candidate line; and artifact mismatches with a detail note and a candidate line. `stage-prerequisite-unmet` splits the same way — diagnostics when the check could not run, artifact mismatches when it ran and failed. Arms drawn around those kinds would have to leave every evidence field optional, which is the flat shape again. The distinction hiding under one kind is whether the check ran and failed or could not run at all, which is a difference in evidence rather than in what the pause is called.

Decision: The kinds whose evidence is not functionally determined are split so that every kind determines exactly one evidence shape: `stage-contract-violation` and `stage-prerequisite-unmet` each become an unmet kind and an uninspectable kind, taking the vocabulary to fifteen. The pairing of each kind with the evidence shape it carries is declared exactly once, as one table total over the kind union, and the `WaitingReason` union is derived from that table rather than written out beside it.

Rationale: Keeping one discriminant is what makes an evidence shape unconstructible under the wrong kind; a second, independent evidence discriminant on the same value would leave a `pending-queues` reason carrying artifact mismatches representable, replacing one illegal state with another. One table total over the kind union is the shape `recovery.ts` already uses to pair each recovery kind with the evidence its decision rests on, so extending the pause vocabulary fails to compile until the new kind states what it carries — which is the point of the exercise, and what lets the several places that currently restate the pairing read one declaration instead. The cost is two more durable kind values with their own terminal banners, and the fixture churn of a durable vocabulary change.

## DR5: The reason fields the kind-to-evidence table leaves over

Scope: `WaitingReason`'s shared optional fields and `WaitingDiagnostics` in `cli/src/state/checkpoint/types.ts`

Context: DR4 makes each waiting kind determine one evidence shape, which leaves three fields that pairing does not resolve. `detail` is carried by two kinds with unrelated meanings — the agent's own reason text after a `BLOCKED` or `REFUSED` token, and a canned note about who owns the uncommitted changes on a refreshed contract violation — and the terminal prints both under one key. `candidateLine` is stored on the blocked and refused kinds, on contract violations, and on boundary reasons, while the renderer draws it for `malformed-outcome` alone; it also duplicates the attempt's own `terminalResult.candidateLine`, which the refresh path reads it back off of in order to copy it onto the reason. And `WaitingDiagnostics` is one bag of three optional fields filled three different ways, which by its own contract is recorded for later inspection and never rendered.

Decision: `detail` ceases to exist as a shared field: the blocked and refused evidence carries the agent's reason text under its own name, and the contract-unmet evidence carries the preservation note under its own. `candidateLine` is carried by `malformed-outcome` alone, where it is that kind's evidence, and is removed from the blocked, refused, contract, and boundary kinds. Both it and the agent's reason text are required and nullable rather than optional, and that treatment applies wherever an absent value is a real state rather than a missing key. `WaitingDiagnostics` is replaced by the two producing situations naming their own required fields — a signal origin for an interruption, error text for a check that could not run — with no union or table over them.

Rationale: One field meaning two things is the same defect as one shape covering several states, and naming each separately makes neither kind able to pick up the other's. Keeping `candidateLine` on the one kind that renders it holds the display seam where it is: the reason renderer receives no attempt, so removing it from that kind would mean widening the paused display event to carry what the reason already holds. Required-and-nullable matches `TerminalResult.candidateLine`, so the two agree, and it applies the discipline DR2 established — a builder states the value instead of omitting the key. Diagnostics are deliberately left lighter than the rest: nothing reads them, so a contradictory bag costs nothing, and the two shapes have nothing in common beyond being diagnostic, which makes a seam over them decoration. The trade-off accepted is that for the kinds that lose `candidateLine`, the attempt's `terminalResult` becomes the only record of that line, so a pause read in isolation from its attempt no longer shows it — which is what the terminal already did.

## DR6: The checkpoint states its own pause correlation; the attempt-history relation stays with validation

Scope: `RunCheckpoint` in `cli/src/state/checkpoint/types.ts`

Context: `RunCheckpoint` carries `condition` and `waiting: WaitingInfo | null` as independent fields, so a `waiting-for-user` document with a null pause and a `completed` one carrying a pause are both constructible. Two further relations sit at the same level: an `executing` run's final attempt must exist and be the executing one, which checkpoint validation proves in a dedicated function and a resume then re-asserts with a non-null index on the history's tail. The element type of the `attempts` array is already changing under DR1, so the validator's construction of that array is being rewritten in this thread regardless.

Decision: `RunCheckpoint` becomes a union over its condition: the `waiting-for-user` arm carries a non-null `WaitingInfo`, and the `ready`, `executing`, and `completed` arms carry `null`. The relation between an `executing` condition and the history's final attempt is not moved into the type — a trailing-element tuple could express it, and it is deliberately left for validation to own. Checkpoint validation keeps proving both relations, since it reads untrusted JSON and constructs the value the union describes.

Rationale: The pause correlation is a two-arm union in a file this thread already rewrites, and without it the thread would deliver a precise attempt and reason vocabulary inside a container that still admits a paused run with no pause. The trailing-tuple form was rejected on cost: it buys one non-null assertion and one validator function while introducing the least readable type in the design, and it needs nothing this thread establishes, so it remains available separately.
