# Decisions — Give harness identity, the outcome vocabulary and the checkpoint module a single owner

## DR1: The terminal-outcome guard bans only the forms the compiler cannot catch

Scope: `cli/src/architecture.test.ts` and every production module naming a terminal-outcome token

Context: The terminal-outcome tokens `DONE`, `BLOCKED` and `REFUSED` appear in production in five structurally different forms: inside a string literal (`harness/backends/sandcastle.ts`, `runner/classify.ts`, `harness/scripted/cases.ts`), as an independently declared type union (`state/checkpoint.ts`), as a `ReadonlySet<string>` of the token strings (`state/checkpoint.ts`), as a comparison against the already-narrowed union (`runner/classify.ts`, `execution/phases/settlement.ts`, `state/checkpoint.ts`), and as display labels naming the `outcome-refused` and `outcome-blocked` event kinds (`display/execution.ts`). TypeScript rejects a comparison whose literal has left the union (TS2367); it rejects none of the other forms. The thread must decide what the new single-owner guard forbids outside `runner/outcome.ts`.

Decision: The guard fires on exactly the three forms the compiler cannot catch — a terminal-outcome token embedded in a string literal, an independent redeclaration of the token union, and an untyped runtime collection of the token strings — anywhere outside `runner/outcome.ts`. Comparisons against the narrowed union are left as they are, and the `display/execution.ts` labels naming the `outcome-refused` and `outcome-blocked` event kinds are out of the guard's subject: they label an event kind, not the protocol. The sites that must therefore derive from the owner are `harness/backends/sandcastle.ts`'s `COMPLETION_SIGNALS`, `state/checkpoint.ts`'s inline `TerminalResult.token` union and its `TERMINAL_TOKENS` set, `runner/classify.ts`'s `EXPECTED_PREFIXES` and its `Outcome: ${token}` message template, and every fabricated `finalText` in `harness/scripted/cases.ts`. The guard's subject is `productionModules()`, which excludes `*.test.ts` and `test-helpers/`, so `test-helpers/fake-harness.ts` is not held to it.

Rationale: The defect class this thread exists to close is silent breakage — a token change that leaves a consumer watching for strings that no longer appear, with a green build. A comparison is not in that class, because the compiler already fails it; banning it would be churn that buys no guarantee and would leave the `display/execution.ts` labels needing an exemption that makes the rule read as arbitrary. `harness/scripted/cases.ts` is in that class and is worse-placed than the Sandcastle adapter the issue leads with: it would turn the demo catalog red with no build error, and the demo sits outside `npm run check`. The trade-off accepted is a two-clause rule rather than a one-clause one, which needs a comment in the guard explaining why a comparison is exempt.

## DR2: The checkpoint vocabulary module is guarded as declarations-only, not by an import allow-list

Scope: `cli/src/state/checkpoint/types.ts` and its guard in `cli/src/architecture.test.ts`

Context: Splitting `state/checkpoint.ts` produces a vocabulary module holding the sixteen exported types the file declares before its first constant. Those types reference six other modules by type-only import — `thread/artifacts.ts`, `pipeline/catalog.ts`, `pipeline/types.ts`, `config/execution.ts`, `workspace/types.ts`, and whichever module owns `HarnessId` — plus the terminal-outcome token type per DR1. A guard was wanted to stop a validator from being added back into the vocabulary module later, and the question is what that guard asserts. Holding the module to importing only `src/shared/` and `src/thread/` is not available: five of those references lie outside both trees, and `src/shared/` is referenced by the validators rather than by any type.

Decision: The guard asserts that `state/checkpoint/types.ts` contains nothing but `import type` statements and `export type` / `export interface` declarations — no value import, no `const`, no `function` — and additionally that it references neither `execution/` nor `display/`. The declarations-only clause is the load-bearing half; the direction clause is a single additional line.

Rationale: An import allow-list constrains which domains a type may name, when the property actually worth guarding is whether the module can run anything at all. Declarations-only settles that by construction — a module with no value import and no non-type declaration cannot hold a validator — and it needs no maintenance as the vocabulary grows, where an allow-list needs an edit for every legitimate new type reference and still admits a validator that reaches only allow-listed modules. The clause holds today with no change to the code being moved: the region is sixteen `export type` declarations and nothing else, every runtime constant in the file (`RUN_CONDITIONS`, `ATTEMPT_RESULTS`, `WAITING_KINDS`, `TERMINAL_TOKENS`, `ISO_UTC`) sitting below them and module-private. The direction clause guards an inversion that has not happened, and is included because it costs one line and nothing in the moved region reaches either domain.

## DR3: Splitting the checkpoint module retargets its four references in the architecture guards and deletes none

Scope: `cli/src/architecture.test.ts`

Context: `architecture.test.ts` names `state/checkpoint.ts` in four places, not the three the thread's originating issue describes, and only two of them are exemptions. `:216` asserts that the atomic writer imports the document type and nothing else. `:413` exempts the module from the pause-literal rule, because `PAUSE_LITERAL` cannot distinguish a type literal from a value literal and trips on the `WaitingInfo` type declaration at `checkpoint.ts:147-148`. `:493` exempts it from the recovery-kind-comparison rule, because the validator tests `kind` against untrusted JSON and has no narrowed union to switch on (`checkpoint.ts:712,716,724` and `:1114,1143,1151`). `:591` is an assertion rather than an exemption: its only use, at `:656`, requires that the transition applier depend on the module declaring the document's fields. The question is what the split commits to for these four.

Decision: All four references are retargeted and none is deleted. `:216` becomes `["state/checkpoint/types.ts"]`; the pause exemption at `:413` becomes `state/checkpoint/types.ts`; the recovery-kind exemption at `:493` becomes `state/checkpoint/validate.ts`; the assertion at `:591`/`:656` becomes `state/checkpoint/types.ts`. `PAUSE_LITERAL` is left exactly as it is. A reduction in the number of exemptions is not an acceptance criterion for this work.

Rationale: Neither exemption is residue. A guard that recognizes a shape by its literal form must exempt the module that declares that shape, and a validator of untrusted JSON must compare against string values whatever module it lives in — so both are irreducible on their own terms, and what the split actually buys is that each one names a small single-purpose module instead of a 1,204-line one holding vocabulary and validator together. Tightening `PAUSE_LITERAL` to stop matching type declarations would make one exemption deletable, but the regex earns its keep by being blunt: one clever enough to tell `reasons: WaitingReasons;` from `reasons: [...]` is one that will miss a hand-assembled pause later, which trades the guard's teeth for a deleted line. Treating the exemption count as a target would also invert the rule in `cli/AGENTS.md` that a failing guard is an argument about direction — the direction here is sound, and chasing the count would drive restructuring nothing else motivates.

## DR4: Harness identity moves to a dedicated `harness/id.ts` that also owns the narrowing predicate

Scope: `cli/src/harness/id.ts`, `cli/src/config/execution.ts`, `cli/src/state/checkpoint/`

Context: `HarnessId` and `HARNESS_IDS` are declared by the settings parser in `config/execution.ts`, and the harness domain imports its own identity type from there. `HarnessId` is consumed by eight modules under `harness/` and by the checkpoint's `observedHarnessVersions` field. `HARNESS_IDS` has four production consumers: the private `isHarnessId` predicate and the diagnostic that lists the ids in prose, both in `config/execution.ts`, and two inline `.includes` membership tests in checkpoint validation. Untrusted narrowing therefore happens at three sites, only one of which uses the predicate, and `HARNESS_IDS` is declared `readonly string[]` — widened on purpose so an untrusted value can be tested against it directly.

Decision: `HarnessId`, `HARNESS_IDS` and an exported `isHarnessId` live in a new `harness/id.ts`, which `harness/provider.ts` imports for the `id` field on `AgentHarness`. The private predicate in `config/execution.ts` is deleted and all three narrowing sites — the settings validator and both checkpoint validation sites — narrow through the shared one. `HARNESS_IDS` is typed `readonly HarnessId[]`, with the single widening cast confined inside the predicate. The three sites share the predicate and not a message: each keeps its own diagnostic, since one narrows an object key and the others a field. The diagnostic that maps `HARNESS_IDS` into prose stays in `config/execution.ts`. This creates the first `config/` → `harness/` and `state/` → `harness/` edges; the `ID_COMPARISON` guard needs no change, because it matches only comparison forms and a bare array of the id literals is not one.

Rationale: A dedicated vocabulary module is what lets a settings parser and a checkpoint validator depend on exactly "which ids exist" rather than on `harness/provider.ts`, the declaration of what a harness *is* — the runtime cost of the latter would be nil, but it is the wrong dependency to state, and the vocabulary-module shape is the one already settled for the checkpoint types in DR2. Moving the predicate departs from the originating issue, which keeps it in config as a config concern; that holds for one narrowing site and there are three, two of them in checkpoint validation, where membership is currently hand-tested against a permanently widened array — structurally the same untyped-collection shape ruled against in DR1. Co-locating the predicate with the collection lets the exported type state the truth and confines the widening to one place.

## DR5: The terminal-outcome vocabulary stays in `runner/outcome.ts`, held to being a leaf

Scope: `cli/src/runner/outcome.ts` and its guard in `cli/src/architecture.test.ts`

Context: DR1 makes consumers in four domains derive the terminal-outcome tokens from a single owner — `runner/` for the parser and the user-facing prose, `state/` for the recorded token union and the validator's token set, `harness/` for the Sandcastle completion signals and the scripted cases' fabricated final text, and `execution/` through the parse type. No one domain is the sole consumer, and keeping the owner in `runner/` adds a `harness/` → `runner/` edge that makes an existing `runner/` → `harness/` pair bidirectional, plus a `state/` → `runner/` edge closing a domain-level loop through `runner/classify.ts`. `src/shared/` cannot hold the vocabulary, because its charter admits only primitives with no domain knowledge.

Decision: `runner/outcome.ts` owns the vocabulary, and the DR1 guard additionally asserts that `runner/outcome.ts` imports nothing at all.

Rationale: The leaf assertion is what makes the new edges safe rather than merely tolerable — a module that the build holds to importing nothing can be depended on from any domain without a cycle ever becoming possible, which reduces the domain-level loop to a naming artifact. Relocating the vocabulary into `harness/` would yield a strictly one-directional domain graph, but it would assert that the protocol belongs to the harness when both harnesses share it and it originates in the skill suite; the graph is not one-directional today in any case, since `harness/` already reaches `pipeline/`, `shared/`, `state/` and `workspace/`. A new leaf domain owned by no consumer would be truthful about a cross-domain contract but is the indirection `cli/AGENTS.md` calls decoration: it costs a reader a jump and returns nothing the leaf assertion does not already give.

## DR6: The `validateCheckpoint` decomposition is deferred; the missing multi-fault test is not

Scope: `cli/src/state/checkpoint/validate.ts` and `cli/src/state/checkpoint.test.ts`

Context: Splitting the checkpoint module three ways leaves a validator module of roughly 935 lines — the private section validators plus the single ~300-line exported `validateCheckpoint` — which makes it the largest production file in the tree, marginally ahead of `harness/scripted/cases.ts`. Decomposing `validateCheckpoint` further is not mechanical the way the file split is: most document sections already have private helpers, but the residue includes cross-section consistency rules that belong to no section, chiefly the recovery-reference checks that resolve a recovery against the attempt history. The contract such a decomposition must preserve is that the validator reports every problem in a document at once rather than failing on the first, and that contract is currently unverified: every assertion in `checkpoint.test.ts` takes the form `errors.some(…)`, so a validator that short-circuited on the first fault would pass the whole suite.

Decision: The `validateCheckpoint` decomposition is out of scope for this thread and belongs to a follow-up ticket. A test that pins the multi-fault contract — a document carrying several independent faults yields an error for each — is added within this thread, whether or not the decomposition ever happens.

Rationale: The criterion this work is measured against is one reason to change per file, and the validator module has exactly one; it fails a size heuristic rather than the criterion, at a size the tree already accepts elsewhere. Performing the decomposition here would stack a non-mechanical redesign onto a change that already narrows 27 importers and adds two guards, and would do so against a contract nothing currently holds — the worst combination for work required to keep `npm run check` green at every step. The test is separable from all of that, costs one case, and is the precondition the deferred work needs; leaving it out would mean the follow-up opens with the same blind spot. The trade-off accepted is scope the originating issue did not ask for, and a small helper to construct a document with several independent faults.

## DR7: The vocabulary includes the `Outcome: ` prefix, and no rendered text changes

Scope: `cli/src/runner/outcome.ts`, `cli/src/runner/classify.ts`, and the terminal-outcome guard in `cli/src/architecture.test.ts`

Context: This extends the guard subject settled in DR1, which reaches a terminal-outcome token embedded in a string literal but not the bare `Outcome: ` prefix. `runner/classify.ts` renders `The stage reported Outcome: ${parse.token} and paused for human attention.`, a string holding the prefix and no token, so the rule as first stated would pass it and would pass any later `"Outcome: " + token` — strings carrying exactly the silent-break risk the guard exists for, since the prefix is as load-bearing as the token values. Separately, `runner/classify.ts` renders the sentence `Outcome: DONE, Outcome: BLOCKED, or Outcome: REFUSED` to the terminal, which a uniform join over the token list does not reproduce.

Decision: `runner/outcome.ts` declares the token list, the `Outcome: ` prefix, and a builder composing a full outcome line from a token. The guard's complete subject is: outside `runner/outcome.ts`, neither a terminal-outcome token nor the bare `Outcome: ` prefix may appear in a string literal, no module may redeclare the token union, and no module may hold an untyped runtime collection of the token strings. Comparisons against the narrowed union and the `display/execution.ts` event-kind labels remain outside the subject, as settled in DR1. Every string reaching the terminal stays byte-identical, so the derived expected-prefixes sentence spells out the `or` before its last element rather than joining uniformly. No demo scenario is added or modified anywhere in this thread, and every existing scenario's markers must keep passing untouched.

Rationale: A rule that catches `"Outcome: DONE"` in the Sandcastle adapter but not the same string assembled one interpolation later in the classifier is a rule with a hole in the middle of its own subject. Requiring byte-identical terminal output is what keeps the work a refactor: the existing scenario catalog then acts as the cheapest available check on it, since any drift in rendered text turns a marker red without a scenario having to be written.
