# Give harness identity, the outcome vocabulary and the checkpoint module a single owner

Three concepts in the Antmay CLI are declared in more than one place, or in a place that does not own them, so a single logical edit lands in several files that nothing holds together. Harness identity (`HarnessId`, `HARNESS_IDS`) is declared by the settings parser in `src/config/execution.ts`, and eight modules under `src/harness/` reach up into `config/` for it; the fix is to move the identity into the harness domain — alongside `AgentHarness` in `harness/provider.ts`, or a dedicated `harness/id.ts` — and have `config/execution.ts` import it, leaving the module-private `isHarnessId` narrowing where it is, reading the moved collection. The terminal-outcome vocabulary has four independent declarations — the token union and `OUTCOME_RE` in `runner/outcome.ts`, an inline union and a `TERMINAL_TOKENS` set in `state/checkpoint.ts`, `COMPLETION_SIGNALS` in `harness/backends/sandcastle.ts`, and a prose repetition of the three full lines in `runner/classify.ts` — and the Sandcastle copy is the dangerous one, because changing the tokens leaves it watching for strings that no longer appear: the SDK stops recognizing completion, the attempt runs to its idle timeout, and nothing fails at build time. The vocabulary needs one owner in `runner/outcome.ts`, every other consumer deriving from it, and a guard in `src/architecture.test.ts` — written first, so its failure specifies the rest — holding exactly one module to declaring the tokens while every other consumer imports them. And `state/checkpoint.ts`, at 1,204 lines the largest and most depended-upon production file (28 importers, 27 of them production), holds three unrelated reasons to change at once: the durable domain vocabulary, the untrusted-input validator, and the file reader. It splits along its existing strata into `state/checkpoint/types.ts`, `state/checkpoint/validate.ts` and `state/checkpoint/read.ts`, with importers narrowed properly rather than papered over with a re-export barrel — that is settled, not open, since a barrel would preserve the exact property that caused the problem. The three `state/checkpoint.ts` exemptions in `src/architecture.test.ts` (in the pause, recovery-evidence and durable-transition guards) should become deletable afterwards, and a new guard should hold `checkpoint/types.ts` to importing nothing but `src/shared/` and `src/thread/`. Optionally, and only if it stays comfortable, `validateCheckpoint`'s ~300-line body can be split per document section, preserving the contract that it reports every problem at once rather than failing on the first.

Throughout: `npm run check` must pass on every change — typecheck, vitest and build, with no half-migrated code and no scenario left red. When an architecture guard fails, the boundary moved: argue the direction rather than relaxing the guard, so the guards end up stricter, never looser. The terminal-outcome protocol keeps its exact `DONE`/`BLOCKED`/`REFUSED` values and the `Outcome: ` prefix, because root `AGENTS.md` names it as load-bearing coupling between the skill suite and the CLI — changing who declares the vocabulary must never change what it is. Catalog entries in `src/pipeline/catalog.ts` stay plain JSON with no methods, because a checkpoint snapshots `SnapshottedStage` verbatim and resume reads only the checkpoint. The pre-release licence applies: rename and remove freely, write no migrations or compatibility shims, and say plainly in the commit message when a change makes existing run directories unreadable. A named `HarnessBackend` interface with `createInvoker` and `probe`, demoting Sandcastle from the real family to one backend among several, is explicitly out of scope and belongs to issue #21.

This is the second of three related pieces of work: issue #38 gives the 32 demo scenarios an assertion surface beyond one exit code and is worth having in place before the checkpoint split touches 27 importers, and issue #40 decomposes `runCommand` and is easier afterwards since `commands/run.ts` is among the importers being narrowed. The three parts of this thread are independent of each other and can land as separate commits in any order, though the outcome guard is cheapest first and the harness-identity move is purely mechanical.
