# Decisions — Address failure modes from the Leitspace field report

## DR1: The suite is the sole target of this thread; the CLI is out of scope and compatibility is not a constraint

Context: The Leitspace field report (`leitspace-field-report.md`) covers both modules, and its open question 5 asks how the CLI's per-stage Git boundaries interact with any new durable layer. The CLI's stage catalog invokes nine suite skills by name and classifies their terminal outcomes, so changes to skill names, inputs, or the outcome protocol break it. The repository currently has a single user and the CLI has not yet been used on a real project.

Decision: This thread redesigns the method and the skill suite only. The CLI is explicitly excluded: it is allowed to go stale against the suite for as long as the redesign takes, and no suite decision in this thread is constrained by keeping the CLI's stage catalog, target resolution, or outcome protocol working. Breaking changes to skill names, artifact shapes, recipes, and the suite/CLI contract are permitted without migration or deprecation paths. Realigning the CLI is a separate, later thread once the suite has reached its next stable form.

Rationale: The suite is where every failure mode in the report was observed, and the CLI automates a chain whose shape this thread is likely to change. Constraining the redesign to the CLI's current contract would preserve the very hops the report indicts. With one user and an unused CLI, the cost of temporary staleness is near zero, while the cost of designing around compatibility is paid on every decision. Trade-off accepted: `cli/README.md`'s stage support table and `documentation.test.ts` may fail against the redesigned suite until the follow-up thread.

## DR2: A thread's design truth is the spec, authored once from live context and amended in place; the thread log is memory only

Context: The field report's failure mode 2.4 and the user's own experience agree on a mechanism: the spec skill forward-designs from `seed.md` plus `decisions.md`, but a discussion settles more than its decision records capture, so the spec agent fills the gaps by inference and `reconcile-spec`, enforcing a "lossless, additive-free" expression of the same lossy log, strips that inference as invented while also deleting legitimate design. The spec is written in the deciding session about half the time; the other half a fresh session regenerates it from disk because the context grew unsafe. Five research reports in this thread root (`research-superpowers.md`, `research-openspec.md`, `research-bmad.md`, `research-gsd.md`, `research-ecosystem-survey.md`) surveyed the ecosystem against three candidate shapes: (A) one design document maintained incrementally during the discussion; (B) decisions kept as an in-place store of settled points with the spec as a thin index over them; (C) no thread-level trace, with the spec synthesized in-session and only project-level records durable. The reports converge on four facts: no project maintains a whole document during a live session, but writing one line at a time during it works (Pocock's glossary, BMAD's memlog); every project that dropped the thread-level trace reports rationale evaporating and lacks any answer for reversing a closed decision; the infer-then-strip loop is information-theoretic, because a decisions-only log cannot be the sole input to a complete spec; and no project keeps a settled-decision store as a co-equal artifact beside a spec. BMAD applies two rules to its own artifacts: a short machine-facing contract is re-rendered from its log and never hand-edited, while its long human-negotiated document is edited in place with the log as audit trail and resume memory.

Decision: Inside a thread there is exactly one design truth, `spec.md`, and one memory, a thread log. Their roles are one-way and never swap.

1. **The thread log is memory, not truth.** During a discussion, and in any skill that settles something, each settled point is appended as one short typed line with its reason folded in, the moment it settles. The write is blind: the log is never re-read during the session it is being written in; it is read only when a session resumes after context loss and when the spec is authored. It carries no lifecycle status; a terminal moment is itself an entry. It is append-only; a later entry supersedes an earlier one on the same point and the history stays intact. Its vocabulary is wider than decisions: it also records constraints, assumptions, open questions, capabilities, and direction, so that it carries the material of the spec and not only the choices made about it. The exact file name, the entry vocabulary, and whether a script performs the append are settled in a later record; the properties above are settled here.
2. **The spec is authored once, from live context.** At the end of the discussion, the same session writes `spec.md` in a single authoring pass while the conversation is still in context. If the session was lost before that point, a fresh session authors the spec from the log, which is complete enough to do so. Authoring includes one audit pass that walks the log claim by claim and confirms each landed; anything the spec states that the log and seed do not support is labelled inline as an assumption or an open question, never deleted and never silently kept as settled. A spec is not complete while an open question remains.
3. **After authoring, the spec is the single in-thread design truth.** Every later change to the design amends `spec.md` in place: the superseded text is kept, marked as superseded, and annotated with the date and the reason, and the same change is appended to the log as one line. Any skill that obtains a new human decision mid-run appends the log line and amends the spec before acting on it. Downstream skills (planning, implementation, review) read the spec and never the log; the log is never cited from any artifact.
4. **`reconcile-spec` is retired.** No skill measures the spec against the log after authoring; the audit pass in point 2 is the only spec-versus-source check and it runs once, inside authoring. A regenerated spec never replaces an authored one.
5. **Thread-local records are never cited from outside the thread.** The present `DR<N>` record shape (Title, Scope, Context, Decision, Rationale, append-only supersession) leaves the thread level and becomes the shape of a project-level decision log, where append-only supersession with stable identifiers belongs; its location, promotion criteria, and single-writer rule are settled in later records of this thread. Cross-thread references cite that project-level log.
6. **This thread keeps the current format.** It was opened under the current method and continues to append `DR<N>` records to this file until it finishes; the shape above applies to threads opened after the redesign ships.

Rationale: This is the only shape that meets every constraint the user set: one design truth, no document maintained during a live discussion, memory that survives a lost session (about half of real threads outlive their safe context), rationale and reversals preserved, and no reconcile step. It removes the regeneration hop, which is the mechanical cause of failure mode 2.4, instead of tuning the two agents on either side of it. Alternatives rejected: (A) maintaining the spec during the discussion distracts the deciding session and has no working instance in the ecosystem; (B) a settled-decision store beside a citing spec has no working instance either and keeps two artifacts that still need a provenance check between them; (C) dropping the thread trace loses exactly the rationale the field report identifies as the method's best-working property and has no answer for reversing a closed decision; a rendered, never-hand-edited spec (BMAD's contract path) conflicts with how a human negotiates and fixes a long spec and is applied by BMAD itself only to short machine-facing artifacts; a design document with no log (superpowers) loses the whole design when a session dies. Principal trade-off accepted: the log becomes load-bearing, so anything a skill settles and does not append is lost on resume, and the existing "record before acting" rule must be honored for every settled point, not only decisions. Second trade-off: a thread holds two files, but drift between them is impossible by construction because one is never read as truth and the other is never derived after authoring. Evidence weighed: superpowers measured a spec/plan review loop at real time cost and zero quality gain and deleted it; GSD measured agents judging their own overreach as ineffective; BMAD's label-not-strip audit is battle-tested; OpenSpec and Pocock users report the loss that (C) implies.

## DR3: The thread log is `log.md`, a flat file of typed one-line entries appended with a shell append

Context: DR2 fixed the thread log's role and properties and left open its file name, its entry vocabulary, and whether a script performs the append. The suite ships no scripts inside any skill. BMAD's equivalent log is a flat `- (type) text` file with no identifiers or timestamps, whose script does an unlocked read-modify-replace and loses entries under parallel writers. The only multi-agent skill in the suite is the subagent implementer, whose subagents never talk to the human. The log must be committed, since its purpose is surviving a lost session.

Decision: The thread log is `log.md` at the thread root, created eagerly by the thread-opening operation with a one-line header. Each entry is one line of the form `- (type) gist with the reason folded in`, with no record identifier and no timestamp; order in the file is the only structure. The entry vocabulary is fixed by the method, identical in every skill, at exactly seven types: `decision`, `constraint`, `assumption`, `question`, `capability`, `direction`, `event`. There is no catch-all type. No script is shipped: a skill appends by a shell append (`>>`) of a single line and never opens the file with a file-editing tool. One writer per session: a skill that fans out to subagents does all appending from the orchestrator, never from a subagent.

Rationale: The shell append gives the three invariants the log needs, append-only, blind, and atomic for a single line on a local filesystem, without a runtime dependency or a script to distribute into every skill folder. A fixed vocabulary means the single reader, the spec-authoring pass, never has to interpret per-skill dialects; omitting a catch-all keeps every line classifiable. Forbidding edit tools is what preserves blindness in practice, since opening the file re-reads it. Renaming away from `decisions.md` is required because the file's vocabulary exceeds decisions and the `DR<N>` shape now lives at project level. Principal trade-off: the rule against edit tools and against subagent writers is a convention a skill body must state, not something the filesystem enforces.

## DR4: The project-level durable layer is a decision log, a glossary, and an authority index; living docs stay project-owned

Context: DR2 moved the `DR<N>` record shape to a project-level decision log and left its location, promotion criteria, and writer open. The field report's failure modes 2.1, 2.3 and 2.5 trace to the method owning no durable artifact above the thread, so Leitspace's domain semantics accumulated in `AGENTS.md`. The ecosystem survey in `researches/research-ecosystem-survey.md` found every comparable toolkit pairs per-change specs with a project-level layer, and that the mechanisms that keep historical material from being read as current all shrink the authoritative surface: an enumerated allow-list of what is current, and consumption of the change artifact into durable documents at the end of the change. OpenSpec's alternative, method-owned living specs per capability with a structural merge, carries a parser that shipped repeated data-loss bugs and a guard that blocks a large share of legitimate changes.

Decision: The method owns exactly three project-level files, created lazily and never a prerequisite: a project decision log in the `DR` record shape with globally stable identifiers and append-only supersession; a glossary of project terms; and a short authority index that enumerates what is currently authoritative, including the project's own living documentation by path. Living documentation itself (READMEs, architecture references, API docs, runbooks) stays in whatever shape the project chooses; the method does not define a living-spec format and performs no structural merge. When a thread finishes, its spec is consumed into this layer: qualifying decisions are promoted to the project log, new terms land in the glossary, the index is updated, and the thread is archived. Any thread artifact not pointed at by the index is historical by construction. The exact paths, the promotion criterion, the single-writer rule, and the shape of the consumption step are settled in later records.

Rationale: This takes the two best-evidenced mechanisms, the allow-list and end-of-change consumption, without owning a merger and a delta grammar forever. A lazy glossary gives vocabulary a home other than `AGENTS.md` at near-zero cost even though its effect on agent performance is disputed. Trade-off accepted: the current design of one capability is answered by code, the project's living docs, and the decision log together, located through the index, rather than by a single living spec per capability.

## DR5: A dedicated closing skill consumes a thread into the durable layer and archives it; no other operation writes the layer

Context: DR4 established that a finished thread's spec is consumed into the project-level layer and the thread archived, and left the shape of that step open. Candidate homes were the implementation skills, `finish`, or a skill of its own. Implementation runs many times per thread, can end blocked, and does not exist for spec-only threads, so it cannot know which decisions bound the delivered outcome. `finish` is the branch handoff and is not run at all in a workflow that works on a single branch without pull requests, which is the repository owner's own practice; `archive-thread`, the existing optional closing act, was never run across ten Leitspace threads. Post-implementation design changes are normally made through a discussion with an agent, but sometimes in a session without Antmay skills, so a spec can be stale at close time.

Decision: A single dedicated closing skill (working name `close-thread`) performs thread consumption. Its scope is exactly four moves, in order: a spec-currency check that reads the implementation report and the delivered changes against the spec's design claims and puts every divergence to the human, amending the spec in place per DR2 from the answers, and refusing to proceed while a divergence is unresolved; promotion of qualifying decisions from the spec into the project decision log; glossary and authority-index update; and archival of the thread, absorbing what `archive-thread` does today, including its temporary-workspace warning. The three method-owned project files (decision log, glossary, authority index) have this skill as their only writer; every other skill reads them and states that boundary in its own body. Living documentation is not part of this skill: it changes within implementation scope, as the thread model already requires. `finish` keeps its branch-handoff scope and recommends closing the thread first so promoted records travel with the delivery. No operation forces the closing skill to run: the thread-opening operation does not check for unclosed threads.

Rationale: One skill with one purpose is discoverable and cheap to invoke, which is the property the user identified as what actually gets a step run in a single-branch workflow. The currency check gates promotion because promoting a stale spec would put wrong records in the one place cross-thread references cite, which is failure mode 2.3 at project level. Note: recommended a forcing function in the thread-opening operation, listing unclosed threads and asking once whether to close them, because an optional closing step has the same history as `archive-thread` and OpenSpec's optional merge; the user rejected it as ugly and accepted the trade-off that closing depends on the user invoking it.

## DR6: The thread carries a delta of the durable layer, written during the discussion and applied at close

Context: DR4 defined the project-level layer and DR5 gave the closing skill sole write authority over it. Which decisions to promote, and when that judgment is made, remained open: reconstructing it at close from the spec means an agent judging without the discussion's context, while the alternative is to make the call when the point settles, with the human present. Pocock's `grill-with-docs` writes glossary terms and ADRs during the session the moment they resolve, and that in-session write of a short, write-once unit is the one form of durable writing during a grilling the research found harmless. DR2 forbids maintaining a long document during a discussion; it does not forbid writing a short record once.

Decision: The thread folder carries delta files that mirror the project layer: candidate project decision records in the full `DR` shape and candidate glossary entries. The discussion writes them during the session: when a settled point passes the binding test, meaning a later thread could build against it incorrectly if not told and could not read it off the code, the agent proposes a record and the user confirms or redirects its text before it is written; the user may also request one directly. Every skill that settles a project-level point mid-thread does the same. A delta record that supersedes an existing project record names that record's global identifier. Within the thread, the delta records are authoritative from the moment they are written: the spec and every downstream skill rest on them and cite them rather than restating them, so the spec-authoring audit has no delta-versus-spec check to run. Until close a delta record is a draft carrying a thread-local draft number; if the same thread later reverses it, the settling operation edits it in place. The log still receives its one-line entry for every settled point, since the log feeds spec authoring. The closing skill assigns global identifiers, appends the records to the project decision log with a coordinate to the thread folder, merges the glossary entries, updates the authority index, and archives the thread; its currency check covers spec and delta together.

Rationale: The promotion judgment is made once, where the context is richest and with the human confirming the record's actual text, and the close becomes an append with no reconstruction. Treating the delta as authoritative inside the thread removes the class of drift where an early record and a late spec quietly diverge, because the spec never re-expresses the record. Trade-off accepted: the discussion gains a second write target beside the log, and a reversal inside the same thread requires one in-place edit of a draft.

## DR7: Project decision records are one file each, identified by a stamped slug from creation; superseded records move to a `superseded/` folder

Context: Partially supersedes DR4, which described the project decision log as a single file, and refines DR6's delta. The remaining questions were the container, the identifier, when the identifier is assigned, whether code may cite it, and how a superseded record is marked. Sequential numbers assigned at close would forbid the implementing thread from citing its own records, and a rule that code cites either every record or none was required. Pocock's `docs/adr/` keeps one file per record so an agent reads only what it needs. The survey's evidence is that historical-versus-authoritative works by shrinking the surface an agent sees, and the repository's own rule is not to maintain in a file a listing the system can print.

Decision: The project decision log is a folder holding one file per record, named `<yymmddhhmm>-<slug>.md` where the stamp is the record's creation time in UTC at minute resolution; the stem is the record's global identifier. Each file opens with the record's title as its first line, then the `DR` shape fields. The identifier is assigned when the record is first written into the thread's delta folder, which uses the same file naming, and never changes; closing the thread moves the files into the project folder unaltered. Code, tests, commit messages, and living documentation may cite a record by its stem, never by path, and never must; nothing thread-local (log entries, spec sections, plan tasks) is ever cited outside its thread. Supersession is a move: a superseding record names the superseded stem, and the closing skill, in the same act that lands the new file, moves the superseded file into a `superseded/` subfolder, leaving its content untouched. A record that stops applying with no replacement is retired the same way, by a short record stating why, and a move. A draft superseded within its own thread before close is edited in place per DR6. There is no maintained index file for the folder: agents list the folder and read the title lines. The authority index from DR4 points at the folder and the glossary and enumerates living documentation.

Rationale: One file per record lets an agent read two records instead of a log; the stamped slug is unique by construction so two open threads cannot collide and no identifier is ever reassigned, which is what lets the implementing thread cite its own decisions; the slug makes the identifier readable where a number was not. Moving superseded records keeps the current folder as the whole authoritative surface without any status field, while preserving the original rationale that deletion would lose and keeping citations resolvable by search. Minute resolution cannot collide because the slug is part of the identifier. Trade-offs accepted: the stamp form diverges from the thread folder's second-resolution form, and a citation to a superseded record in code goes stale silently until a search reveals the move.

## DR8: A delta record found wrong downstream blocks planning via a pending decision and blocks implementation only when intent must change; deviations are tracked in the implementation report

Context: DR6 makes the thread's delta records authoritative from the moment they are written, so a record can be accepted in discussion and found wrong only during planning or implementation. The method already distinguishes an implementation deviation that stays within accepted intent, which proceeds and is recorded, from a change to intended behavior, which stops and surfaces a human decision. The closing skill's currency check (DR5) needs to know every deviation without re-deriving it from a diff.

Decision: During planning, a delta record or spec decision found wrong is queued as a pending decision; planning does not proceed on it, and resolving the bundle edits the draft record and amends the spec before planning resumes. During implementation, a deviation that stays within accepted intent proceeds and is recorded; a contradiction of a delta record or of a spec decision is a change of intent and is queued as a pending decision, ending the run blocked, exactly as today. The implementation report carries a dedicated deviations section in which every deviation names what was built, the spec section or delta record it departs from, and why. No separate deviations file exists. The closing skill's currency check reads that section as its primary input.

Rationale: A delta record is by definition a binding intent, so building against a wrong one means the implementer picks a side on a contested point and the human learns of it at close, after further work may rest on it; with the human present during implementation, a pending decision costs one answer and a resume, and the run keeps its progress file. Keeping deviations in the singleton report avoids a second file to keep current. Alternative considered: never blocking implementation and tracking every discrepancy for review at close; rejected because it trades a cheap interruption for potential rework of dependent tasks.

## DR9: Project decision records are ADRs under `docs/adr/`; the glossary is `docs/glossary.md`; the authority index dissolves into the project's `AGENTS.md` method section

Context: Partially supersedes DR4, which named a method-owned authority index as a third artifact, and fixes the paths DR7 left open. The remaining questions were the layer's location, its vocabulary, how an agent gets a catalog of records without a maintained index, and where the list of authoritative living documents lives. The suite installs skills into a project, not project files, so any script the method relied on would have to be written into every project. Agents already carry strong priors about a `docs/adr/` folder and the ADR supersession convention, which helps sessions that run without Antmay skills.

Decision: Project decision records are called ADRs. They live at fixed, method-owned paths with no setup step: `docs/adr/` for current records and `docs/adr/superseded/` for superseded and retired ones; the glossary is `docs/glossary.md`. The thread's delta mirrors them as `adr/` and `glossary.md` at the thread root, so close is a move plus a glossary merge. An ADR file opens with `# <title>` on its first line and a one-sentence summary as its first paragraph, followed by the Context, Decision, and Rationale fields; that fixed opening is what lets a single shell command over the folder print a catalog of identifiers, titles, and summaries on demand. No index file and no script are shipped or maintained; the listing command is documented once, in the project's `AGENTS.md` method section. That section, written by the project's humans and not by any skill, carries the read order for agents, the listing command, the pointers to `docs/adr/` and the glossary, and the list of the project's authoritative living documents by path. The closing skill therefore performs four moves: currency check, move of the thread's ADRs into `docs/adr/` with superseded records moved to `superseded/`, glossary merge, and archive. The thread-level `DR<N>` term is retired everywhere; ADR names only project records, and the thread's memory is the log of DR3.

Rationale: Fixed paths remove a configuration surface every skill would otherwise read first; the ADR name buys read-order compliance from agents that have never seen the method; a catalog printed from the files keeps one source of truth, consistent with the repository's own rule against maintaining listings the system can print; keeping the living-documents list in `AGENTS.md` under human ownership is where every agent session, with or without Antmay skills, will actually read it, and it keeps that file to rules and pointers. Trade-off accepted: the "architecture" in ADR is a misnomer for product rules, and the living-documents list depends on humans keeping it current.

## DR10: An ADR file is YAML frontmatter with `name`, `description`, and optional `supersedes`, followed by a free-form body whose required content is context, decision, and reason

Context: Partially supersedes DR9's rule that an ADR opens with a title line and a summary paragraph followed by fixed Context, Decision, and Rationale fields, and DR2's statement that the thread-level record shape moves to project level. A catalog printed from the files needs a parseable opening; a fixed body risks forcing sections that do not fit the decision at hand and inviting padded prose the human never asked for. Pocock's ADR format mandates only a title and one to three sentences covering context, choice, and reason, treats Considered Options and Consequences as optional, and his own ADRs invent headings per record.

Decision: An ADR file opens with a YAML frontmatter block carrying `name`, a short title written as a full decision sentence; `description`, one sentence for the catalog; and optionally `supersedes`, one or more stems of project ADRs this record replaces or retires. There is no status key: location is the status, per DR7. The body is free in form and required in content: it must make the decision intelligible without the thread by giving the needed context, state the decision in full, and give the reason. A single paragraph satisfies this. Further sections appear only when they carry something the required content does not, with considered options, consequences, and scope as the usual candidates, under headings chosen to fit the record. The closing skill reads `supersedes` to determine which project ADRs to move to `superseded/` when it lands the record. The catalog listing reads `name` and `description`.

Rationale: The frontmatter is the form every skill file already uses, so agents know it and a one-line command parses it; the `supersedes` key is the one structural element the closing skill needs mechanically. Leaving the body free avoids sections that do not fit while keeping the reason mandatory, because the reason is what makes a record worth citing and the human confirms the text before it is written under DR6. Trade-off accepted: bodies vary in shape across records, so a reader cannot rely on a fixed heading to find the decision sentence.

## DR11: The thread folder separates design truth at the root from execution rounds under `rounds/`, one subfolder per plan-and-implement pass

Context: DR2 amends the spec in place after implementation, so a thread can go through several plan-then-implement passes, and DR5's currency check needs every pass's deviations (DR8). With a single `plan.md` and a single `implementation-report.md` at the thread root, a second pass overwrites the first and its deviations are lost. Every comparable toolkit separates a change's durable design from its execution residue.

Decision: The thread root holds design truth and thread-wide artifacts: `seed.md`, `log.md`, `spec.md`, the `adr/` delta folder, the `glossary.md` delta, `proposal.md` when used, `roadmap.md` for Roadmap threads, and the `.pending-decisions/` and `.pending-reviews/` workspaces. Execution lives under `rounds/`, one subfolder per round named `<yymmddhhmm>-<slug>` with the stamp in UTC at minute resolution. A round is one plan-then-implement sequence against the spec as it stands when the round opens; it is created by the first skill that writes into it, normally the planning skill, or the implementation skill when a round has no plan. Each round folder holds `plan.md` (brief plan or strict-plan index), `plan-tasks/` for a strict plan, `implementation-report.md` describing that round's outcome and its deviations section, and that round's `.implementation-runs/`. Every thread has at least one round. There is no thread-level implementation report: the spec is the current design, the code is the current outcome, and the closing skill reads every round's report for its currency check. The folder is named `rounds/`.

Rationale: Rounds make repeated passes first-class instead of an overwrite, keep each pass's plan and deviations intact for the close, and put the design truth and the execution residue in visibly different places so a reader knows which is which. A uniform layout with at least one round spares every skill a root-level special case. The name `rounds` avoids `changes`, which the method already uses for the thread's unit of work and which OpenSpec uses for its own concept. Alternative rejected: a follow-up pass as its own Quick thread, which would split the design truth across threads. Trade-off accepted: a one-pass thread carries one extra folder level.

## DR12: One read order for every reading skill, and a conflict with the project layer is surfaced unless the thread already supersedes the record

Context: No skill in the suite states what to read first; the spec and discussion skills read only the thread. The field report's failure mode 2.3 is agents treating other threads' artifacts as authoritative. With DR7 and DR9 the project layer is `docs/adr/` and `docs/glossary.md`, and a thread changes a project record only by writing a draft ADR that names it in `supersedes` or by redefining a term in its glossary delta. Pocock's setup and GSD both instruct downstream skills to surface a contradiction with an existing record rather than override it.

Decision: Every skill that reads context follows one order: first the project layer, listing the ADR catalog and opening the relevant records, and reading the glossary; second the active thread, meaning `spec.md`, the thread's `adr/` and `glossary.md`, and whichever round artifacts the skill needs; third nothing else. Another active thread is read only through a reference the method defines, today a Roadmap child reading its parent's `roadmap.md`. An archived thread is read only when the user names it in the invocation, and then as history, never as authority. A contradiction between the thread's material and a project ADR or glossary term is intentional, and raised by no skill, when the thread's `adr/` holds a draft naming that ADR in `supersedes` or its `glossary.md` redefines the term. Every other contradiction is an unnoticed conflict: an interactive skill puts it to the user, a completion-oriented skill queues a pending decision, and no skill resolves it by overriding the project record. Raising such a contradiction during the discussion, before any draft exists, is part of the discussion's job; the user's confirmation that the change is intended is recorded by writing the superseding draft, which makes it intentional from then on.

Rationale: One order, stated once, is the cheapest mechanism that works once consumption and the allow-list exist; naming the intentional case mechanically, by the `supersedes` key or a glossary redefinition, is what keeps a thread that is deliberately changing a project record from being interrupted about it, while everything else is by definition a contradiction nobody chose. Trade-off accepted: a conflict noticed in a completion-oriented skill blocks the run until a human answers.

## DR13: The method's common rules live in one model-invocable method skill; other skills carry only their own procedure and a one-line pointer sits in the project's `AGENTS.md`

Context: The common rules of the method (thread layout, read order, ADR listing command, citation rule, log and spec roles, conflict rule) are currently restated across skill bodies, and no rule reaches a session that runs without invoking an Antmay skill, which is a normal case in the repository owner's practice. Three homes were weighed: a managed block in the project's `AGENTS.md` written by a setup skill; a dedicated model-invocable skill; or shorter skill bodies with the rules still inside each. Pocock's `grill-with-docs` delegates its whole body to two other skills and documents partial loading as its most reported failure.

Decision: The method's common rules live once, in a dedicated method skill that the model may invoke on its own. Every other skill makes loading the method skill a hard step of its preflight, refers to the method skill for the common rules instead of restating them, and keeps inline only the rules that protect artifacts if that load were skipped, above all its own write boundary. The project's `AGENTS.md` carries one human-written line stating that the project follows the Antmay method and that the method skill is to be loaded before working under `docs/threads/`, `docs/adr/`, or `docs/glossary.md`; that line is not a managed block and no setup skill exists. The project's list of authoritative living documents (DR9) stays human-owned in `AGENTS.md`. Open, to be settled at implementation: whether the repository's `docs/` method reference becomes the source the method skill is rendered from or shrinks to developer-facing material, so that the method text has one source.

Rationale: The method skill installs and updates through the same path as every other skill, so no setup machinery and no block versioning are needed; it loads only when relevant instead of in every session; and with the pointer line it reaches skill-less sessions, which a rules-in-skills arrangement never could. Trade-off accepted: an agent that skips the load runs with only the inline protective rules, which is why those stay in each body.

## DR14: A Roadmap thread is a coarse index edited in place, stays open until its destination is reached, and opens children lazily; the feedback channel and materialization are retired

Context: The field report's failure mode 2.2: full child briefs written at materialization were wrong before the second child opened, `roadmap-feedback.md` accumulated records no skill read before a child began, and the author hand-wrote an addendum into a child seed to restate the current state. Under DR6, DR9 and DR12 the constraints a roadmap imposes on its children are project ADRs that every child reads first, and a child that finds a parent-level fact wrong writes a superseding draft ADR promoted at its own close. The ecosystem survey found every comparable toolkit keeps a single coarse index edited in place, defers detail until the frontier reaches it, and makes the child update the index at completion; a replacement for the feedback channel needs a named reader at a named moment.

Decision: A Roadmap thread stays active until its destination is reached or abandoned and is closed last, after its children. `roadmap.md` is a coarse index edited in place by the roadmap's owner: the destination, the ordered entries each with a stable identifier, a one-paragraph sketch and a scope boundary, an out-of-scope list, and a not-yet-specified note for what cannot yet be seen. It carries no shared-constraints section; constraints are ADRs in the roadmap thread's delta, promoted when its ADRs land. No child thread is created up front. When the frontier reaches an entry, the user opens a child thread whose seed references the parent thread and the entry; the child runs a normal discussion against the project layer as it stands. An entry is pinned once its child is opened; unstarted entries may be reordered, merged, or dropped. The single permitted cross-thread write is redefined: when a child closes, the closing skill updates the parent's entry with a one-line outcome and the child's folder name. `roadmap-feedback.md`, `append-roadmap-feedback`, `materialize-roadmap-threads`, and `reconcile-roadmap` are retired. A parent-level discovery travels as a superseding ADR; a discovery implying new work is a proposed entry the user adds to the index.

Rationale: This is the only shape in which every piece of information has a reader: the next child reads ADRs by the read order and the parent's index is updated by the child that finished. It removes the frozen-brief-plus-diff-channel arrangement that required rebasing feedback by hand, and it makes the hand-written addendum the normal path. Trade-offs accepted: the roadmap thread remains active for the whole direction, and the child brief's detail is produced at child-open time by a discussion rather than pre-written.

## DR15: The proposal artifact and the reconcile family are removed except a plan check that fixes faults and queues the rest; `review-spec` stays, `review-roadmap` goes

Context: DR2 retired `reconcile-spec` and DR14 retired `reconcile-roadmap`. The remaining downstream skills were `propose`, `reconcile-proposal`, `reconcile-plan`, `review-spec`, `review-roadmap`, `review-implementation`, `review-code`, and the two plan skills. The proposal artifact has never been used by the repository owner. A strict plan is many files produced at the end of a long authoring context, so a self-check inside that same context is weak exactly when the plan is large; the spec has no such problem because its audit runs in the session that holds the whole discussion. `review-spec` checks whether a fresh agent could plan and implement from the spec alone, which under DR2's live-context authoring is the risk worth checking. `review-roadmap` judges pre-written child briefs, which DR14 removed.

Decision: The proposal artifact is removed from the method: `propose` and `reconcile-proposal` are retired and `proposal.md` leaves the thread layout; direction is settled in discussion and written into the spec. `reconcile-plan` is replaced by one plan check that runs in a fresh context against the current round's plan with the spec as its sole authority. It corrects in place every fault that follows from the spec: a task contradicting the spec, an acceptance criterion no task covers, an ambiguous or wrong step, a wrong target path. It never removes implementation detail the plan added, and it never satisfies a gap by inventing a task. Anything it cannot fix from the spec becomes a pending decision. Its name is settled at implementation. The plan skills keep their own self-check. `review-spec` stays as an optional read-only review. `review-roadmap` is retired. `review-implementation` and `review-code` are unchanged. `resolve-pending-decisions` writes per DR2 and DR6: it appends the log line, amends `spec.md` in place with superseded text kept and dated, and writes or edits a draft ADR when the point is project-level; it writes no `DR<N>` record.

Rationale: Removing an artifact nobody used removes a hop where intent could be re-elaborated for no benefit. The plan check is kept on the strength of a fact that distinguishes it from the spec case, context size at authoring time, and is constrained by the two properties whose absence produced the spec reconcile failure: a complete authority and a fix-only mandate. Trade-off accepted: one extra hop remains in the chain, chosen deliberately for large plans.

## DR16: A pending-decision point states the blocker and its evidence, with an optional free-text suggestion, and carries no options menu

Context: A pending-decision bundle today carries a routing header, a required suggested-action paragraph, and one canonical discussion point per question, each with a framed fork, options, and a recommendation. The producing skill knows what blocked it and why; it does not hold the option space, which is framed live with the human when the bundle is resolved. The field report lists the pending-decision queue among the parts of the method that worked.

Decision: A pending-decision bundle keeps a routing header naming the producing skill, the target, the originating request, the creation time, and the point count. Each point is half finding, half decision: it states what is blocked, why the producer could not derive the answer, and the evidence it weighed, in that producer's own words. It may add a free-text suggestion when the producer sees an immediate fix, and nothing requires one. It carries no options, no recommendation, and no discussion-point structure. The bundle-level suggested-action paragraph is dropped; anything of that kind goes in a point's free text. `resolve-pending-decisions` frames each point as a discussion would, live with the user, and writes the outcome per DR15.

Rationale: The producer's knowledge is the blocker, not the fork; asking it to frame options forces invented alternatives and a recommendation made without the human, which is the same overreach the spec redesign removed elsewhere. A minimal point is also cheaper to emit inside a run that is about to end blocked. Trade-off accepted: the resolving session does the framing work the producer used to do.

## DR17: The spec skill is invoked by the user after the discussion; the discussion skill writes no spec and declares no context budget

Context: DR2 has the spec authored once from live context at the end of the discussion, or from the log in a fresh session, without saying which skill performs the authoring or whether the discussion skill manages the session's context. The alternatives were the discussion skill writing the spec as its last act, a handoff from the discussion skill to the spec skill, or the user invoking the spec skill. A soft context budget with a split rule in the discussion skill was also proposed.

Decision: The discussion skill ends when the user ends it and writes only the log lines and draft ADRs and glossary entries of DR3 and DR6; it does not write the spec and does not hand off to the spec skill. The user invokes the spec skill, in the same session when the context is still safe or in a fresh session otherwise. The spec skill's inputs are the live conversation when present, otherwise the log, plus the seed, the thread's draft ADRs and glossary, and the project layer per DR12. The discussion skill states no context budget and no split rule; managing session context is the user's responsibility, and the blind append of DR3 is what makes an early stop lossless.

Rationale: One skill per artifact keeps write authority legible, and the user is the only party who can judge when a session's context is no longer safe. Note: recommended an advisory budget and a documented split rule in the discussion skill so the fresh-session path is stated where a new user would find it; the user declined and accepted managing context by hand.

## DR18: The roadmap index lives outside the thread at a project-level path; a Roadmap thread is an ordinary thread that closes before its children open

Context: Partially supersedes DR14 (the Roadmap thread staying active until its destination is reached and closing last, the child seed referencing a parent thread, and the closing skill writing a parent thread's `roadmap.md`), the Roadmap-child exception in DR12, and `roadmap.md`'s place in the thread layout of DR11. Under DR14 a Roadmap thread stayed open only to hold the index its children update, which made its ADRs land in `docs/adr/` last, after the children built on them, and left no way for a child to read them meanwhile. Pocock's wayfinder keeps the map outside the unit of work: the map is an issue that tickets link to, and it is discarded once the work ships.

Decision: The roadmap index is a project-level file at a method-owned path, `docs/roadmaps/<yymmddhhmm>-<slug>.md`, with the stamp in UTC at minute resolution. A Roadmap thread is an ordinary thread: it discusses the direction, writes its ADRs and glossary entries in its delta, authors the index with the shape DR14 defines (destination, identified entries each with a one-paragraph sketch and scope boundary, out-of-scope list, not-yet-specified note, no constraints section, no statuses, no child briefs), and closes through the closing skill like any other thread, so its ADRs land in `docs/adr/` before any child opens. The thread layout carries no `roadmap.md`. A child thread's seed references the index file and the entry it was opened from, not a parent thread. Children read the project layer and their own thread only; the read order has no Roadmap exception. The index is edited in place by its owner; when a child closes, the closing skill updates that child's entry in the index with a one-line outcome and the child's folder name, which is a write to a project-level file and stays within the closing skill's sole write authority over the project layer. No skill writes another thread's files under any circumstance. When the destination is reached or abandoned, the owner deletes the index; the outcome lives in the code, the ADRs, and the archived threads. Pinning of started entries and free reordering of unstarted ones hold as in DR14.

Rationale: Moving the index out of the thread removes the only reason a thread ever stayed open for another thread's sake, restores the natural landing order in which a direction's constraints precede the work built on them, and eliminates the last cross-thread write and the last read-order exception. Alternatives rejected: extending the read order so a child reads its parent's drafts, which patches the symptom and leaves a child ADR able to supersede a record not yet in `docs/adr/`; an early partial landing by the closing skill, which adds a mode to that skill and runs a currency check before the destination exists; a roadmap that emits no ADRs, which would push direction-level constraints back into the index as restated text. Trade-off accepted: a fourth method-owned project path, and a finished index is deleted rather than archived, with git as its history.
