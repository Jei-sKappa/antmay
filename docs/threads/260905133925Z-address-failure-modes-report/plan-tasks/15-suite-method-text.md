### Task 15: Write the suite's method overview and developer material, remove the `docs/` reference

**Objective:** Give the redesigned method its one user-facing overview at `suite/method.md` and its developer-facing conventions at `suite/skill-authoring.md`, and remove the method reference documents from `docs/`.

**Input / context:** Starts from task 14 (every skill now describes the redesigned method). `spec.md` `## The redesigned method` in full (the overview describes it as current state), `### Documentation and repository maintenance` (the suite's method text, what moves, what is removed), and the acceptance criteria that read the overview: AC-1.1, AC-5.1, AC-5.3, AC-5.4, AC-7.3, AC-11.2; decisions.md DR24, DR26. Paths fixed in `plan.md`: `suite/method.md`, `suite/skill-authoring.md`. The recipe sequences are the ones task 14 wrote into `suite/shared/references/recipes/`. No skill body references either new document, and neither document is synced into any skill.

**Steps:**

1. Write `suite/method.md` for a user of the suite, in this order:
   - **What the method is** — one unit of work per thread, intent written before it is built, reviewable Markdown on disk; conventions guide and never govern (fold in the conventions-first and subject-neutrality points from `docs/README.md` in the redesigned vocabulary).
   - **Thread layout** — the tree from spec `### Thread layout` reproduced with the same entries (`seed.md`, `log.md`, `spec.md`, `adr/`, `glossary.md`, `plans/<stamp>[-<slug>]/{plan.md, plan-tasks/}`, `implementations/<stamp>[-<slug>]/{report.md, .runs/}`, `.pending-decisions/`, `.pending-reviews/`) and one paragraph each on the seed, the log (memory, not truth; seven types; two readers), the spec (design truth authored once and amended in place), the delta (`adr/`, `glossary.md`, the binding test), plans and implementations (one folder per pass; the report and its deviations), and the workspaces.
   - **The project layer** — `docs/adr/`, `docs/adr/superseded/`, `docs/glossary.md`, `docs/roadmaps/`, created lazily and never a prerequisite; the ADR file in brief and the catalog printed by a command (point at the ADR format shipped inside every skill, do not restate the command); living documentation stays project-owned and changes within implementation scope; the citation rule (ADR stems may be cited from code, tests, commits, and living docs, never by path and never required; thread-local material is never cited outside its thread); the human-written `AGENTS.md` method section (pointers to `docs/adr/` and `docs/glossary.md`, the catalog command, the living-documents list), written by the project's humans and by no skill, with no setup skill.
   - **The lifecycle** — open (`open-thread`), discuss, spec, plan and check, implement, review, finish, close (`close-thread`: checks, landing, glossary merge, roadmap entry, archive); pending decisions and pending reviews as the two queues; the terminal outcome protocol in one paragraph; historical versus living documentation; branch-agnosticism; external references stay passive.
   - **The three recipes** — Quick (open, implement, close, with discussion, spec, and plan optional), Standard (discussion, spec, plans, implementations, close), Roadmap (an ordinary thread whose deliverable is the index at `docs/roadmaps/` plus its ADRs; it closes like any thread before entries are worked and authors no spec unless wanted; the user opens a thread from an entry when the frontier reaches it; an entry's slug is pinned on open; the closing skill writes beneath the entry's heading; the owner deletes the index when the destination is reached). Each recipe's step list matches task 14's recipe references. Fold in the "admitting a future recipe" bar.
