# Decisions

## DR1: The operational-workspace preflight covers all three workspaces and checks both ignore coverage and tracked content

Scope: the operational-workspace preflight check added to `antmay afk run`

Context: the method defines exactly three thread-local operational workspaces — `.pending-decisions/`, `.pending-reviews/`, and `.implementation-runs/` — which Antmay skills create on demand inside the selected thread. The clean-worktree preflight and the per-stage Git boundary both read `git status` without `--ignored`, so a workspace that Git ignores is invisible to both, while one that Git does not ignore passes preflight when absent and then trips a later stage's boundary. Two distinct repository states produce that failure: the path is not covered by any ignore rule, and the path is covered but holds content Git already tracks, because Git honors the index over `.gitignore`. Which workspaces a run will create is not predictable from its stage list, since any stage whose skill discovers an open human decision can write `.pending-decisions/`.

Decision: the check covers all three workspaces on every run, unconditionally, and verifies two independent properties of each. First, that the workspace path is covered by Git's ignore rules. Second, that Git tracks no content under it. Either property failing for any of the three refuses the run. The two failures carry different corrections: missing ignore coverage is corrected by adding an ignore rule, tracked content by untracking the path, so they are reported as distinct problems rather than one generic message.

Rationale: the feature exists to convert a predictable late-stage boundary failure into an immediate setup error, and checking ignore coverage alone would leave a second, reachable cause of that identical failure unguarded for the sake of one additional Git invocation — the tracked-content state arises without any force-add whenever operational files were committed before the ignore rule was written. Narrowing coverage to the workspaces the selected stages could create was rejected: it requires a per-stage mapping that `.pending-decisions/` makes nearly universal anyway, and the user must correct the repository once regardless, so the narrowing saves nothing real while adding a fragile table. The trade-off accepted is two distinct correction messages instead of one.

## DR2: Ignore coverage is probed as a directory, one `git check-ignore` invocation per workspace

Scope: the operational-workspace preflight check added to `antmay afk run`

Context: DR1 requires the preflight to verify that each of the three operational workspaces is covered by Git's ignore rules and holds no tracked content. Git offers several probe forms and they do not agree. Probing the workspace path without a trailing slash reports "not ignored" for every ignore rule written with a trailing slash — including this repository's own `docs/threads/**/.pending-decisions/` — because such a rule matches directories only. Probing a synthetic filename inside the workspace reports "ignored" even for a rule that covers only some filenames, such as one ending `/*.md`, under which a stage writing any other file still trips the boundary.

Decision: ignore coverage is probed with `git check-ignore -q --no-index -- "<workspace-path>/"`, one invocation per workspace, with the trailing slash mandatory. Exit code `0` is coverage, `1` is missing coverage for that workspace, and `128` or a spawn failure aborts preflight as a Git error rather than being read as missing coverage. `--no-index` keeps this probe purely about pattern coverage, so a workspace holding tracked content reports only the tracked-content problem rather than both problems for one root cause. Tracked content is probed separately with a single `git ls-files -z -- <p1> <p2> <p3>` over the three paths written without trailing slashes; any emitted path names a workspace with tracked content. The refusal reports every failing workspace from both probes together rather than stopping at the first.

Rationale: the trailing-slash directory probe asks whether the entire directory is ignored, which is exactly the property the Git boundary depends on, so it is the semantically correct question and not merely the convenient one — its rejection of a filename-restricted rule is the right answer, and the synthetic-filename form's acceptance of that rule is a false pass. Separate per-workspace invocations rather than one batched call follow from `git check-ignore`'s NUL-separated output requiring `--stdin`, which the codebase's `execFile`-based Git wrapper does not provide; three cheap invocations avoid adding stdin plumbing for no gain. Collecting all failures matches how pipeline-document loading already reports every discoverable problem at once. The trailing slash, the `--no-index` flag, and the `1`-versus-`128` distinction are each silently wrong in a way a permissive test fixture would not catch, so each is stated as a requirement rather than left to the implementer.

## DR3: Both `run` and `resume` gate on operational-workspace ignore coverage, immediately before their clean-worktree check

Scope: the operational-workspace preflight check in `antmay afk run` and `antmay afk resume`

Context: the workspace ignore check needs only the resolved repository root and thread-relative path, so its position within a command's gate sequence is free. Position relative to the clean-worktree check is not neutral: when a workspace is both unignored and holds leftover files, the clean-worktree check fires first and instructs the user to commit what they want to keep or revert the rest, which followed literally commits operational residue into the repository. Both `run` and `resume` carry that same clean-worktree check and the same message. A paused run may be resumed long after it started, and the repository's ignore rules are ordinary tracked files that can change in between.

Decision: both commands run the check. In `run` it becomes the first gate of the repository-state block, immediately before the clean-worktree gate, shifting the gates after it down by one. In `resume` it runs immediately before that command's clean-worktree gate and applies unconditionally — the exemptions that skip the clean-worktree check for `git-policy-violation`, `commit-error`, and `stage-contract-violation` pauses do not extend to it. Both commands call one shared implementation.

Rationale: running before the clean-worktree gate is what makes the refusal diagnostic rather than misleading, since the alternative ordering hands the user advice that damages the repository. Gating `resume` as well matters more than gating `run`: an unattended run that paused overnight is resumed straight into the stages that create operational files, with nobody watching the first boundary fail. The cost is one additional refusal path in `resume` with its own tests, which is small against leaving the documented hole open on the command most exposed to it. Ignore coverage is orthogonal to worktree dirtiness, which is why the contract pause — exempt from cleanliness because a dirty tree is exactly what it inspects — is not exempt here.

## DR4: The refusal names the failing workspaces and prints repo-wide ignore rules as its correction

Scope: the operational-workspace preflight check in `antmay afk run` and `antmay afk resume`

Context: the check refuses on two independent failure kinds that need different corrections — missing ignore coverage is an ignore-rule edit, tracked content requires untracking and committing — and a workspace can hold tracked content while already being covered, so the two are not ordered stages of a single fix. Thread resolution enforces that a thread sits at exactly `<repoRoot>/docs/threads/<thread-folder>`, so a repository-wide ignore rule is correct for every thread the CLI can be pointed at. The CLI provisions no configuration and therefore cannot write the correction itself; the message is the entire remedy.

Decision: the refusal is a single message that lists every failing workspace grouped by failure kind, each group followed by its own copyable correction. The missing-coverage group is followed by the repository-wide `docs/threads/**/<workspace-name>/` rules to add, named against the resolved repository root. The tracked-content group lists the offending file paths exactly as `git ls-files` reported them and is followed by a `git rm -r --cached` command targeting the workspace directory, with an instruction to commit. Only failing workspaces appear in either group. The message opens by stating that Antmay skills write these directories during a run and that an unignored workspace makes a later stage fail its Git boundary, so the refusal explains itself without reference to documentation.

Rationale: the repository-wide rule form is a one-time fix and matches the layout the method already prescribes, whereas the selected thread's literal path would have to be re-added for every thread opened afterwards. Listing only the failing workspaces avoids implying that a workspace already covered was also wrong. The tracked group reports files rather than the directory because the file paths are what identify the commit that introduced them, while the correction operates on the directory. Stating the consequence in the message keeps the refusal actionable for a user who has never read the CLI's documentation, which is the population this gate exists to catch.

## DR5: One demo scenario covers the refusal, and the scenario obligation is extended to structured preflight refusals

Scope: `cli/scripts/scenarios/`, `cli/AGENTS.md`

Context: the CLI's scenario catalog exists so that every distinct terminal rendering is visible to a human without a real harness, and the obligation is currently written in terms of the curated display — banners, closing blocks, stage dispositions, startup blocks, sub-lines. Preflight refusals bypass that display entirely: they write plain text to standard error and return exit code 1, and none of the thirteen existing refusals has a scenario. The refusal defined in DR4 is different in kind from those: it is a multi-line message carrying two grouped lists and two copyable blocks, whose indentation and grouping can degrade without anyone noticing. Both the test fixture and the demo fixture already write trailing-slash ignore rules for all three workspaces, so the gate breaks nothing that exists and a scenario must remove that coverage deliberately.

Decision: one demo scenario exercises the refusal and covers both failure kinds in a single message — it strips the ignore rules for two workspaces and force-adds a tracked file under the third, so the rendering shows the missing-coverage group, its rules block, the tracked group, and its `git rm` block together, and stops at exit code 1. In the same change, `cli/AGENTS.md` records the boundary that makes this consistent: a preflight refusal earns a scenario when its message is structured — grouped lists or copyable blocks — and not when it is a single sentence.

Rationale: covering both failure kinds costs marginally more fixture setup than covering one and is the only way the grouped layout is ever seen whole, so a scenario showing half the message would pay most of the cost for part of the value. Writing the boundary into `cli/AGENTS.md` is what stops this from reading as a precedent that obliges thirteen further scenarios for one-line refusals; the line is drawn at formatting that can actually break.

## DR6: Of the four inherited verification gaps, only the demo timing coupling is closed; the other three are recorded as deliberate at the code

Scope: `cli/`

Context: the preceding thread left four accepted verification gaps. The demo scenario `07-runtime-prerequisite` couples its `afterMs` to a scripted case's delay window through a comment, because a `.mjs` scenario cannot import the TypeScript constant. The unverifiable-postcondition branch is unreachable end to end, since preflight rejects its only producible cause. The checkpoint validator requires each snapshotted stage `id` to name a catalog stage and checks nothing else about the descriptor, which is what allows the runner's pipeline-agnosticism to be proven with synthetic fixtures. The documentation test's "user-visible reason" assertion is a length-and-punctuation threshold that cannot distinguish a genuinely user-facing reason from a long internally worded one.

Decision: the governing rule is that a gap is closed when a future change could silently break something a user depends on, and recorded as deliberate when what it fails to check is either structurally unreachable or load-bearing by design. Under that rule the demo timing coupling is closed. The other three are kept as they are, and each has its reasoning written as a comment at the code it concerns — beside the unreachable branch, beside the checkpoint validator's stage-id check, and beside the documentation assertion — rather than only in this thread's artifacts.

Rationale: the timing coupling is the only one of the four where an ordinary future edit turns a scenario into a false pass without any signal, and the fact that the implementation report and the scenario's own comment give contradictory accounts of what a missed window does is evidence that the present behavior is not understood. The other three have no better mechanical form available: a test for the unreachable branch would have to fabricate a state the system cannot produce, tightening the checkpoint validator would destroy the property it exists to protect, and no assertion expressible in a test can judge whether prose is user-facing. Recording the reasoning at the code rather than only in a thread artifact is what stops a future maintainer from re-raising a concern whose answer lives in a document they will never open.

## DR7: The demo timing coupling is closed by a gated test, and the scenario's stale comment is corrected

Scope: `cli/scripts/scenarios/07-runtime-prerequisite.mjs` and its binding test

Context: DR6 closes the demo timing coupling. The scenario's `run` step fires its `during` hook at `afterMs`, which must land inside the window the scripted case `spec-correct-delayed` holds open, and the two values are related only by a comment. Working the outcomes through establishes that a value landing after the window lets both stages complete and exits 0, while one landing before it makes preflight composition refuse and exits 1; the scenario declares exit 2, so either miss already fails the demo loudly. The scenario's comment claims instead that a late value ends on the postcondition banner at exit 2 and would therefore pass while showing another scenario's rendering. That outcome is impossible: the catalog entry for `spec` promises only that `spec.md` exists, so deleting the thread's plan cannot violate it. The comment is residue from a draft whose first stage promised the plan. Separately, `SPEC_CORRECT_DELAY_MS` is exported TypeScript that a `.mjs` scenario cannot reach at runtime, because the demo executes the bundle, but that a test can import directly.

Decision: a gated test dynamically imports the scenario module and asserts that its `run` step's `afterMs` is strictly less than `SPEC_CORRECT_DELAY_MS`, so changing either value alone fails `npm run check`. The scenario's comment is rewritten to state what the code actually does: both a too-early and a too-late value produce an exit-code mismatch and a failed demo. The demo driver gains no output assertion.

Rationale: binding the scenario to the constant under the test gate reuses the pattern `pipeline/documentation.test.ts` already establishes for holding a non-TypeScript surface to the code, and needs no change to any documented rule. Teaching the demo driver to assert output was rejected because it contradicts the demo's stated contract of verifying exactly one thing per invocation, and buys nothing here since the exit code already discriminates every miss. Correcting the comment matters independently of the test: as written it describes a false-pass hazard the code cannot produce, which would send the next maintainer to fix a problem that does not exist.

## DR8: `DocumentReference.form`, `DocumentReference.raw`, and `gitCursor.headAtStageEntry` are removed

Scope: `cli/src/config/references.ts`, `cli/src/state/checkpoint.ts`

Context: three returned or persisted fields have no consumer. `DocumentReference.form` and `raw` are read nowhere in production code — only in the reference resolver's own tests — even though the type's doc comment claims they exist so a diagnostic can explain the routing; every diagnostic in that module is composed before a `DocumentReference` is constructed. `gitCursor.headAtStageEntry` is read in exactly one place, where it computes the value written straight back into itself, and it is printed nowhere, so it does not serve as a diagnostic either. Its sibling `observedHead` is genuinely consumed: resume compares it against current `HEAD` and reports the difference. The CLI is pre-release with an explicit licence to remove fields and no obligation to keep previously written state readable.

Decision: all three fields are removed. `gitCursor` becomes `{ stageIndex, observedHead }`. Every checkpoint literal in the test suite is updated in the same change.

Rationale: keeping `headAtStageEntry` under a "diagnostic-only" label was rejected because the label would be false — a value nothing reads and nothing prints is not a diagnostic, and documenting a purpose a field does not have repeats the failure mode DR7 corrects elsewhere. Retaining `raw` against a future diagnostic was likewise rejected: the raw reference is on the command line the user has just typed, which is where such a diagnostic would obtain it. The accepted cost is a mechanical sweep of every checkpoint literal in the test suite, which the type checker drives to completion; the preceding thread routed around that same sweep once, which is why the field survived until now.

## DR9: The five recorded duplications are consolidated, and `isPlainObject` moves into a new shared module

Scope: `cli/src/`

Context: five duplications were recorded across the preceding implementation. Four have an unambiguous home: the queue-reason assembly is duplicated between `runner.ts` and `classify.ts`, which sit in the same directory and where the classifier already owns the private originals — and the duplication is wider than recorded, covering `gateErrorMessage` and `pendingQueuesMessage` verbatim as well as the assembly itself; `describeContractSide` is duplicated between `runner.ts` and `resume.ts` and formats a type that `thread/artifacts.ts` owns; the harness membership list exists as an array in `config/execution.ts` and a set in `state/checkpoint.ts`, which already imports the `HarnessId` type from that module; and the `as HarnessId` cast sits inside the check that narrows it, in the same file as a hard-coded diagnostic list. The fifth, `isPlainObject`, exists as four byte-identical copies in validators under `config/`, `pipeline/`, `harness/scripted/`, and `state/`, and the CLI has no low-level shared module — every top-level directory under `src/` is a domain, and that layout is documented.

Decision: all five are consolidated. The queue-reason functions are exported from `classify.ts` and their copies in `runner.ts` deleted; `describeContractSide` moves to `thread/artifacts.ts`; `HARNESS_IDS` is exported from `config/execution.ts` and consumed by `state/checkpoint.ts`, which also resolves the cast and lets the adjacent diagnostic derive its harness list from that constant. `isPlainObject` moves into a new shared module under `src/`, imported by all four validators, and that directory is added to the layout section of `cli/AGENTS.md` in the same change.

Rationale: four byte-identical copies of the predicate every JSON validator in the codebase opens with is the shape of a missing module rather than incidental repetition, and leaving it in place guarantees a fifth copy the next time a loader is added; the cost is one line in the documented layout. The counter-pressure is real — the CLI's engineering principles list KISS and YAGNI beside DRY, and surgical-change discipline would leave a three-line type guard alone — but this thread exists in part to settle these duplications, and declining to settle the only one carrying any design content would leave the item where it started.

## DR10: Unmet artifact contracts are reported in plain language from one shared description table, and the prerequisite pause states the clean-worktree constraint

Scope: `cli/src/thread/artifacts.ts`, `cli/src/display/terminal.ts`, `cli/src/runner/runner.ts`

Context: when a stage's artifact prerequisite or promise is unmet, the closing block reports it entirely in the executor's internal dimension vocabulary — the `Artifacts:` list renders rows such as `plan: expected "brief", found "absent"` and `spec: expected true, found false`, and the `Detail` sentence above it renders the same values as `plan = "brief"` pairs. A reader unfamiliar with the project cannot tell that a brief plan means `plan.md` at the thread root with no `plan-tasks/` folder. The pause's action line compounds this by saying only to restore the artifact state the stage requires, which names nothing concrete and also omits that resume requires a clean worktree — `stage-prerequisite-unmet` is not among the pause kinds exempt from that rule, so following the line literally can end in a refusal. How the artifact was lost decides the remedy: a deleted tracked file is restored with a checkout and needs no commit, a newly written or modified tracked artifact does need one, and a gitignored artifact needs neither. A dimension can also be unmet with nothing missing at all, as when a strict plan is required and a brief one is present.

Decision: one description table, defined beside the artifact-state dimensions in `thread/artifacts.ts`, maps each dimension and value to a plain-language phrase naming the concrete file and its shape. The `Artifacts:` list renders its rows from that table, and `describeContractSide` — which DR9 already relocates to this module — is built on the same table so the `Detail` sentence and the list agree. The display layer composes no phrasing of its own. The table is exhaustive over the artifact-state dimensions by construction, so adding a dimension fails the typecheck rather than silently falling back to a raw value. The pause's action line stays a shared constant and becomes: restore the artifacts listed above and leave the worktree clean, then resume.

Rationale: putting the specifics in the `Artifacts:` list keeps them in the one place that is already per-dimension and structured, and lets the action line stay short, static, and true for all three restore routes; stating the constraint rather than a remedy is what makes it correct in every case. The same table fixes the `stage-contract-violation` block, which renders the identical list, so both banners improve from one change, and both are already covered by existing demo scenarios. Composing the action line dynamically from the unmet dimensions was rejected: it would turn a persisted checkpoint field into generated prose requiring validation and test coverage for every dimension combination, in order to repeat on one line what the line above already says. Exempting this pause from the clean-worktree rule was rejected as well — the contract pause is exempt because a dirty tree is exactly what it must inspect, whereas a prerequisite pause never launched an attempt, so the exemption would only let arbitrary uncommitted work ride into the next stage. The single-table constraint is what keeps this from spreading phrasing logic across the display and domain layers.

## DR11: The method docs absorb the meaning change only; the CLI's contract stays in the CLI's own documentation

Scope: `docs/glossary.md`, `docs/recipes/standard.md`, `cli/README.md`

Context: four documentation surfaces disagree with the code. The glossary defines a stage as an id, a skill name, a target, a Git policy, and a queue resolution, omitting the artifact prerequisite and the promised transition that the composition engine turns on. Two passages — one in the glossary, one in the Standard recipe — read as though the executor ships the `standard` pipeline, when what exists is a copyable document in the CLI's README that the user saves under their config root, after which the bare name resolves to it. The CLI's README groups `review-spec` with the stages permitted to touch `spec.md`, although its allowed-changes list is empty, its change requirement false, and its commit-subject template absent, making it the one supported read-only stage. The README's copyable settings block names concrete model strings whose only caveat sits far away in the smoke checklist.

Decision: all four are corrected. The glossary's stage definition gains the artifact prerequisite and the promised transition. The two pipeline passages state that a pipeline is a document the user authors or saves, with the CLI's README publishing a ready-made Standard one, and say nothing further — they do not absorb the document schema, the config-root layout, the reference grammar, or the stage-support table. The CLI's README moves `review-spec` out of the group permitted to touch `spec.md` and states that it permits no tracked change at all. The settings example gains a one-line note at the block itself recording that the models are examples validated against no provider; no model validation is added anywhere. All edits describe the corrected state as though it had always been so, with no note of what the text previously said.

Rationale: the glossary is the repository's naming authority, so a term whose meaning has moved must be corrected there; that obligation does not extend to importing the CLI's contract into the method documentation, where it would become a second copy to keep in sync across a module boundary the repository deliberately keeps thin. Validating model strings was rejected outright: the CLI cannot know a provider's catalog, and any allowlist would break on the next model release, so a note at the point of copying is the whole available remedy.

## DR12: The manual smoke checklist is removed from the CLI README and replaced by a short verification note in `cli/AGENTS.md`

Scope: `cli/README.md`, `cli/AGENTS.md`

Context: the CLI's README carries a fifteen-step, human-run smoke checklist against real Codex and Claude Code credentials. It has never been run and is not read, so it provides no assurance while standing as a permanently undischarged acceptance criterion. Eleven of its steps duplicate coverage the automated suite and the demo scenarios already provide — reference errors, the startup summary, profile overrides, suffix selection, listing — and its ignore-rules setup step is superseded outright by the preflight gate this thread adds, which refuses with the exact rules rather than asking a reader to remember them. Four steps describe things no automated test can reach, because the entire suite fakes the harness: a real session launching on the harness its binding names, the curated live stream against the verbose attempt log, a real boundary commit following a genuine `DONE`, and native session capture with out-of-band continuation. Only two files reference the checklist — the section itself and a phrase in the CLI's agent guidance listing it among the README's contents — and no test asserts it, so removing it cannot affect the check gate.

Decision: the checklist section is deleted from `cli/README.md`. A short paragraph — roughly four sentences, no checkboxes and no numbered ceremony — records in `cli/AGENTS.md` that the test suite fakes every harness and names the four things only a real harness can prove. It sits with that file's existing test-suite and scripted-harness material, and the phrase listing the checklist among the README's contents is removed in the same edit. The note claims no schedule and asserts that nobody runs it periodically.

Rationale: the note belongs in the agent- and developer-facing guidance rather than the published README because it describes this codebase's verification strategy, not the CLI's contract with a user; that placement also resolves the pointer rather than leaving the guidance referring to a README section that no longer exists. Deleting the section outright was weighed and rejected: the reason for removing the checklist is that its ceremony is never performed, and that reason applies to the fifteen boxes but not to the fact that every harness in the suite is faked, which is worth a paragraph where a maintainer will meet it. A consequence carried forward is that DR11's one-line note on the settings example becomes the only surviving warning that the example models are not reachable accounts, since that warning previously lived only in the deleted checklist.
