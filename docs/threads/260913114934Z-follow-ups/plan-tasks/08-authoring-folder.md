### Task 8: Replace `skill-authoring.md` with `suite/authoring/` and delete `method.md`

**Objective:** Give the suite's authoring conventions one home per concern — five files under `suite/authoring/` in the maintainer register carrying every rule this thread's decisions settle — and remove the two documents they replace, `suite/skill-authoring.md` and `suite/method.md`.

**Input / context:** `spec.md` § "Documents" (Deleted; `suite/authoring/` with the five files and their boundaries; "Where a current rule spans two of these…"; "The version-bump rule does not survive") and AC-9.1, AC-9.5 (for the two deleted files). Settled decisions: `decisions.md DR17` (the folder and its starting cut), `DR2` (three-part body), `DR7` (instruction rule with both tests and the inline guard), `DR4` and `DR16` (dead-concept test, the six sweep classes, description rule per role), `DR8` (model-invoked category definition), `DR15` (format skeleton), `DR9` (`method.md` deleted; no document describes a lifecycle or a sequence of skills), `DR11` (maintainer register), `DR14` (no version-bump rule). Material: `suite/skill-authoring.md` (438 lines, sixteen sections) is the source for every rule that survives; read it in full first, then decide for each section which file owns it. `suite/method.md` is deleted without a successor — its thread layout is now `formats/thread.md`, its project-layer conflict rule is now `consult-adrs`, and its lifecycle and recipes have no home by decision. Starts from the suite as left by task 7 (the bodies already follow the rules these files state, so write the rules from the decisions, checking a body when an example helps).

Register: maintainer documentation — written to whoever edits a skill in this repository; may cite ADR stems and name repository paths; states rules and their rationale in the present tense; describes the current state, never the diff (no "no longer", "previously", "unlike before"). Each rule has exactly one home; a second file may point at it in one line and never restates it.

**Steps:**

1. Read `suite/skill-authoring.md` end to end and map every section to one of the five files (or to "dropped": `## When a primitive is extracted`, the recipe-neutral naming rationale in `## When a capability earns a separate skill`, the version-bump rule, every sentence whose subject is a primitive, a recipe, an archive, or `docs/threads`).
2. Create `suite/authoring/skill-roles.md` (NEW): the two roles — **user-invoked** (a capability a person deliberately reaches for; `disable-model-invocation: true` in `SKILL.md` and `policy.allow_implicit_invocation: false` in `agents/openai.yaml`) and **model-invoked** (useful to an agent in any situation, whether or not an entry point is running, which entry points may also point the agent at; both restrictions omitted, the interface block alone); the `agents/openai.yaml` interface block (`display_name`, `short_description` written fresh); the rule that the two harness declarations never diverge and are changed together; the description rule per role (user-invoked: one short plain phrase saying what the skill does, because the harness withholds the description from the model and only a person reads it; model-invoked: precise and complete about when to invoke, at whatever length that takes, because the model routes on it); the group folders and that `model-invoked/` is named for the role; when a capability earns a separate skill (a materially different purpose, durable output, or execution contract — never a variant of an existing one); naming (user-invoked names in the user's intent language; model-invoked names as the act an agent performs, `consult-adrs`).
3. Create `suite/authoring/interaction-posture.md` (NEW): the three postures (dialogue-driven, completion-oriented, one-shot deliverable) and the central question; the completion-oriented preflight (validates the invocation input, required artifacts, tooling, credentials, safety gates — no thread resolution — and refuses with a precise re-invocation instruction, never a bundle); the dirty-worktree authorization rule; the two `BLOCKED` paths (queued human intent through the pending-decisions instruction; an unfixable operational defect with a diagnosis); clarification vs decision at resolution time; the **terminal outcome** (the line, the three tokens, the fixed name, that it composes with the skill's confirmation, that it always names a run's end state and never a thread's — a thread's lasting artifact is its **final deliverable**); the rule that only skills emitting it mention it and the authoring-silence rationale; internal progress as factual prose and **skill-local return tokens** (fixed name, never called status or outcome, never emitted in the terminal outcome).
4. Create `suite/authoring/body-structure.md` (NEW): the fixed section headings (`## Inputs` — list form, opens with the `/consult-adrs` and `/consult-glossary` items, then the thread files, primary input with its accepted forms; `## Procedure` — the single heading for an end-to-end sequence, absent from all-reference skills; `## Workflow` is never a heading); the three-part body (immediate inline content; conditional pointers; step-based pointers; what stays inline is what makes the skill that skill; pointers cite full skill-relative paths, woven into prose); the instruction rule (design-time test: name each step as a verb-noun act with no skill name — an act that can be so named and has a defined result is an instruction; review-time test: remove the skill's name and purpose from a block and read it; size and readership are not criteria; the inline guard: anything that only makes sense knowing which skill is running stays inline); write boundaries stated inline in every body; no legacy awareness (precise input contracts, no recognition of foreign layouts, mismatch handled as ordinary input ambiguity); the dead-concept test (does the negation forbid something a reader with no memory of the old design would plausibly do?); the six sweep classes with one line each (posture mismatch; dead-concept negation; restated guarantee; skill-independent block inline; routing prose in the body; repository leakage); what a review of a body may do (remove or replace a hit with the positive instruction it guarded, nothing beyond the hit); worked examples live in `references/` and carry no rule that exists nowhere else.
5. Create `suite/authoring/shared-references.md` (NEW): why copies are generated (a skill never reads another skill's `references/`); the canonical folder `shared/references/` and its three kinds — **formats** (an artifact's shape; the skeleton: `# <Artifact> format`, one paragraph, `## Shape`, `## Rules`, nothing else; vocabulary as an inline rule; never a command, procedure, or policy), **instructions** (one act, imperative, addressed to the performer, naming no skill; a format says what an artifact is, an instruction says how one act is done, never mixed), **trackers** and `repository-conventions.md` (conventions the suite reads rather than defines); the manifest contract (flat map, skill path → list of sources relative to `shared/references/`; a skill declares what it reads or writes); the sync script's ownership (deletes and rewrites exactly the declared files; orphans deleted by hand; never hand-edit a copy); editing a multi-reader instruction means checking every declaring skill.
6. Create `suite/authoring/side-effects.md` (NEW): write authority (one predetermined mutation contract per skill, no mode switches, stated inline) and the suite-wide boundaries as they stand after this thread — thread creation writes `seed.md` and `log.md`; `discussion`, `resolve-pending-decisions`, and `spec` append to `log.md`; `discussion` and `resolve-pending-decisions` write the thread's `adr/` and `glossary.md`; `spec` and `resolve-pending-decisions` amend `spec.md`; plan skills and `check-plan` write under `plans/`; implement skills write under `implementations/` and living documentation in scope; `close-thread` alone writes `docs/adr/`, `docs/glossary.md`, and the roadmap closing line and leaves the thread in place; `roadmap` alone creates an index; no skill writes another thread's files; an implementation skill never edits its spec or plan; the review contract (read-only; findings bundle or a concise pass; never `.pending-decisions/`); the filesystem-deletion rule (never delete user content unless asked; the pending-queue exception; bodies silent about deletion in both directions; "remains in place" wording); temporary workspaces (`.pending-decisions/`, `.pending-reviews/`, `.runs/` — created on demand, uniquely named per producer, one bundle per invocation, `.runs/` per invocation with the UTC-stamped directory name, factual progress records, never cited by a durable artifact).
7. Where a rule spans two files, place it under the concern a maintainer consults it for and let the other file point at it in one line (for example `interaction-posture.md` owns the terminal outcome; `body-structure.md` says in one line that a body mentions it only if it emits it and points there).
8. Delete the two documents: `git rm suite/skill-authoring.md suite/method.md`.
9. Search the five new files for `docs/threads`, `docs/roadmaps`, "primitive", "recipe", "archive", "version", "no longer", "previously", "unlike", and fix every hit that is not a live rule.
