# Decompose attempt settlement into the named gates its order encodes

`settleAttempt` in `cli/src/execution/phases/settlement.ts` is roughly 200 lines organized by four numbered section comments — the last function in the execution domain shaped that way, after `runCommand` was decomposed and the engine loop became one module per phase. `cli/AGENTS.md` states the rule this violates: a function long enough to need internal section comments is a set of collaborators that has not been named yet. Settlement already drives `verify-promise.ts` and `boundary.ts` as named sub-steps, so the pattern to follow exists. This is maintainability work rather than an active defect, and settlement is the densest safety-critical ordering in the run — the gate order is the product, and the module header already says so — which is the argument for naming its steps rather than leaving them inline.

The intended outcome is that `settleAttempt` states the gate order and drives named collaborators, with no internal section comments standing in for names. The purpose-shaped steps the four sections describe are identified and split between declared sub-steps under `phases/` and private helpers of one branch, then extracted without moving a gate, adding a checkpoint write, or changing which facts a settlement records. Each new sub-step gains a `PHASE_CALLERS` row naming `execution/phases/settlement.ts` as its one caller, following the rows `verify-promise.ts` and `boundary.ts` already hold.

The contract to preserve is the gate order exactly as it stands: re-scan the thread's pending queues, parse the terminal outcome on completion, and read the post-attempt `HEAD` for every settled attempt; treat a signal-caused abort as an interruption before ordinary non-DONE queue or harness-error classification, so a first-signal rejection is never relabelled, retaining the post-attempt scan's pending paths as its evidence; verify a recognized `DONE`'s promised artifact state before the Git boundary is looked at, so an unkept promise never reaches boundary evaluation and the completed attempt is preserved for a human repair to finalize; evaluate the Git boundary only once that promise holds, recording the tip the finalization left behind — boundary commit included — as the settled attempt's `headAfterAttempt`; then classify and settle into exactly one of three endings: the stage advanced, the stage succeeded but its queue holds the run, or the stage stopped and the run pauses. Beyond the order: a settled attempt and the pause it settled into remain one checkpoint document written by one `commitCursor` call carrying both transitions; `stageDisposition` keeps reading the attempt's own terminal token rather than the governing pause reason, so a stage refused while a pending bundle holds the run still reports `refused`; a `pause-done` settlement keeps reporting `stageSucceeded` and an advisory head movement keeps rendering as the `paused` disposition; attempt failure telemetry keeps riding on the reason the pause leads with; and no display event, wording, or emission order changes.

Verification is a trace comparison showing no reordering — retrace with `npm run trace` and compare against the baseline using `cli/temp/compare-traces.mjs` — the scenario catalog reporting the same verdicts, focused settlement, engine, recovery, boundary, and architecture tests, and `npm --prefix cli run check` passing.

Out of scope: changing the gate order, the classification rules, or which endings exist; any checkpoint schema or persisted-shape change; further decomposing `verify-promise.ts` or `boundary.ts`; changing terminal wording or display event shapes; and decomposition motivated only by a line-count target rather than a distinct reason to change. The work is independent of the sibling decomposition ticket #44 — the two touch different domains and can land in either order — and both are lower priority than an active defect.
