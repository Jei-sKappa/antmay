# Decision Log

## DR1: Scope the thread to `settleAttempt` alone

Context: The thread's premise is that `settleAttempt` in `cli/src/execution/phases/settlement.ts` is the last function in the execution domain organized by internal numbered section comments. Inspection shows that is not so: `launchAttempt` in `cli/src/execution/phases/attempt.ts` is a ~175-line function carrying two numbered section comments in a 247-line file, and it violates the same `cli/AGENTS.md` rule. It is the sibling half of the same engine step pair — `engine.ts` drives launch and settlement on adjacent lines. The question is whether this thread decomposes both.

Decision: This thread decomposes `settleAttempt` only. `launchAttempt` is out of scope here and is left to its own ticket, filed separately. Where this thread settles a convention that would govern any `phases/` decomposition — what earns a declared sub-step under `phases/` versus a private helper, and how a sub-step is named — that convention is recorded generally enough for the later `launchAttempt` work to apply it without re-litigating, rather than as a fact about settlement alone.

Rationale: The safety argument for this refactor is a trace diff against a recorded baseline showing no cross-module side-effect reordering. That argument's value degrades as the diff grows: a two-function decomposition whose retrace reports a reordering leaves the author bisecting their own change across two independent safety-critical orderings. The two functions share a folder and the architecture guard's caller table but share no ordering and no lifecycle concern, so decomposing them together buys much less coherence than the precedent of taking two sibling command procedures in one thread did. The trade-off is that a known second instance of the same violation stays in the codebase after this thread closes, and that a convention derived from one example may need revision when the second is attempted.

## DR2: Settle an attempt by folding a closed `Settlement` value through one writer

Scope: `cli/src/execution/phases/settlement.ts` and its extracted sub-steps

Context: `settleAttempt`'s largest section is the three mutually exclusive endings — the stage advanced, the stage succeeded but its queue holds the run, or the stage stopped and the run pauses — at roughly 95 of the function's 200 lines. Each ending amends the executing `AttemptRecord`, commits one checkpoint carrying both its transitions, emits one display event, and returns. Two of the three already share that skeleton through the private `settleIntoPause`, and the shared inputs already have a name in the `SettlingAttempt` type; only the advance branch sits outside both. `classifyAttempt` already returns a closed union of exactly the three actions.

Decision: The three endings are expressed as a closed `Settlement` union — the advanced ending, the done-pending-queues ending carrying its waiting value, and the stopped ending carrying its waiting value together with whether a signal-caused abort ended the attempt and whether a refused boundary's head movement is advisory — and one extracted sub-step folds that union exhaustively. The fold is the single place that amends the executing record, calls `commitCursor` with the settled attempt and the transition it settled into, emits the settlement's display event, and produces the return value. The orchestrator's branches construct the `Settlement` value and do nothing durable themselves. Adding a fourth ending must therefore fail to compile until it states what it records and which event it draws.

The fold reproduces the three record shapes exactly as they stand: the advanced ending carries no `pendingFiles` key, the done-pending-queues ending carries `pendingFiles`, and the stopped ending carries `pendingFiles` only when non-empty plus a `failure` taken from the reason its pause leads with, with `result` being `interrupted` for a signal-caused abort and `waiting` otherwise. Where placing those shapes side by side shows one to be equivalent to another under a fact that holds at that ending — a done-pending-queues pause always observes a non-empty queue, so an unconditional and a conditional `pendingFiles` cannot differ there — the spec states that fact explicitly and a test pins the serialized record, rather than the unification being made silently.

Rationale: The fold completes a factoring the module had already begun for two of its three endings, where giving each ending its own module would have had to undo that sharing to reach surface symmetry. It also keeps the thread's central invariant structural instead of reviewable: one checkpoint write carrying a settled attempt together with the pause it settled into is enforced by there being one write site, rather than being a property to re-verify in three files. This is the same shape the execution domain already relies on one level down, where every cursor movement is a named transition applied through one reducer and pauses are built by one module per situation, so settlement stops being the branch-shaped exception between them. The principal trade-off is a second vocabulary above that transition vocabulary, which a reader must place — a transition says how the cursor moves, while a settlement says how an attempt ended, bundling the attempt result, the transition pair, and the display event that no transition carries — and one indirection between a branch and the record it produces. Bringing the three record shapes onto one screen is what makes the `pendingFiles` asymmetry between them legible at all; it is invisible today only because the writes sit sixty lines apart.

## DR3: Keep the gate sequence inline in the settlement orchestrator

Scope: `cli/src/execution/phases/settlement.ts`

Context: Beyond the three endings, `settleAttempt` opens with a post-attempt read of the pending queues, the terminal-outcome parse on a completed attempt, and the post-attempt `HEAD` read, then a signal-abort guard, then the promise gate and the Git boundary. The question is which of these become extracted sub-steps. The reads are three independent operations with no ordering constraint among themselves, and the `HEAD` one produces a value the boundary finalization later replaces, because that finalization owns every Git observation the boundary makes.

Decision: The gate sequence yields no new module. The three reads open the orchestrator as straight-line code; the signal-abort guard stays inline as a guard clause calling the existing interruption collaborator; the promise gate and the boundary gate remain one call each to the sub-steps that already exist. The numbered section comments are removed and the order they narrated is carried once by the module's own doc comment, which already states it.

Two pure pieces are extracted as private helpers inside the module rather than as sub-steps: the assembly of the stopped path's waiting diagnostics from a failed outcome, and the construction of the refused-boundary argument the stopped pause builder receives.

Rationale: The gate order is what this thread exists to make legible, and the signal-abort guard's position is itself the safety claim — that a first-signal rejection is never relabelled as a harness error or a queue hold — so moving it behind a call would hide the one gate whose place in the sequence is the property. Bundling the three reads into a value would produce a struct destructured on the next line, one of whose fields is overwritten downstream, which is the decorative seam the engineering philosophy warns against and the line-count-driven extraction this thread rules out. The recovery tree's evidence-gathering module is not a precedent for the opposite conclusion: it branches over the recovery vocabulary and assembles a classified case, whereas these reads decide nothing. The trade-off is that the orchestrator remains around ninety-five lines — longer than brevity alone would want — with the compensation that every line in it is a named gate call or a value construction and nothing stands between the gates and their reading order.

## DR4: A `phases/` module is one that reaches outside the execution domain

Context: This thread must place each piece it names either under `phases/` as a declared sub-step carrying a row in the architecture guard's caller table, or as a private helper. The criterion for that placement was not written down anywhere, and it governs any later decomposition in the same domain.

Decision: A module under `execution/phases/` or `execution/entry/` is a step that reaches outside the execution domain — the filesystem, Git, the checkpoint writer, the attempt log, the harness, or the display seam. A pure transformation of values already in hand is not a sub-step: it is a private helper in the module that branches on it, or, when more than one phase needs it, a pure module in `execution/` root beside the pause builders and the recovery vocabulary. Caller count and length decide nothing; the guard table's one-caller rule is a constraint a sub-step must satisfy rather than a reason for it to exist.

Applied to this thread, that yields exactly one new module: `cli/src/execution/phases/commit-settlement.ts`, exporting `commitSettlement` and declaring the `Settlement` union beside it, the way the promise-verification sub-step declares its own observation and verdict types for the orchestrator to import. It qualifies because it performs the durable checkpoint write and emits the display event. The guard's caller table grows by exactly that one row, naming the settlement orchestrator as its one caller. No `phases/settlement/` subfolder is introduced — a directory holding one module adds a level of nesting and conveys nothing — and the module's pure helpers, including the two existing ones that build the stored terminal-result candidate and read the stage's disposition, stay private to the orchestrator.

Rationale: The criterion is descriptive of the ten rows the guard table already holds rather than newly imposed: every module under those two folders reaches the world, while the domain's pure modules — the pause builders, the recovery vocabulary, and the recovery decision table that is documented as touching nothing — deliberately sit outside them. The competing criterion, that a sub-step is a step the engine loop itself names, is contradicted by the promise-verification and boundary sub-steps, which the settlement phase drives. Holding the line at effects keeps the caller table meaning "these are the steps that touch the world", which is the property that makes reading it worthwhile; admitting pure helpers would dilute it into an inventory of files. The trade-off is that a long pure helper stays inside a module that is already long, so length alone will never be grounds for promoting one.

## DR5: Commit the trace comparator and regenerate the baseline

Scope: CLI verification for this decomposition

Context: The thread's acceptance rests on a trace comparison proving that moving code changed no cross-module side-effect sequence. `npm run trace` is a committed developer tool — `cli/scripts/trace.mjs` over the four pieces in `cli/scripts/trace/` — that deliberately sits outside the check gate, as the demo does. The comparator it is paired with does not exist in the repository: `cli/temp/compare-traces.mjs` lives under a root-gitignored, untracked `temp/`, on one working copy. That comparator is the right instrument for this refactor, because it reads the ordered call sequence from the raw per-call records rather than the rendered call tree, compares by function name filtered to the names the baseline already carried, and reports newly visible names and re-attributed modules separately rather than as differences — which is exactly what a moved function and a closure promoted to a top-level declaration produce. A local trace directory from an earlier date also exists, predating more than a dozen commits to `src/`.

Decision: The comparator is promoted into the repository as `cli/scripts/trace/compare.mjs`, exposed as an `npm run trace:compare` script and named in the list of trace pieces that `cli/scripts/trace.mjs` already carries in its doc comment. It stays outside `npm run check`, alongside the tracing and demo tools it belongs with. The trace baseline this thread compares against is regenerated from the thread's own pre-change `HEAD`; no pre-existing local trace directory is reused as a baseline.

Rationale: An acceptance criterion executable only on one untracked working copy cannot be checked by anyone but its author, and in this repository the checker is often an agent in a fresh checkout that has no such directory — so committing the comparator is what makes the thread's central safety claim verifiable at all. It also serves the sibling decomposition the scope decision defers, which needs the same instrument for the same reason and would otherwise rediscover, reimplement, or skip it. The cost is scope growth beyond the ticket's stated boundary, which the spec states plainly rather than absorbing silently; it is small in practice, because the tool already exists and works, leaving a move, a script entry, and one sentence of documentation. Reusing the older local trace directory would compare this change against a tree that predates the command decomposition and much else, so any difference it reported would be unattributable.

## DR6: Pin the settled record shapes at the engine boundary

Scope: CLI verification for this decomposition

Context: The settlement fold becomes the single site producing the three distinct serialized attempt records, and the spec must pin those shapes so the promised no-change property is checked rather than asserted. The choice is whether that assertion sits at the engine boundary or in a focused test on the fold itself. No module under `cli/src/execution/phases/` has a test file today; every phase is proven by running it through `cli/src/execution/engine.test.ts`, which already reads settled attempt fields off the durable checkpoint, including `pendingFiles`, `headAfterAttempt`, and the attempt's result. Those `pendingFiles` assertions cover pause paths only; nothing asserts that an advanced attempt's record carries no `pendingFiles` key.

Decision: The three record shapes are pinned at the engine boundary in `engine.test.ts`, with one regression case added for the advanced ending asserting that its serialized attempt carries no `pendingFiles` key. No test file is introduced for the settlement fold, and none for any other phase module.

Rationale: The serialized checkpoint is the actual contract surface — it is what a later resume reads and what checkpoint validation judges — so an assertion there proves the property, while a focused test on the fold would assert an in-memory object that the same assertion already covers. The absence of phase-level unit tests is a property rather than an oversight, and it is the same one the guard table's single-caller rule protects: a phase is meaningful only in the order it runs in, so it is proven by being run. Introducing the first exception for a fold whose inputs are wholly determined by the engine's own paths would buy duplicate coverage at the cost of that property. The trade-off is that a failure in the fold is reported by an engine-level case rather than located precisely, which is acceptable because the fold is small and has exactly one caller.
