# Ticket tracker integration for thread creation and closure

The Antmay method currently starts every unit of work from a local seed written by `/open-thread`. Work that originates in an external issue tracker has no first-class path: the tracker reference can be recorded in the seed's `External:` field, but nothing creates the tracker entry, nothing opens a thread from one, and nothing reconciles a shipped thread back against it.

We want to close that loop for GitHub, with three capabilities in mind: creating a tracker entry from a rough idea, composing its description in the same restrained, need-shaped style as a seed rather than an exhaustive spec, and optionally applying a marker label (`antmay` or `thread`) so Antmay-managed entries are identifiable; opening a thread from a marked entry, with the entry's identifier or title feeding the thread's slug, and possibly a mode or sibling skill that works from an unmarked entry too; and a way to check whether marked entries have already been implemented by a thread so they can be closed.

Only GitHub is in scope for now — no Jira, ClickUp, or other trackers. But the vocabulary and boundaries should be designed generically from the start, speaking of *tickets* rather than *issues*, so a second tracker can be added later without reshaping the skills. The shape of the integration is deliberately open: how many skills versus modes, where the tracker boundary sits relative to `/open-thread`'s current stance that external references are passive and read-only, and whether implementation-checking belongs in a skill at all are all questions this thread should settle. Dissenting analysis is explicitly welcome.
