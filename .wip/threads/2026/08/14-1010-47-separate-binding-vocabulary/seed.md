# Separate the local binding vocabulary from the documents that carry it

`cli/src/config/execution.ts` is a single module of roughly 487 lines that carries four things changing for different reasons: the local binding vocabulary together with the intrinsic timing defaults, the strict `settings.json` schema, the strict execution-profile schema, and the rule that resolves one selected stage's complete binding from those two sources.

Two concrete signals, rather than the line count, argue for separating them. First, the consumers are already one per concern while the module they read from is not: the run preflight tree was decomposed along exactly this seam, so `commands/run/preflight/load-settings.ts` wants `loadStageSettings`, `load-profile.ts` wants `loadExecutionProfile`, and `snapshot-stages.ts` wants `resolveStageBindings` — each imports one symbol and gets a module that also reads files, validates two unrelated document schemas, and declares the vocabulary. Second, the checkpoint vocabulary reaches this module only for a declaration: `cli/src/state/checkpoint/types.ts` imports `ResolvedStageBinding` from here. The architecture test holds that vocabulary to type imports and type declarations only and the import is type-only, so nothing is violated today, but a reader following the checkpoint's own binding type lands in a module that calls `fs.readFileSync`. The earlier checkpoint split established the opposite posture for exactly this reason: a consumer's import list should say whether it loads a document, validates one, or only names a shape.

This is maintainability work rather than an active defect, so every accepted and rejected document shape must remain stable. The contract to preserve: a missing `settings.json` succeeds as the canonical empty document while a present one is validated strictly and reports every discoverable problem at once against its resolved path; a missing execution-profile document at an already resolved path is an error rather than a prompt to look elsewhere; only `<config-root>/settings.json` is read for settings, no file is ever created, and no environment interpolation is performed; a selected stage takes its whole binding from one source document — the profile when the profile binds it, settings otherwise — with fields never merging across the two, so a profile entry can inherit neither a settings timing value nor a settings harness; only the intrinsic defaults fill an omitted timing field and those defaults keep their current values; harness and model stay one indivisible validated pair; a selected stage bound by neither source is an error naming that stage, and every such stage is reported together; diagnostic order and wording are unchanged for all three entry points.

The intended outcome is that the module is separated along its reasons to change — the vocabulary and defaults, the settings document, the profile document, and binding resolution — deciding along the way whether the two document schemas warrant one module each or share a validator module for the stage-binding map they both accept; that `state/checkpoint/types.ts` points at the declaration-only module so the checkpoint vocabulary reaches no module performing I/O; that the three preflight steps each narrow to the module they need, with no barrel, index, or re-export spanning the split; that the tests follow the modules they cover, splitting `config/execution.test.ts` accordingly; and that focused config, preflight, snapshot, checkpoint, documentation, and architecture tests pass along with `npm --prefix cli run check`.

Out of scope: any settings or execution-profile schema change, including renaming a key or relaxing unknown-field rejection; changing which source document wins or introducing any field-level merge between them; changing the intrinsic timing default values; revisiting harness identity ownership, which a separate issue covers; and decomposition motivated only by a line-count target rather than a distinct reason to change. The work is independent of the checkpoint-validation decomposition and of the settlement decomposition; all three are maintainability work behind any active defect.
