# Required-output assertions for the demo scenario catalog

The 32 scenarios under `cli/scripts/scenarios/` are `cli/AGENTS.md`'s executable UI contract for Antmay's terminal interface, but they assert nothing about what they render: a scenario declares one expected exit code per invocation and the driver compares only that. Because every pause exits `2` and every preflight refusal exits `1`, a scenario that reaches *a* pause instead of *its* pause still passes, and the driver itself already notes that a scenario failing preflight before reaching its subject is reported as `[PASS]` for the wrong reason. The call-trace report makes the gap measurable: nine pause builders in `src/execution/pause.ts` — `queueBlocked`, `queueUnreadable`, `prerequisiteUninspectable`, `contractUninspectable`, `refreshPendingBundles`, `refreshQueueUnreadableHoldingDone`, `refreshPromiseUninspectable`, `refreshPromiseUnmet`, `refreshBoundaryRefused` — are reachable in ordinary use and no traced scenario calls any of them, against a rule that every distinct terminal rendering has a demo scenario.

The intended outcome is a required-output declaration per scenario — one or more substrings or regexes the driver checks alongside the exit code — with all 32 existing scenarios filled in. Markers pin a rendering's identity (`WAITING FOR USER`, `STAGE CANNOT START`, `git policy violation`, `PAUSED — stage contract`, the `Continue` line, the printed resume command) without turning every wording change into a test edit; full transcript snapshots are explicitly not wanted. The per-scenario `transcript.txt` files already under `cli/temp/mytraces/` are a ready source for choosing those markers.

With assertions in place, each of the nine unreached renderings is then settled deliberately — either a scenario reaches it, or it is consolidated into a neighbour a reader cannot distinguish it from — and re-running `npm run trace` turns the uncalled-function list into a standing coverage report for the rule. Editing the `cli/AGENTS.md` paragraph that currently places `npm run demo` outside the assertion surface and outside the check/CI gate is in scope, because giving scenarios an assertion surface contradicts its premise. Whether the suite then joins `npm run check` is deliberately out of scope and unsettled: the gate runs in about 90 seconds today and 32 scenarios that each build and spawn the binary against isolated `/tmp` fixtures would dominate it, so add the assertions first, measure, then decide.

Two neighbours: issue #37 names two specific renderings with no scenario — the at-rest interrupted run summary and the `warning:` line — found in the same trace report, and is two instances of what this mechanism serves, best taken inside this work or immediately after it. And once scenarios assert their own output, `src/display/terminal.test.ts` (1,213 lines asserting exact terminal text, with only 10 snapshot assertions in the whole suite) becomes substantially reducible because the scenarios would carry the UI contract rather than merely demonstrate it; that reduction is a follow-up decision, not part of this.

Shared constraints carried by the ticket: `npm run check` must pass on every change — typecheck, vitest and build, with no failing tests, type errors, half-migrated code, or red scenario. When a guard in `src/architecture.test.ts` fails, the boundary moved: argue the direction rather than relaxing the guard to match the new import, and the guards end up stricter, never looser. The terminal-outcome protocol keeps its exact `DONE`, `BLOCKED` and `REFUSED` token values and its `Outcome: ` prefix, since root `AGENTS.md` names it as load-bearing coupling between the skill suite and the CLI; changing who declares the vocabulary must never change what it is. Catalog entries in `src/pipeline/catalog.ts` stay plain JSON with no methods, because a checkpoint snapshots `SnapshottedStage` verbatim and resume reads only the checkpoint. The pre-release licence applies: rename and remove freely, write no migrations or compatibility shims, and say plainly in the commit message when a change makes existing run directories unreadable.

This is the first of three related pieces of work and comes first on purpose: it changes no production code, so it carries no behavioral risk, and its assertions are the safety net that makes the other two verifiable. Issue #39 splits three concepts that have no single owner, including a checkpoint module with 27 production importers; issue #40 decomposes a 465-line command procedure whose step ordering is safety-critical. Both want scenarios that fail loudly before they land.
